# Report 15 — Day 8, Thursday 2026-10-29, 18:00 ET

The Investors asked whether a widget can update without the app running. At 08:05 I ruled yes, within Apple's limits: Python will run inside the widget itself, switched on only after real-iPhone tests. That moves submission from Day 17 to Day 25, or Day 28 if those tests fail. The rest of the day built and hardened that path, and a review loop that ran too long was closed with a written threat model. Revenue is $0 of $200.

## The story of the period

**Highlight: the Investors asked for a live widget, and we changed the plan for it.** At 07:19 an Investor asked on #41 whether widgets can update live. In version 1 as planned, they could not. A widget is drawn by a small separate program, the widget extension. iOS wakes it on its own schedule, and ours could only redraw the picture the app had last saved. New data waited for someone to open the app. At 07:33 the Investors made solving this the current priority. They made the Day 17 launch flexible and asked for a deep search for a widget that updates with the app closed.

Wrenna did that search first. By 07:46 she had L20, a ranked list of every route she could find. She read seven of Apple's public pages, the iOS 27.1 software kit on our Mac, and the documentation of Scriptable and Pyto, two apps that already run scripts in widgets. Her finding: no route is truly live. iOS gives a Home Screen widget about 40 to 70 reloads a day, 15 to 60 minutes apart, and Apple decides when. Idris and Pernille then wrote their views separately, without seeing each other's.

At 08:05 I ruled. ADR-007 is our decision record for how scripts run. Its lane (c) means Python runs inside the widget extension itself, on every reload Apple grants, with no app alive. It is built for 1.0 behind a switch that is off in code. A device test session sets the switch, on Days 22 to 23, after #100. A Simulator number never switches it on. If the device tests fail, we build the simpler option (b) instead: declared web fetches done in Swift on each reload, which we call bound fields, and submit on Day 28. Pernille argued for building bound fields in 1.0 regardless. I recorded her dissent and the reason I did not take it: we can build the same fallback at the same price after the verdict. The reply on #41 lists each option with its limits and its delay in days. Wrenna then wrote the App Guide page: every way to keep a widget fresh, with four worked examples. It says "every 15 to 60 minutes" and never "live" (T-0681).

At 10:17 an Investor wrote that this work does not need Fable, our most capable and most expensive model. The ruling had already run on Fable. The build work follows our usual model table, Opus for design and build.

**The pieces that landed for it.** Pernille built the Python half of the lane at 08:34 (T-0676). A widget script can be marked to run in the widget. Saving it checks that it imports only a small, light list of modules, and the widget refuses anything heavier with the same message. That keeps the widget inside its memory. Idris built `pywidget.net.get` at 09:01 (T-0677). It lets a widget script fetch from the web through iOS's own secure connection, so it never loads Python's heavy network code. Odalys's review found that one bad 1 MB answer could cost about 20 MB of memory at once. That is too much inside a widget (T-0686). Idris set separate caps for each process. In the app, a body may be up to 1 MiB. In the widget, 256 KiB, with the reply to Python capped at 512 KiB (T-0691). Idris then re-measured, counting costs the first test left out, and Pernille reviewed the method. The worst case is now 4.19 MiB, measured in the app, not yet in the widget (T-0698, T-0699).

**The app now writes widgets by itself.** At 08:25 Idris landed T-0512, the app's write path. Before it, only test hooks wrote a widget's picture. Now placing a Python widget, changing what it shows, opening the app, or the Refresh Widgets shortcut runs that widget's script and updates the Home Screen. Odalys reviewed it (T-0683). She found that one stuck script could freeze the Refresh Widgets shortcut forever. She also found that every return to the app reran every widget. Idris fixed both by 09:32. A stuck run now gives up on that widget. One refresh runs at a time, at most every 30 seconds unless widgets changed (T-0689, T-0690).

**What went wrong: a review loop with no finish line.** The lane's guard must keep one widget script from weakening the guard for the next one. Odalys reviewed it eight times between 09:40 and 17:11: T-0685, T-0704, T-0710, T-0713, T-0717, T-0727, T-0731 and T-0734. Pernille fixed each round. Each round found something smaller, and each one was real. But the later finds all needed a script that tampers with Python's own internals on purpose. Nobody had written down whether that was in scope. That was my job, and I did it late. At 16:54 I wrote the threat model (T-0733). The lane protects people from crashes, lost data and wrong blame for ordinary scripts. It does not defend a person's widgets against that same person tampering on purpose. At 17:11 Odalys's last check passed with no false alarms on the Mac or the Simulator (T-0734). Pernille then wrote the seven deliberate routes the lane does not stop, which we call Not held, each with what still catches it (T-0735). The lesson is mine: write the bar before round two.

**The package sandbox: a tested block, not an escape attempt.** `pkg_sandbox` is the locked box on our Mac mini where downloaded Python packages would be built. Odalys re-checked it at 17:42: all earlier holes are closed and 182 of 182 tests pass (T-0362). She left one route to me. A process in the box might ask LaunchServices, the macOS service that opens apps, to start something outside the box. At 17:45 I ruled against trying to break out to prove it (T-0738). Pernille will block that route and test that the block holds (T-0739). Odalys will re-review it (T-0740). The hold on real package runs (T-0299) stays until both are done. At 12:11 the Operator had already moved numpy, Pillow and matplotlib to version 1.1, because no permission rule for building them was in place by the noon deadline (T-0287). So nothing real runs in that box for 1.0. That also closed the last pending alpha row: A8s, the native-package import check, is now n/a (T-0513).

**Projects slice 2 is ready for after the alpha.** Projects and Files lets a script live in a folder with other files. Slice 2 adds import and export of .py files and zips, on a separate branch. Pernille's review found that a file ending in capital .PY was imported and then hidden (T-0722). Idris fixed it (T-0723). Her next check found that a zip full of same-named files froze the app for minutes. Now 1,000 copies import in a quarter of a second (T-0726, T-0728). It merges after the alpha commit, 10-31 12:00.

**The test widget is out of the shipping build.** A widget we used only to time Python's start-up showed in the widget gallery as "Python result". Idris removed it from the extension, with a test that checks the built extension's own bytes (T-0674). Odalys approved it at 18:05. Her review also found that alpha row A3's add-a-widget test passes on any of our widgets already on the Home Screen. On the test Simulator there were 30. So it cannot show that the add placed one. That is T-0743, first thing next session, before the dry run.

**What went wrong: build statistics lost at 16:18.** In Idris's Projects worktree, a separate checkout of the code, a `git checkout` threw away about 22 uncommitted lines of ops/metrics/xc.jsonl. That file records each Xcode build's run time. The lost lines covered this afternoon's branch builds. So the measure for experiment OPT-040, the share of time Xcode is busy, is short those runs. The rule now: after an Xcode task, restore only ops/site-checks/, never ops/metrics/.

**What went wrong: a wrong task number.** At 12:49 Pernille cited T-0708 for Idris's Swift half in a done-note, before reserving a number. T-0708 belongs to Wrenna. The right line is T-0709, and the board now says so. She logged it herself.

**An experiment ended with no effect.** OPT-032 tested giving workers a short task briefing instead of their whole notebook. After ten sessions per arm it cut start-up lookups by 1.40 on average, short of the 3 it needed (p 0.233). The old way stays. The model-routing trial, which tests cheaper models for routine work, takes its slot (T-0596).

**Decisions and why**

- **T-0671 (08:05), widget freshness:** lane (c) built for 1.0 behind the switch, opened only by device tests; submission Day 25, Day 28 if the tests fail. The Investors prefer Python in the widget, and it is the freshest route without a server. Pernille's dissent is recorded.
- **T-0733 (16:54), the lane's threat model:** protect against accidents and wrong blame, not deliberate self-tampering. Without a written bar, a review loop never ends.
- **T-0720 (16:54), folded, not built:** a script deleting the widget's demotion file on purpose is a known limit. The next run's report or a memory kill demotes the widget again.
- **T-0738 (17:45), package sandbox:** a tested block on the LaunchServices route, no escape probe. The hold on real package runs stays.
- **T-0596 (17:37), Odalys:** OPT-032 closed with no effect; model routing becomes the main trial.

**What was learned**

- A bold option is honest only with its date and its failure date written beside it.
- A security review needs a written threat model before round two, or every round finds one more thing.
- Measure in the place that matters. The net.get memory numbers are from the app process; the widget's own number waits on T-0696.
