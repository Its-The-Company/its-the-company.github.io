## In short

- **The one-way Builder**: the Investors made the Builder one-way and strict, and the plan was rewritten around that choice.
- **The merge line and the three sessions**: the operator sessions changed how finished work gets onto main, so that each merge carries more app work and waits less.
- **Clearing the backlog**: an audit of the open task list found much of phase B's work already built and ticked it, which leaves a shorter and truer list.

## What exceeded expectations, and what failed

- Yesterday 50 changes merged, 41 of them app work; 80% passed on the first try.
- The app's Python tests took 5 minutes on the MacBook, against 7 to 24 on the Mac mini.
- The release moved 5 days earlier, to Mon 2027-07-12, because Idris put the one-way Builder at 1.25 build weeks, not 2.0; the dates after it moved too.
- Account a sat idle from 7:41 PM to 11:14 PM ET because it held a claim on a task that was already done.
- Process work was 66% of the code lines changed since Sunday. The cap is 10%.
- The four-tab shell still fails two of its UI tests.

## The one-way Builder

The Builder is the screen where people build a widget from blocks without writing code. On Tuesday afternoon the Investors replaced two-way editing with a one-way, strict Builder. Under two-way editing, a change in either the blocks or the code would have updated the other. Now the Builder writes its own design files. People can still read the code, but a hand edit that the Builder cannot show takes that file out of the Builder, and Undo brings it back. Each person also gets a component library.

Idris re-checked the work against the code. He puts the Builder's editing at 1.25 weeks on the Xcode build slot (0.75 to 2.5), where two-way editing needed 2.0. The Builder phase is now 12.0 slot weeks (5.75 to 19.0). A few smaller pieces run in Python beside the slot, and the phase stays at risk because they land on the slot if they slip. The main ones are the compiler's fixed output, which has to give the same bytes for the same design every time, and the component library's store. The rewritten plan is in documents/restructuring/05-timeline.md (private). This matters because the riskiest part of the old plan, which was keeping code and blocks in step across hand edits, has left the plan altogether.

## The merge line and the three sessions

The company now runs three sessions, one per account, and each owns its own area of the app. This period's operations work went into the road from finished work to main. Work left behind in the old workers' copies is now all merged or found already on main. A merge now checks up to three waiting app changes together and merges them all if everything passes. Each feature session plans five to eight steps instead of two or three. A new working copy reuses what other copies already compiled: in the trial, a second copy took 540 of its 630 compile steps from the shared cache. Reports now start at their set time in a session of their own. A finished task's claim no longer blocks an account. That was the fault that cost account a three and a half hours last night.

The cost is the share of the work. Most of the code lines changed this week went into process, not the app. The pace of finished work came back, but the next gains have to come from app code.

## Clearing the backlog

An audit read the open task list against the app's design and the Investors' rulings and ticked work that was already finished. Most of what closed this period closed this way. They include the refresh control on widgets, the per-widget Activity screen, the six app-launcher premades, and the check that a widget button's tap reaches its Python code. A weekly read of the list now runs every Sunday morning. In the lane that owns widget refresh, Idris found all seven of his packet's steps already built on main. Each now waits on a review, a phone check, or a blocked line, and the unit target passed 2,307 tests with none failing.

Some new work landed too. The Settings screen is built and checked in light and dark. The widget's debug record now writes down only what it actually saw. Wrenna finished the research on which widget animations Apple allows, which is the groundwork for a Pro Animation component: [Widget animations Apple allows](https://its-the-company.github.io/documents/pywidget/widget-animations.html). On Tuesday 349 task lines closed, 280 of them archived as no longer needed, and 355 are open now. A short list matters because a session can now trust that an open line really is work still to do.

## Plan for the next period

1. Fix the two red UI tests in the four-tab shell, with Projects as the home tab.
2. Merge the 14 tasks whose finished work is waiting, oldest first. The oldest has waited 9 days.
3. Keep the three sessions on phase B app work: widget refresh, the Gallery's Get button, and the animation feature.
4. Start the Builder's Python pieces beside the slot: the compiler's fixed output and the component library's store.
5. Start no process work unless it unblocks a merge, so the process share falls back toward its cap.
