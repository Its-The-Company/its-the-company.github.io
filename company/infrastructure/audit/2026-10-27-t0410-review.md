## Part 1: T-0408

**`_add_app_packages` (runner.py).** It puts `<bundle_root>/app_packages` right after the last `sys.path` entry
inside the bundle or the stdlib, removes any earlier copy, and runs before `_snapshot()`, so `_reset` puts it
back. It imports nothing and reads no `.pth` file. If the folder is missing, it adds nothing. The order matches ADR-003 s3.6 item 3.

Who shadows whom:
- *The bundle shadows the user's packages folder.* `paths.add_user_packages` puts the folder after the last bundled
  entry, which is now app_packages. This is intended: the installer resolves user wheels against the bundled
  dist-infos (s3.6 item 1).
- *The user's script folder shadows the bundle, and the stdlib too.* A file run does `sys.path.insert(0, dirname(script))`.
  That is CPython's own rule and what a Python user expects. Editor runs insert nothing. This is acceptable.
- *Finding (P3): a cross-run leak.* `_keep_module` keeps any module whose file is under bundle_root. None of the
  eight packages is imported at bootstrap, so all of them are first imported during a run, with the script's folder
  at `sys.path[0]`. Suppose a bundled package imports a name the script's folder also holds. The bundled module then
  binds the user's module, and the bundled module outlives reset while the user's module is cleared. Probe
  (host, the real runner through bridge_driver): `app_packages/bpkg` does `import dep`, `app_packages/dep.py`
  says "bundle", and `scripts/dep.py` says "user". Run 1, a file run: `user user`. Reset. Run 2, an editor run:
  `bpkg.dep.WHO, dep.WHO` = `user bundle`. One run now sees two copies of `dep`. It bites in practice when a user
  keeps an `idna.py`, `certifi.py` or `urllib3.py`, or a stdlib-named file that requests imports for the first time,
  beside a script. This is not a safety issue (it is the user's own code), but results then depend on what earlier
  runs did.
- *Latent (P3):* nothing in the app calls `store.activate()` yet. When it is wired, `bundled_roots` must include
  bundle_root. With the stdlib alone, the user's folder lands before app_packages.

**AppPackagesPathTests.** All 3 pass on 3.9.6 and 3.13.18. I seeded 4 mutants of my own, separate from the author's
3, and each fails the class: stdlib clause dropped (1 failure), call moved after the snapshot (1), no dedupe (1),
insert before the last bundled entry (2). Test 1 uses the installer's real placement rule, loaded from its file,
and imports a marker that both folders hold. It shows the bundle wins and that reset restores the path.

**log/assets.md rows.** I checked all eight wheels in ~/.cache/pywidget/packages against manifest.toml (sha256 and
bytes) and read their licence files and METADATA as zip data with python3.13 -I. Licence, version, copyright holders
and the presence or absence of a NOTICE file all match. Two rows need more:
- jedi: the row gives the vendored typeshed as Apache-2.0. Its LICENSE file also says "Parts of typeshed are
  licensed under ... the MIT license" (Copyright (c) 2015 Jukka Lehtosalo and contributors). The components
  registry already says "Apache-2.0 AND MIT". The notice ships whole, so the attribution duty is met; only the row
  is short.
- requests: "the wheel has no NOTICE file" is true. Since T-0411, the tag's NOTICE ships in Acknowledgements, and
  the row should say so.
- certifi: the row says MPL-2.0 and "ships unmodified as source", and the gate needs both. Side note on the gate,
  not on this commit: pkg_stage's check passes on the word "unmodified" anywhere in the row, so the use column
  alone would satisfy it.

The licence gate bites in a non-Debug stage. With idna's row removed, `pkg_stage stage` exits 3 ("idna 3.20: no
log/assets.md row"). With the real file, it exits 0 with no warnings.

**certifi MPL-2.0.txt.** 16,726 B, sha256 3f3d9e00...9d04, ASCII, LF line endings, equal to its source record.
One GET through terms_guard.fetch of https://www.mozilla.org/media/MPL/2.0/index.txt during this review returned 200 and
the same bytes.

**Release generic iOS build, reproduced.** Command: `tools/xc.sh -project PyWidget.xcodeproj -scheme PyWidget -configuration Release

## Part 2: T-0411

**The package rule.** `pkg_ships` (tier staged by the phase, plus file, sha256 and bytes) is the same test as
pkg_stage's staging loop (`tier in tiers`, then skip unless file/sha256/bytes). `staged_tiers` reads the phase from
project.yml with comments stripped, and reads the script's `PKG_TIERS:-pure` default. If it cannot read the default,
it falls back to both tiers, so it never misses a notice. My 3 mutants each fail one case: pin check dropped, phase
check dropped, tiers ignored. The author's old-status-rule mutant is separate.

**The 14 components.** All 12 wheel-derived files in pywidget/licenses/upstream match the files in my Release app's
app_packages byte for byte, and each notices/ copy carries the same sha256. The parso entry is MIT AND PSF-2.0,
and typeshed is Apache-2.0 AND MIT; both are correct. Acknowledgements.txt carries the full MPL-2.0 text once,
the PSF licence, Kim Davies' BSD notice, Jukka Lehtosalo's MIT notice and the requests NOTICE.

**requests' NOTICE: is it the right notice to ship? Yes.** The wheel carries only LICENSE. The NOTICE at the root of
tag v2.32.5, the tag the 2.32.5 release was cut from, is "Requests / Copyright 2019 Kenneth Reitz" (38 B). One GET
of https://raw.githubusercontent.com/psf/requests/v2.32.5/NOTICE through terms_guard.fetch returned the same bytes.
Apache-2.0 4(d) asks for the NOTICE "as part of its distribution". Taking it from the same tag is the safe reading,
and it costs one attribution line. One wording slip: NOTICE.source.json "why" says "GitHub contents API", but the
URL is raw.githubusercontent.com, not api.github.com.

**Generated outputs vs the built Release app.** `tests/acknowledgements_test.py`: PASS 49, FAIL 0 on 3.9 and
3.13. `acknowledgements.py build` rewrote Acknowledgements.json, Acknowledgements.txt and audit.json, and git shows
no diff, so the committed outputs are exactly what the tool writes. (I ran `build --help` expecting usage text, and
it ran the build itself. That is harmless here, because there was no diff.) `check --app` on my Release app reports
only the 3 known gaps (mpdecimal, hacl, mimalloc).

But **the built Release app contains no Acknowledgements.json or .txt.** There is no resource in project.yml and no
copy anywhere in the bundle. The full MPL-2.0 text is also not in the app; only certifi's 989 B short notice is,
in app_packages. So "match the built Release app" holds for the notices in app_packages, not for the screen files.
`check --app` does not notice they are missing. And the T-0411 done-note's "The app's Acknowledgements screen now
lists the eight Python packages" is ahead of the facts: the generated screen text lists them, but no screen ships
until T-0042.
