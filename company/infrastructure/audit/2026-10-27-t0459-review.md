## The questions in the brief

**Every kind as drawn.**
- Alert (destructive with Cancel), the number prompt (decimal pad), choose (title, message, 2 to 6 options, Cancel) and pick multiple (search, ticks, Cancel/Done) can all be presented from the wire as drawn.
- The text prompt's "Save" label cannot be requested (F5).
- The HUD with progress cannot be presented (F4).
- The form's text, number, toggle, choice and date fields are all on the wire. The drawing's section headers ("BILL", "PEOPLE"), the stepper for People, the segmented Tip control and the footer line are not. Swift will choose the presentation in T-0447: a choice of up to 4 short options is shown segmented, otherwise a menu; a number is a text field; one section, with the message as its header. Maren passes this at screenshot time. Info, no line.

**Wire against s4.** The fixture's `{"module","method","args","timeout"}` maps onto `call(module, method, payload, timeout)`, and the payload is compared by JSON value. The `{"ok"}`/`{"error"}` replies match s4. `error.context` is read by `device.error_for` (v5.1), so a Swift refusal produces `.context == "widget"`.

**Can XCTest use the 50 cases as they are?** Yes, if the Swift suite:
1. substitutes "@day" with local midnight;
2. skips `swift: false`;
3. treats "stop" and "timeout" as slot events, not replies;
4. maps each reply to a tap by index (there is no UI-action column).

One Simulator case should also confirm that Python's local zone matches `TimeZone.current` for date fields (T-0447).

**Cancel and refusal.**
- Cancel returns None for every waiting kind, and an empty answer is never None. Checked in the fixture and by mutant m2.
- `hud` never answers null, and a null reply raises RuntimeError.
- Widget, Shortcut and preview runs refuse before anything is sent (m14) and after the argument checks.
- Swift can be left with a prompt nobody waits for in two ways, F2 and F3. I found no path where Python waits on Swift with no way out inside a run: Stop posts to the run's slots.
- Info for T-0447: the unconditional Shortcut refusal rules out the L9 s2.3 foreground hand-off that the T-0447 line mentions. If that hand-off is wanted, the Python refusal has to change too.

**Runner change.** It is one line, guarded by the existing `CONTEXTS` check, and it is set after `_reset()`. Correct for in-run use; the gap is that it is never cleared (F2).

**"App" in user-facing strings.** None found. The refusal says "in a widget run / a Shortcut run / a gallery preview". "app" appears only as the internal context value and in comments.
