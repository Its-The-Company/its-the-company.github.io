not landed, the same 195 and the same causes as `tools/land_why.py` over the window). Rerun with no Claude:

## Findings (n beside each)

1. Work waits; checks are short. Of 499.6 h summed over all attempts' steps, 473.3 h (95%) is waiting and 26.3 h is
   running. The wait before an attempt starts dominates: median 82.6 min from the branch's last commit (n=113) and
   78.0 min from the previous outcome on a retry (n=72), against a host check median of 6.6 min (n=37) and a rebase of
   1 s (n=69). One caveat: "last branch commit -> starts to land" can include time the lane's session was still open.
2. Little's law says the queue, not the checks, sets time to merge. Mean work in progress 74.0 tasks against 1.77
   tasks landed by a land per hour: 41.9 h expected time to merge (64.3 and 2.3 per hour, 28.0 h, counting any route
   to main). Measured on the tasks that did land, median 0.8 h (n=60), which only says the ones that land, land fast;
   144 tasks seen in the window had not landed by a land at its end (126 by any route).
3. The cumulative-flow chart shows the gap opening all window: arrivals and starts track each other (204 and 204),
   landings fall behind (60). Starting is not the bottleneck; finishing an attempt green is.
4. A land is not on GitHub when it lands. Land to push of main: median 13.6 min, p90 63.1 min (n=50, all 50 matched to
   a push by first-parent position). The land's "push" step (1 s, n=22) moves the local main only.
5. 145 of 195 outcomes did not land. Causes (land_why.py's split): 41 red with the same failures on other branches,
   29 worktree missing, 26 conflict in code, 14 main moved during checks, 12 red on its own failures, 11 conflict on
   bookkeeping files only. Reds shared across lanes point at three tests: test_stdlib_manifest's two import tests
   (33 red outputs, 14 lanes each) and test_lane_gate_flag's scan test (21, 12 lanes).
6. Flakes at the same commit: MacBook xc-test, 3 of 5 commits run twice gave a pass and a fail (n=5, small). Session
   suite runs at one head (ops/runs/test-runs.jsonl): site_test.sh 2 of 4 commits mixed, governor_test.sh 2 of 2,
   9 more suites 1 of 1. Those runs can come from a worktree with changes not committed, so they bound flakiness from
   above.
7. Conflicts (37 attempts): research/inbound/apple/index.tsv is the most conflicted file (10), then tests/site_test.sh
   and tools/personal_land.sh (5 each). Replayed with git merge-tree, 86 conflict blocks in the logged files, median 9
   lines. The main-side commits that touched those files were task commits (59 of 63 file and attempt pairs), not the
   machine records: once land_why's bookkeeping split is taken off, conflicts come from parallel work on the same
   few shared files.

## What could not be reconstructed

- Per-step times (rebase, host, xc, push) before 2026-11-06 03:55, when ops/runs/land_steps.jsonl began: 166 of 228
  attempts have only their start and outcome times ("checks, steps not logged" in the map).
- Each suite's start and end inside the host step: run_host prints a duration per suite, not a start, and only a red
  keeps its output; a passing land's output (ops/runs/personal-land-<id>.log) is overwritten by the next land.
- Exit codes of passing steps (only a red's code is written in its outcome line), and the commit a land's host check
  tested (never logged), so there is no "same commit" rerun for land host checks; per-test flake rates at one commit
  exist only for MacBook jobs and session suite runs.
- Arrival: 18 attempts follow a "ready at" line; the rest take the branch's last commit (113), the previous outcome
  (72), or nothing (23 with no arrival at all).
- Conflicts are replayed as a merge of the tip and main at the attempt's start (from the reflogs), not the land's
  commit-by-commit rebase: 18 of 37 replays name other files than the log, though 26 cover every logged file. Binary
  files (a .png) have no lines. Which main commit wrote each conflicting line (blame) is not done; sources are file level.
- Main's own green or red over the window: tools/main_green.py keeps only its last result.
- Runner results are read from origin/macbook-results as last fetched; a rerun after a fetch can add jobs.
- "On main by any route" counts a task out at the first first-parent commit on main whose subject opens with its id;
  a partial commit would count it early.
- GitHub's activity API returned 298 pushes of main back to 2026-11-04 06:28, which covers the window (142 in it).
