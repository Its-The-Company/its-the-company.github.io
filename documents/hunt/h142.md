## 2. Guided generation emits the typed query, not SQL

- Guided generation uses **constrained sampling**, which "gives strong guarantees that the response is in a format you expect" ([Generating Swift data structures with guided generation](https://developer.apple.com/documentation/foundationmodels/generating-swift-data-structures-with-guided-generation)). That guarantees a well-formed `Query`. It does not guarantee the right one, and the 60-question harness has to measure that.
- `@Generable` works on structs and enums. `@Guide` can set `.range(...)` on numbers, `.count(n)` and `maximumCount(_:)` on arrays ([Generable](https://developer.apple.com/documentation/foundationmodels/generable), [Guide(description:)](https://developer.apple.com/documentation/foundationmodels/guide\(description:\))). That gives `limit` 1...20 and a <span title="A measured fact that holds a grade below a letter, however good the rest is.">cap</span> of 3 filters.
- "The model generates Generable properties in the order they're declared" (same guided-generation page). So declare `source` first, then `measure`, then `group`, then `filters`, so each choice can condition on the one before.
- Field and value lists depend on the user's library and are only known at run time. Use [DynamicGenerationSchema](https://developer.apple.com/documentation/foundationmodels/dynamicgenerationschema) with `anyOf` (the guided-generation page's menu example) for the field names of the imported sources only.
- [Tool](https://developer.apple.com/documentation/foundationmodels/tool) / [tool calling](https://developer.apple.com/documentation/foundationmodels/expanding-generation-with-tool-calling) is the fallback for resolving a name ("Harbor Lights", "Sandworld") against the library. Tool schemas, inputs and outputs all count against the context ([TN3193](https://developer.apple.com/documentation/technotes/tn3193-managing-the-on-device-foundation-model-s-context-window)).

## 3. Context size against a 300,000-row library

- The window is **4,096 tokens per LanguageModelSession** and covers instructions, prompts, tool information, Generable schemas and every response ([TN3193](https://developer.apple.com/documentation/technotes/tn3193-managing-the-on-device-foundation-model-s-context-window); [exceededContextWindowSize](https://developer.apple.com/documentation/foundationmodels/languagemodelsession/generationerror/exceededcontextwindowsize\(_:\))). One token is about 3 to 4 characters in English (same pages). `contextSize` is back-deployed before iOS 26.4 ([contextSize](https://developer.apple.com/documentation/foundationmodels/systemlanguagemodel/contextsize)); `tokenCount(for:)` is iOS 26.4+ ([tokenCount(for:)](https://developer.apple.com/documentation/foundationmodels/systemlanguagemodel/tokencount\(for:\))).
- Arithmetic: a Spotify stream row in the fixture JSON is about 449 bytes (1,807,506 B / 4,028 rows), so roughly 110-150 tokens at Apple's ratio, and 300,000 rows are some 33-45 million tokens. That is about 10,000 times the window. **The library never enters the prompt.** The model sees the question, the schema, and at most a short list of the library's field names. Names are resolved by app code: an exact match, then a fuzzy match offered as "did you mean" on screen. A tool is used only if that fails.
- Plan rule: one new session per question (TN3193's "new session" advice), no chat history. The schema's own token count is **unmeasured** and gets measured with `tokenCount(for:)` in the probe.

## 4. The query language

```
Query    := source measure [group] filter{0,3} [range] [compare] [during] [share] [sort] [limit]
source   := spotify | podcast | letterboxd | netflix | storygraph | strava | any
measure  := count | minutes | hours | activedays | streak | first | last
          | distinct:FIELD | sum:FIELD | avg:FIELD | max:FIELD
group    := FIELD | year | month | weekday | hourofday | decade | source
filter   := FIELD op VALUE        op := eq | ne | contains | gte | lte
range    := from:DATE to:DATE     (inclusive; compare := a second range)
during   := source filter{0,3} unit:(day | week)   -- keeps rows whose date falls in the other source's matching periods
sort     := desc | asc | key      limit := 1..20      share := percent of grouped rows
FIELD    := per source (spotify: creator title album minutes hourofday skipped platform; podcast: title show minutes;
            letterboxd: title release_year rating rewatch tags; netflix: title show season;
            storygraph: title creator rating pages tags format; strava: title type minutes km)
```
A field the source lacks is a **refusal with a reason** ("netflix export has no 'minutes'"), never a guessed number. The reference evaluator is `H142-raw/h142_fixture.py` (Python, a test oracle, not app code). It fixes the expected answers before any model runs.

## 5. The 60-question test set

**Where the questions come from.** H141-raw <span title="What keeps an idea below the top: the cap that applies to it now.">holds</span> only `pull.py` and no data yet. The task named r/truespotify titles in H137-raw, but **H137-raw has none**: its asks are r/lastfm, r/trakt, r/TheStoryGraph and r/TVTime, and the Letterboxd and Strava pulls stopped on 422. So each question below is **my own sentence**, shaped by a dated title from those files (post id in "Drawn from") or by PITCH-11 section 1's examples. None of them is a user's typed sentence. When H141 lands, its titles replace the phrasing and the set is re-scored.

**The fixture.** It is code-generated with seed 142 and every name is invented. `gen` was run twice and the five files came out byte-identical. They are not committed (the Spotify file is 1.8 MB); regenerate them with `python3 -I H142-raw/h142_fixture.py gen OUT`. SHA-256 prefixes are in `H142-raw/fixture-sha256.txt`. Contents: Spotify extended JSON (4,028 song rows and 44 podcast rows, podcast rows with null track fields), Letterboxd `diary.csv` (283), Netflix per-profile `Title,Date` CSV (674), StoryGraph CSV (34 books with date ranges), Strava `activities.csv` (294). The data runs 2023-01-01 to 2025-12-31. The questions are in `H142-raw/questions.jsonl` and the answers in `answers.tsv` (`h142_fixture.py answer OUT questions.jsonl`).

**Template path** (phones without Apple Intelligence; section 1's `deviceNotEligible`). There are six fill-in forms, all over the same grammar: top-N by group, a total, a time series, two ranges compared, a streak, and all services by month. Each takes **at most one filter**, picked from a list. Measured on this set: **templates answer 50 of 60**. Six questions are refusals on both paths (Q18, 19, 27, 51, 57, 58), so templates answer 50 of the 54 answerable. The model adds exactly **4** (Q14, 32, 50, 56): the `during` joins, which are the cross-service difference itself. This bears straight on weakness 1. On my phrasing, the typed box buys four questions, and they are the four that carry the pitch. A template for `during` ("in the weeks I was ... [pick a book or show]") would close even those, so the model's real job here is phrasing, not reach. The test set is mine, so this share measures my questions, not users'.
