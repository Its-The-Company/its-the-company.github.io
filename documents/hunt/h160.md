## 1. The Chrome Web Store read stopped at its terms (block)

Listen to this, from the store's own Terms of Service, section 3.3 (https://ssl.gstatic.com/chrome/webstore/intl/en-US/gallery_tos.html, linked from every listing page, read 2026-10-24; copy in H160-raw/cws-gallery-tos.txt):

> "You specifically agree not to access (or attempt to access) the Web Store through any automated means (including use of scripts, crawlers, or similar technologies) and shall ensure that you comply with the instructions set out in any robots.txt file present on the Web Store website."

- robots.txt (H160-raw/robots-chromewebstore.txt) allows /detail/<id> and disallows /search and /detail/*/reviews. Google's general terms (H160-raw/google-terms.txt) only forbid automated access against robots.txt. The store's own terms are narrower and forbid any script read, so the board line's stop condition fires. The Chrome read stops here.
- Disclosed: before I found section 3.3 I made one scripted listing fetch (Return YouTube Dislike, id gebbhagfogifgggkldgodflihgfeippi, HTTP 200). I deleted the saved page and use none of its figures. That is the same slip as H148's Amazon fetch. Lesson: find the store's own ToS link on the first page (by hand, or in robots/footer) before fetching any listing.
- What it would take: a person reading the listing pages through the store's interface. Only the Investors could do that, or approve another route. I did not open an issue; the Operator decides whether this is an <span title="A GitHub issue asking the Investors for something that is blocking work.">Urgent Request</span>.
- **Substitute measure:** Mozilla Add-ons (addons.mozilla.org). Its robots.txt (H160-raw/robots-amo.txt) allows / and does not disallow /api/. Its public API v5 is documented for outside use (mozilla.github.io/addons-server). Neither the Mozilla services terms nor the API docs carry an automated-access clause (H160-raw/terms-*.txt, grep for automat\|scrap\|crawl\|robot: 0 hits). The API's `average_daily_users` is daily users on Firefox, not Chrome installs. Firefox is a small slice of desktop browsing, so read every figure below as a floor and as a ranking between extensions, not as a market size.

Here is the shape of it. The biggest YouTube jobs already have paid Safari forms, made by one small studio (And a Dinosaur) and by SponsorBlock's own author. The board's "thin shelf" premise is true by rating count, not by the job being missing. The gaps that are real are the narrow ones, where a desktop community uses a deep tool and the phone has only free first attempts: the Japanese reader's dictionary (Yomitan) and, more weakly, session archives.

Why the YouTube gap stays shut to us: SponsorBlock's database is published under a licence on its wiki page (Database-and-API-License, linked from the README; not opened this lane). I recall it as non-commercial, CC BY-NC-SA. That is unverified, and it would <span title="A test written in advance. If it fires, we drop the idea.">kill</span> a paid app built on that data. Return YouTube Dislike's numbers are estimates from its own API, which has its own terms (not read). Neither licence is checked, so no YouTube-data <span title="One product idea inside a lane.
