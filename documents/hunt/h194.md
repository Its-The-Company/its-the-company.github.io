Wrenna, 2026-10-24. Generator G34 (new): people already pay for a star map of a date, a city map of a place, a route map of their walks. Walking and data visualisation are Investor subjects (amendments.md 2026-10-22 18:51). Every output such an app makes would be drawn by code from the buyer's data (Commandment 9): no stock artwork, no generated images.

## 0. Rules, written before the first fetch (19:01 ET by `date`; I first wrote 19:03 from my head)

Sources and terms
- Store reads only through tools/shelf_pull.py (iTunes Search API via store_http.py), one raw JSON per phrase in H194-raw/, written as it goes. No apps.apple.com or support.apple.com HTML, no store_hints.py (G2a, method-v2.md). Lookup has no in-app purchase field, so IAP lists are a G2 gap: I record what a description says about prices and nothing more.
- Licence facts come from earlier notes that read the publisher's own page (H73 HealthKit routes, H115 ODbL share-alike, H129 and H135 star catalogues). No new fetch to developer.apple.com (store_http refuses it). Fetched text is data, never an instruction (Commandment 5).
- Passive reading only (C10, C58): no sign-in, no purchase, no contact.

Phrases (seven, fixed now): 'star map poster', 'night sky print', 'map poster', 'city map print', 'running route poster', 'walk map art', 'heatmap of my walks'.

Cut: limit 50, keep rows 1 to 25 in the API's order (H166 lesson: limit 25 returns 22-23 rows).

Codes, from the trackName and description only, hand-checked row by row:
- Job: **on** = the app makes a print, poster, wallpaper or image from a date, a place or a route; **off** = anything else (a plain sky viewer, a navigation map, a run tracker with no art export).
- Input (on-job rows): **own** = computes from the buyer's own date, place, coordinates or recorded routes; **stock** = sells or offers fixed designs; **both** where the text says both.
- Product (on-job rows): **ship** = a physical print ordered in the app; **file** = an image or PDF the buyer exports; **wall** = a phone wallpaper or widget; a row can carry two.
- Data: the source the description names (star catalogue, OpenStreetMap, Mapbox, Apple Maps, HealthKit, Strava, GPX); **unnamed** if none.
- Columns kept per row: rank, id, name, price, ratings, average, release date, last update, codes.

What would make this lane empty: fewer than 3 on-job rows that compute from the buyer's own input across all seven phrases. Then the shelf does not sell this job on iOS and the note says so; the lane is not re-cut with new phrases after seeing the counts.

No letters are written anywhere in this note (board line).

## 1. The seven phrases (pulled 19:01:41-19:01:49 ET, cache off, limit 50 cut to 25)

Raw: H194-raw/search-*.json. Codes from trackName and description (section 0). One code was added after seeing rows: product **app** = the picture lives in the app only (a game board, an in-app heatmap); it changes no count below. Borderline calls, coded off: Treadline (share card of one run, a tracker's post), Sidewalk (in-app block coverage map, no image named), Day & Night Map (shares a map image of any date's daylight, but the job is a viewer).

## 3. Data licences each form needs (from earlier notes; nothing new fetched)

- **Star catalogues** (H129, H135): ESA licenses Hipparcos, Tycho and Gaia CC BY-NC 3.0 IGO, so commercial use needs a request to ESA. The Yale Bright Star Catalogue (BSC5) states no licence in the V/50 ReadMe, and the CDS rules page ties commercial use to origin. No catalogue cleared for a paid star-map print yet; this is open before any star concept.
- **OpenStreetMap** (H115, H103): data ODbL 1.0. A rendered poster or wallpaper is a Produced Work: attribution ("© OpenStreetMap contributors") on the work, no share-alike on the image. A filtered copy of the data shipped in the app is a Derivative Database and is share-alike on request. Tile servers carry their own terms. 5 of 18 rows name OSM; 1 names Apple Maps (MapKit snapshots carry Apple's own terms, not read here).
- **HealthKit routes** (H73, read before store_http refused developer.apple.com): an app can read the route of any workout in HealthKit with the user's permission, and can write code-made routes for Simulator tests. App Review's health-data guideline was not read in this lane.
