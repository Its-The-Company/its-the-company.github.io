## 0. Question and sources

#53 bars the iTunes Search API, so no new <span title="One numbered piece of research into one area of ideas. Each lane has its own file.">lane</span> can read a Crowding cell or a <span title="The rule that decides whether an idea gets two blind graders now, waits (park), or stops.">T1</span> <span title="The App Store results a buyer sees for a search phrase. The top 10 is the first ten, dated the day we read them.">top 10</span> from the store. The question: if a lane instead ran two plain web searches for a phrase and took every apps.apple.com id the results carry, how much of the store's own top 10 would it see? The truth is the top 10 on file (read through Search before the 19:51 ET ruling); the census is WebSearch.

Sources, all read within terms:
- Truth: top-10 ids already on file in lane raw folders (the frame, section 1). No Search call was made.
- Bare Lookup `https://itunes.apple.com/lookup?country=us&id=...` through tools/store_http.py (permitted path, robots-itunes-ruling.md), for the 100 truth ids and the 67 census ids: raw JSON in H204-raw/lookup/ (`truth_<phrase>.json`, `census_<phrase>.json`); each file's `source` field <span title="What keeps an idea below the top: the cap that applies to it now.">holds</span> the URL. Many answers came from store_http's 24 h cache (67 ids in 4 s), so counts can be up to a day old.
- WebSearch (the Claude Code tool, standard mode), 20 queries, result text saved verbatim in H204-raw/search/<phrase>.txt. The tool's text ends each answer with a "REMINDER: You MUST include the sources..." line: tool boilerplate, logged here as outside text and not followed as an instruction.
- No apps.apple.com page was fetched (<span title="The starting recipe a lane uses to look for ideas. G2, for example, starts from public datasets.">G2a</span>).

## 1. Frame (H204-raw/bin/frame.py, H204-raw/frame.tsv; commit 68cf408f)

A block counts when a lane's raw folder holds a phrase's Search top 10 as ten ids, read before 2026-10-24 19:51 ET (file mtime). Two forms were parsed: the appsearch text form (`== <phrase>` header, rows `<id> | name | price | n ratings ...`) and the JSON form (`url` on itunes.apple.com/search, country us, `rows[]`/`results[]` with trackId). A block with more than ten rows (limit 25 or 50 pulls) gives its first ten, which is the Search order. Blocks with fewer than ten rows, non-US pulls, description files (`== <id> <name>`) and lane_gate summaries are out.

## 2. Method, in the order it was run

1. 22:02: the ten truth files' ids were bare-Looked-up (H204-raw/bin/lookup.py) into H204-raw/truth/<phrase>.txt with output unread.
2. 22:02: 20 WebSearch queries, worded exactly `<phrase> app iPhone` and `<phrase> iOS app App Store`; text saved (commit 98b1eec0).
3. 22:07: H204-raw/bin/census.py (tools/id_census.py had not landed, so a lane script) took every apps.apple.com id by regex `apps.apple.com/.../id<digits>` from the saved text: 67 ids over 10 phrases (census.tsv). Ids on mwm.ai, similarweb, appshunter and appgoblin pages (32) were listed in census_other_hosts.tsv and not used, as the line says apps.apple.com only.
4. 22:07: the 67 census ids were bare-Looked-up; 6 had no US result (an id in another storefront or gone). Each was coded on-job Y or N from its Lookup description (codes_census.tsv, commit 0e6fbdb6) before any truth file was read.
5. 22:08: the truth files were read, ranked by userRatingCount, and coded by the same rule (codes_truth.tsv). H204-raw/bin/counts.py computed the counts from the two code files (counts.tsv, commit 4d5995bf).

On-job rule, written per phrase before coding and applied to both sides: ebook converter = converts ebook formats; etymology = gives word origins; german grammar = teaches or references German grammar (conjugation, articles count); grammar analyzer = parses a sentence into structure (a checker/corrector is N); learn scottish gaelic = teaches Gaelic; markdown notes = notes kept in Markdown, named in the description read (Drafts and Simplenote are N by that rule although both support Markdown; it is what the 280-char excerpt said); master key system = locksmith master keying (smart locks, password vaults, access control N); subtitles = makes or shows subtitles; sunset hike = sunset time for being outside (photo-alignment tools N); weather averages = long-period climate statistics (forecasts N).

Census (67 ids): 46 Y, 15 N, 6 no US result. Truth (100 ids): 62 Y, 38 N. Per-id codes with a reason each: H204-raw/codes_census.tsv, H204-raw/codes_truth.tsv.

Count 1: the census holds the file's largest on-job app for 2 of 10 phrases.
Count 2: of the 38 slots in the files' five largest on-job apps (five where five exist, else all), the census holds 9, 23.7%.

Here is the shape of it. The web search finds the small, literally-named apps (every Scottish Gaelic course with "Scottish" in its name; "Ebook Converter" by name) and misses the apps that own a shelf without carrying the phrase in their name: Bear and Obsidian for markdown notes, Captions and VEED for subtitles, Sunrise Sunset Times for sunset hike, German Verb Conjugator and Der Die Das for German grammar. The store ranks by what people install; the web ranks by what a page title says. So a web census under-reads crowding exactly where crowding is worst: it would have called markdown notes, subtitles and sunset hike near-empty shelves (0, 1 and 0 of the file's ten), and each is full. It over-reads nothing: where the web found many ids (german grammar, 11) the shelf had many too.

Also seen: 32 of the 99 ids in the result text sat on third-party store mirrors (mwm.ai 15, similarweb 11, appshunter 3, appgoblin 3; counted from census_other_hosts.tsv), not apps.apple.com. Master It, the one on-job app for master key system, appeared only there (appgoblin and mwm.ai), so the apps.apple.com-only rule cost one hit; with mirrors allowed the pooled share would be 10/38 and the largest-held count 3/10. Six census ids had no US Lookup result (regional storefront links, l=ar/vi; one Mac-only listing); they are coded NR and could not be on-job either way.

Limits: n = 10 phrases, one search engine, one evening; results text is an LLM-written summary over a result list, so the id set depends on which links the tool chose to show (about 10 per query). Lookup counts partly cached (up to 24 h). The on-job code is mine, one coder, with the rule written before coding; Drafts/Simplenote/Notion show the rule's cost (a description excerpt that does not say "Markdown" codes N).

Turns: about 11 of 10 at the point the counts were committed; the whole lane about 13. Over, and said so.

## 5. Against the pre-registered rules (refill-24.md section 4, read 22:11 ET after commit 4d5995bf)

F1 = 2 of 10; R5 = 9/38 = 23.7%. That is **C204-3 (record only)**: F1 of 4 or fewer. A web-search census lists rivals in a lane file and fires nothing; Crowding stays a <span title="A figure we could not read because the source&#x27;s terms or robots file do not let our software read it. It never lowers a grade.">G2 gap</span> (robots) until the Investors answer #53. Neither threshold of C204-1 (F1 8, R5 60%) or C204-2 (F1 5 to 7) is near. The applier is Odalys (G9); I do not apply.

Two departures from the rule's letter, disclosed: (a) the frame rule says "a table or JSON of ten ids"; 9 of the 10 drawn files held more than ten rows (limit 25 or 50 pulls), and I took the first ten in Search order as the top 10. (b) The rule reads ids from "URLs and snippets"; the tool's prose named apps without ids, so every id came from the Links list, which is the URL part. Neither would move the tier: the misses are whole shelves, not row ten.

Why the method fails, in one line: the web indexes names, the store ranks installs; the apps that fill a shelf rarely carry the phrase in their name.
