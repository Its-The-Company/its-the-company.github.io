Reviewer: Idris (T-4897, Commandment 13). Author: Pernille. Reviewed: 70d106726b as a whole (Swift
`SettingsKinds.isUpcoming` and its three `PremadeSettingsTests` travel cases, `countdown.py` `_local` and its
readers, the `AllDay` cases in `test_premade_settings.py`, spec s2.3.2), plus the Page code the commit did not touch
that reads the same stamp: `SettingsPage.swift` `detail` (line 508), the date editor (lines 803-811) and
`SettingsKinds.sorted`. The commit is not on main yet (it is on `parked/a/20261118-101248-50907`); `SettingsPage.swift`
is the same at 70d106726b and main 040e64c499, so its line numbers hold at both. Date: 2026-11-18.

I wrote the rule this commit replaces (86cf6f47bd, `startOfDay` plus a calendar day), so finding L1 below is in my
own code, carried over unchanged.

## Tests run

All on a `git archive` export of 70d106726b in a scratch folder, nothing run in the shared worktree.

- `python3.13 -m unittest test_premade_settings` (in `pywidget/tests/widgets`): 24 tests, OK. `AllDay` alone is
  14 tests, OK, the four travel cases among them. (The commit message's "Python AllDay: 24 OK" is the whole file.)
- A boundary sweep, Swift against Python. A standalone build of the commit's own `SettingsKinds.date`, `stamp`,
  `parseStamp` and `isUpcoming` (copied byte for byte, with a two-case stand-in for `SettingsValue`) wrote an all-day
  stamp for every day of 2026 and 2027, picked at 9:00 AM in each of 16 zones, then found by bisection, for a phone in
  each of the same 16 zones, the instant `isUpcoming` turns false. Python read the same stamps through
  `countdown._end`. Zones: New York, Bangkok, Tokyo, Sao Paulo, Honolulu, Kiritimati (+14), Pago Pago (-11),
  Auckland, Chatham (+1:45 PM), Apia, Lord Howe (30-minute DST), Kathmandu, Santiago, Havana, Beirut, St John's.
  - 186,880 cases. Every stamp the Swift writer made begins with the date picked in the picking zone, the date line
    included (Kiritimati to Pago Pago is 25 hours).
  - Python's end is always 12:00 AM, in the phone's zone, of the day after the written date: 0 exceptions.
  - Swift agrees with Python in 186,784 cases. The 96 that differ are all one case (L1): an event dated on a day
    whose own midnight the clocks skip (Havana 2026-03-08 and 2027-03-14, Beirut 2026-03-29 and 2027-03-28,
    Santiago 2026-09-06 and 2027-09-05), from each of the 16 picking zones.
- Malformed stamps, both halves: `"2026-12-18T24:00:00"`, `"2026-02-30T12:00:00Z"`, `"...+25:00"` and a leading space
  are refused by both (`isUpcoming` nil, `read` drops the row). A date alone and `"2026-12-18T12"` read as Dec 18 on
  both. `"...+09"`, `"20261218T120000+0900"` and `"2026-W51-5"` are read by Python 3.13 (Dec 18) and refused by Swift
  (nil). That gap is older than this commit (`parseStamp`'s doc says it reads what `parse_time` reads), only a file
  the app did not write can carry those forms, and it keeps the new code safe: every stamp `parseStamp` accepts
  begins with `YYYY-MM-DD`, so the commit's ten-byte read cannot see anything else.
- Not run: the Swift suites in Xcode. The commit cites `ops/runs/xcodebuild-20261118-090439.log` (2093 executed,
  0 failures); that log is not in this worktree or in the commit, so I have not seen it.

## The Swift half

`isUpcoming` reads the written date from the stamp's first ten bytes only after `parseStamp` has accepted the whole
stamp, builds 12:00 PM of that date in `calendar`, takes `startOfDay`, and adds a calendar day. Building noon first is
right: it never lands in a skipped hour, so `startOfDay` gives the day's real start even where midnight does not
exist. The `ymd.count == 3` guard cannot fail after `parseStamp`, and failing it returns nil, the same as an
unreadable stamp. A timed row still compares its instant. Correct for every case in the sweep apart from L1.

## The tests, Swift against Python

The three Swift cases and the Python cases describe the same events: Dec 18 2026, picked in New York (-5:00 AM) and
read in Bangkok, picked in Tokyo (+9:00 AM) and read in Sao Paulo and Honolulu. The Swift helper goes through the real
writer (`SettingsKinds.date` at 9:00 AM in the picking zone) and checks the stamp begins `2026-12-18T12:00:00`, then
checks Dec 17 9:00 AM, Dec 18 12:30 AM and 11:59 PM upcoming, Dec 19 12:00 AM not, all in the phone's zone. Python checks the
same boundary plus what only the widget has: "Today", "Tomorrow", the day count, the bar's goal, the shown date and
the VoiceOver line. Python also has 14 h east (New York to Tokyo); Swift does not, but its 12 h east case already
fails on the old rule. Under the old rule the east and 19 h west cases fail and 12 h west passes (its instant is
12:00 AM of the right day), which the commit message says plainly. Both halves are in December, so none of the three
travels across a clock change; the 25-hour-day cases cover that, and they have no Swift twin for a skipped midnight
(L1).

## Findings

### M1 (Medium): the Page still shows an all-day row's day from its instant

`SettingsPage.swift:508-509` (`detail`) formats the stamp's instant in the phone's zone. So does the date editor
(`SettingsPage.swift:803`, the `DatePicker` selection), and `SettingsKinds.sorted` orders rows by instant. After
this commit the widget and the Past section read the written date, but these three do not:

- Picked Dec 18 in Tokyo, phone in Honolulu: the widget says "Dec 18"; the Page's row says "Dec 17, 2026", and so
  does the editor. Picked Dec 18 in New York, phone in Bangkok: the row says "Dec 19, 2026".
- In that editor, turning on "Time" stamps the shown instant: the event becomes Dec 17 at 5:00 PM, a timed event a
  day early. The person sees it, but nothing they chose asked for it.
- Order: on a Honolulu phone, an all-day Dec 18 event picked in Tokyo sorts above a timed Dec 18 8:00 AM event on the
  Page (its instant is Dec 17 5:00 PM there) and below it on the widget (`_upcoming` sorts by `_local`, 12:00 PM of the
  written date).

So yes, line ~509 needs the same rule, and two more places with it. One helper (the written date at 12:00 PM in
`calendar`, the same few lines `isUpcoming` now has) used by `isUpcoming`, `detail`, the editor's selection and the
sort key would keep the four together. Board line T-4904.

### L1 (Low): on a day whose midnight is skipped, the Page keeps the event an hour too long

When the clocks spring forward at midnight (Havana, Beirut, Santiago in the sweep; Cairo does too), the
event's day begins at 1:00 AM. `startOfDay` gives 1:00 AM and `date(byAdding: .day, value: 1)` keeps the time of day, so
`isUpcoming` ends the event at 1:00 AM the next day instead of 12:00 AM. Example: an all-day event on Mar 8 2026, phone in
Havana: Swift ends it at Mar 9 1:00 -4:00 AM, Python at Mar 9 12:00 -4:00 AM. For that hour the Page lists the event as
upcoming while the widget has dropped it, and the save check accepts it. Not new: 86cf6f47bd (mine) had the same two
lines, and this commit carried them over. Fix: take the end as `startOfDay` of 12:00 PM on the written date plus one
day, so both ends are built the same way; add a Swift case (Havana, Mar 8 2026) beside the 25-hour one. Board line
T-4905.

### Notes, no fix asked

- The commit message counts "Python AllDay: 24 OK"; 24 is the whole file, `AllDay` is 14.
- `parseStamp` refuses three forms Python 3.13's `fromisoformat` reads (above). Older than this commit and only
  reachable from a hand-written file; worth fixing in the doc comment the next time `parseStamp` is touched.

## Verdict

**PASS with findings.** The new rule is right on both halves: in 186,880 swept cases, the date line and a 25-hour
spread included, the widget always ends an all-day event at the phone's midnight after its written date, and the
Page's `isUpcoming` agrees everywhere except on a day whose own midnight is skipped (L1, an hour late, older than this
commit). The three Swift travel cases match the Python ones and two of them fail on the old rule. Malformed stamps
are refused the same way as before. Open: the Page's row date, date editor and order still read the instant, so
after travel the Page and the widget show different days for the same event (M1). Neither finding blocks landing
70d106726b; M1 should land before the App Store release with it. Lines: T-4904 (M1), T-4905 (L1).
