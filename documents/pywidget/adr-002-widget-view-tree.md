## Context

C4 needs Python to describe widget UI that WidgetKit renders with SwiftUI. WidgetKit renders only an archived SwiftUI view hierarchy produced by the widget extension; Python cannot create SwiftUI views directly, and (L3, open) may not run in the extension at all. C6 (Builder blocks), C8 (web IDE preview) and C13 (design system templates) all need the same description. Full spec: [`../research/L4-view-dsl.md`](l4-view-dsl.html); schema: `../design/viewtree.schema.json`.

## Options considered

1. **Python builds a JSON view tree; a generic SwiftUI interpreter in the extension renders it.** One format serves iOS, web and the Builder. Python never has to be present at render time.
2. **Python renders bitmaps (Pillow) and the widget shows an image.** Simplest renderer. Loses Dynamic Type, vibrant and accented modes, self-updating text, accessibility and light/dark (spec section 10). Kept as a fallback node, not the design.
3. **Python emits SwiftUI source compiled at build time.** Impossible on device (no compiler) and against Guideline 2.5.2 for marketplace code.
4. **A fixed set of template widgets parameterized by Python values.** Easy, inexpressive; fails the "fully customizable" founder decision.
5. **Expose SwiftUI through a live bridge (Python objects wrapping views, rendered in-process).** Requires Python inside the extension on every render and ties the format to the Python process; the web IDE would need a second description anyway.

## Decision

Option 1. Specifically:

- Document shape `{schema, version, generator, widget, timeline, actions, state}`; node shape `{t, p, m, c}` with ordered modifiers; all dates ISO 8601 UTC; sorted keys so serializations are byte-stable.
- Node catalog v1: stacks, Spacer, Divider, Group, Text (string, date styles, timer interval, locale-formatted number), Image (SF Symbol, bundled asset, bitmap), Gauge, ProgressView (value or timer interval), five shapes, Path with seven commands in unit or point space, Button and Toggle bound to one generic App Intent by action name, Link, AccessoryBackground, and one conditional `When` keyed on render-time environment (family, renderingMode, showsContainerBackground, isLuminanceReduced, colorScheme, dynamicTypeSize, stale).
- Paint: raw color with optional dark variant, semantic colors, linear/radial/angular gradients, materials. Fonts: text styles (Dynamic Type), system size/weight/design, custom (bundled only).
- Timeline: entries with per-family `views` and a `view` fallback, relevance, `TimelineReloadPolicy` mirror, `sampled_at`/`stale_after`.
- Interactivity: `actions` map, Python handlers `(state, args) -> state` with a default 2 s timeout, state in the App Group, optimistic UI through `invalidatableContent`.
- Versioning: integer major; additive within a major; renderer ignores unknown modifiers/props and swaps unknown nodes for `alt`; the extension ships a renderer per major ever released.
- Builder: blocks compile to the same `pywidget_ui` calls (L17 option c on a); round-trip only for Builder-written files that still parse to the subset.

## Consequences

- Good: one contract, three renderers (SwiftUI, HTML/SVG, Builder preview is the SwiftUI one); old widgets keep rendering after app updates; a widget can be previewed on the web without a phone; the extension needs no Python.
- Good: the format is testable without Xcode (`pywidget/tests/test_viewtree.py` runs on the system Python 3.9).
- Cost: every SwiftUI feature we want must be added to the catalog, the schema, two renderers and the Builder; novel visuals wait for a release. Mitigation: `Path` covers charts and dials now; the bitmap fallback covers the rest with documented losses.
- Cost: a `When` conditional in the tree is a small interpreter inside a renderer. Kept to one node and seven env keys on purpose.
- Risk: the catalog grows into "SwiftUI in JSON". Rule: a node enters v1 only when one of the 12 premades needs it (was "15 gallery designs"; chair ruling 1).
- Depends on L3: if Python does run in the extension, `When` and `views` become optional optimizations; the format is unchanged.

## Evidence

- iOS 27.1 SDK interfaces (families W:938–974; rendering modes W:1040–1052; `widgetAccentedRenderingMode` W:176–189, iOS 18; `WidgetTexture.glass` visionOS-only W:12–24; `TimelineReloadPolicy` W:1659–1662; `containerBackground` S:15907; `invalidatableContent` S:2785; `Button(intent:label:)` AI:186; `Toggle(isOn:intent:label:)` AI:237; Gauge styles S:13066, 16258, 19952, 24449, 32371).
- Reference serializer and 20 unit tests: `pywidget/python/pywidget_ui/`, `pywidget/tests/test_viewtree.py`.
- Corrections to the brief recorded in [`../research/CORRECTIONS.md`](corrections.html) (tinted/clear are not API rendering modes; iOS 26 glass has no iOS widget API; `systemExtraLargePortrait` exists on iOS 27).

## Design read, 2026-10-26 19:54 ET (Maren, T-0217)

**Agree with option 1; accept with the four additive changes below, all inside major 1.** Only a tree keeps what the approved look depends on (creative/approved.md item 2: A Paper light, B Studio dark): Dynamic Type, light and dark from one source, and the stripped modes (accented, vibrant, clear), where design-system-v0 s8.3 carries a widget on two text levels and a luminance <span title="Our grade scale, nine steps: D, D+, C-, C, C+, B-, B, B+, A. An idea&#x27;s ladder is the letter it reaches before any cap.">ladder</span>; option 2's bitmap loses all three. The 12 premade trees validate against schema v1 with 0 problems and use 15 of its 22 node types ([`../design/widgets/nodes-needed.md`](nodes-needed.html)), so the catalog is about the right size and the "a node enters only when a gallery design needs it" rule <span title="What keeps an idea below the top: the cap that applies to it now.">holds</span>. (1) **Semantic paints are a closed list of design-token roles.** The Paint bullet should say: semantic names are the keys of `Shared/TreePaint.swift` `assets` (`text.*`, `accent`, `accent.soft`, `status.*`, `line.*`, `bg.*`) plus the aliases `primary`, `secondary`, `tertiary`; the renderer resolves them per appearance, per Increase Contrast set, on the card (`onCard`) and in stripped modes (`roleAlpha`); and `widgetCard` (schema since 17ca21de, missing from this text) is the container background premades use. Today `Color.semantic` takes any string, and TreePaint's comment says validate refuses an unknown name; it does not. The L4 example ([`../research/L4-view-dsl.md`](l4-view-dsl.html) line 233) and `tests/test_viewtree.py` line 60 call `container_background(Color.semantic("background"))`; "background" is not a key, so TreePaint draws `TextPrimary`, a near-black card in light, and a user who copies the example gets it. Fix: the DSL and validate refuse an unknown name with the closest one (<span title="The starting recipe a lane uses to look for ideas. G2, for example, starts from public datasets.">G5</span> as both reviews agreed: "did you mean text.secondary?"; for "background": "use ui.WidgetCard()"), and the example uses `WidgetCard()`. (2) **Fonts name the display face.** "system size/weight/design" should list design `display` (New York in light, SF Pro Rounded in dark; schema since 17ca21de), so one tree follows both appearances. (3) **A2 enters v1:** `accessibility_element(children=)` and `accessibility_value`, asked for by both name reviews before the first premade ships and in neither the schema nor the DSL today; without them a gauge and its label are two VoiceOver stops and the gauge speaks no value (design-system s6). (4) **R2 enters v1:** a `timeZone` (IANA name) on date text, for World clocks, one of the Pro 7 ([`../design/states/state-spec.md`](state-spec.html) line 209); the fallback is one string per minute, 60 entries an hour, and a clock that lags a minute is a defect a buyer sees. R4 (`tint`) stays out of v1; accent on gauges is acceptable. One Consequences line to add: the update card, error card, badge, stale mark, too-large and taps-off states are drawn by the renderer from `state-spec.md`, never by the user's tree, so every widget shows them the same way; `When(stale)` may change content, but no tree can hide the corner slot.

## Chair line (Ines), 2026-10-26 20:01 ET (T-0218)

Form: author's proposal (Idris), then an independent design read (Maren, above), then the chair (C13, C30). Read: the Decision and Consequences above; Maren's read; ADR-007 s4, s5.2, s6, s7.4 and my 21:08 chair line there (3bac1693); bridge-contract.md v5 s7 (the `widget_tree` record, `tree_seq`, `MAX_WIDGET_TREE_BYTES`); L4-view-dsl.md s8 and s14.1 (my T-0020 rulings, a0fecb81); L5-interactivity.md s15 (my 00:15 chair note, row V1); `pywidget_ui/__init__.py` at HEAD (`Color.semantic`, `WidgetCard`, `MAX_INLINE_BITMAP_BYTES`, `MAX_ACTION_TIMEOUT`); `Shared/TreePaint.swift` line 57-62; `viewtree.schema.json` at HEAD (`widgetCard`, `fontDesign` `display`). I ran nothing.

**Ruling 1: accepted. Option 1, the versioned JSON view tree from a Python DSL, is the widget format for v1 and for the product's life (one major, additive within it).** Option 2 stays a fallback node, as written. The reason is Maren's: the approved look (creative/approved.md item 2) depends on Dynamic Type, light and dark from one source, and the stripped modes, and only a tree keeps all three. The 12 premade trees already validate against schema v1 using 15 of 22 node types ([`../design/widgets/nodes-needed.md`](nodes-needed.html)), which is the evidence the catalog is sized right. One correction to the Consequences rule as written: "one of the 15 gallery designs" reads "one of the 12 premades" (ADR-001 3.1; battery became storage, still 12).

**Ruling 2: the L3 dependency is closed by ADR-007, and it closes the other way from the "Depends on L3" line.** No Python runs in any extension (ADR-007 s4 item 1, 5.2). So `When` and per-family `views` are **required** parts of the format, not optional optimisations: the extension has nothing but the tree to branch on. Three facts from ADR-007 and the contract that this ADR now carries:
- The tree reaches Swift as the contract's `widget_tree` record (v3 and later; `finished.tree_seq` names the one record Swift takes), is validated against `viewtree.schema.json` in Swift, and is written atomically as `widgets/<id>/tree.json` only on `ok`. A document that fails validation is ADR-007's `schema_error`; the last good tree stays.
- The stale mark is the provider's, not the tree's: it inserts one synthetic entry at `T = sampled_at + stale_after` wherever T falls (ADR-007 7.4); an entry is stale **at or after** T (7.1 row 5). L4 s8 says `now - sampled_at > stale_after`; that `>` is corrected to `>=` (board note on T-0233). Absent `stale_after` means never stale, and the IDE's New-widget template sets 30 minutes (ADR-007 A1). `When("stale")` may change content; no tree can hide the renderer's corner slot (Maren's Consequences line, accepted below).
- Snapshot and placeholder render the last good tree, else the premade's bundled preview tree, else the renderer's placeholder; never a run (ADR-007 5.2). A premade therefore ships a preview tree in the bundle; that is a `pywidget_ui` document like any other.

**Ruling 3: Maren's four additive changes are accepted into major 1, and the "background" bug is fixed before any premade ships.**
1. **Semantic paints are a closed list**: the keys of `Shared/TreePaint.swift` `assets` plus `primary`, `secondary`, `tertiary`; `widgetCard` is the container background premades use (it was in the schema at 17ca21de and missing from the Paint bullet; the bullet now reads with this item). `Color.semantic` and `validate` refuse any other name with the closest one; for "background" the message is "use ui.WidgetCard()" (Pernille, T-0233, Python first); the L4 line-233 example and `tests/test_viewtree.py` line 60 change to `WidgetCard()` in the same commit. TreePaint's comment that validate refuses unknown names is false today and is corrected when T-0233 lands (Idris, T-0234). One renderer rule, because the renderer stays tolerant (L4 s14.1, "strict for writers, tolerant always"): a semantic name the renderer does not know draws `widgetCard` when it is the `containerBackground` paint and `text.primary` anywhere else, so a newer major's name never produces a near-black card on an older renderer (T-0234, one test).
2. **Fonts list the `display` design** (New York in light, SF Pro Rounded in dark; schema `fontDesign` enum at HEAD already carries it with that description). Text change only.
3. **A2 enters v1**: `accessibility_element(children=)` and `accessibility_value`, schema, DSL and renderer (T-0233 then T-0234). A gauge and its label are one VoiceOver stop with a spoken value, or the premade fails design-system s6.
4. **R2 enters v1**: `timeZone` (an IANA name) on date text, for World clocks (Pro 7; state-spec line 209). R4 `tint` stays out of v1; accent on gauges is acceptable.
Maren's Consequences line is accepted verbatim: the update card, error card, badge, stale mark, too-large and taps-off states are drawn by the renderer from `state-spec.md`, never by the user's tree, so every widget shows them the same way.

**Ruling 4: <span title="A measured fact that holds a grade below a letter, however good the rest is.">caps</span> are numbers, not shape, and live outside the schema.** ADR-007 s6 says C sets "the ADR-002 schema caps (node count, image bytes, entries per timeline)". Today two caps exist and both are provisional: the whole tree, `MAX_WIDGET_TREE_BYTES` = 512 KiB (contract s7, in `_pywidget_runtime.limits` and its Swift twin), and an inline bitmap, `MAX_INLINE_BITMAP_BYTES` = 64 KiB (the DSL). There is no node-count or entries-per-timeline cap. They are set when the renderer task measures the fixture tree's render cost (ADR-007 open item 2), in `validate` and `limits` with the Swift twin, never in `viewtree.schema.json`, so a changed number never invalidates a saved document (T-0245, Pernille, after T-0206's measurement). Until then the 512 KiB cap is the only size rule a user can hit, and its message is the contract's.

**Ruling 5: the Interactivity bullet is read with L5 s15.** In v1 a tree may carry `Button` and `Toggle`, the renderer draws them, and taps do nothing; the IDE prints one console line saying so (L5 s15 row V1), no v1 premade uses either, and the store page claims no interactivity. Handlers `(state, args) -> state` run in the **app** as action runs (contract v4.5's reserved `action`, 1.1), default 2 s and never more than `MAX_ACTION_TIMEOUT` 5 s; `state` rides in the document. On iOS 18-26 the intent runs in the extension and queues the tap (ADR-007 T5 correction, L5 s4); from iOS 27 it can be pinned to the app. None of this changes the format: `actions`, `state` and the two nodes are in major 1 as proposed.

**Ruling 6: the schema at HEAD is the accepted shape; the L4 s14.1 rows (T-0209, in flight) are additive and already ruled.** Idris's G1-G3, G6, G9, G10, G14-G16 (my T-0020 rulings, a0fecb81) and the names-review rows T-0231 carries land inside major 1 without a new chair line. The freeze is Day 13 (2026-11-03): after it, a format change is a 1.1 question and goes through this ADR with a dated line. The Builder bullet (L17 option c on a) stands.

What would make this fail: a premade that fails `schema_error` in review because the DSL and the schema disagree, which is why ruling 6 keeps one writer and a strict schema; and a render cost on device that makes the 512 KiB cap wrong, which ruling 4 answers by keeping caps out of the schema.

Board: T-0233 (Pernille, P2, note added), T-0234 (Idris, P2, note added), T-0245 (Pernille, P3, new). T-0048 and T-0206 were waiting on this acceptance and are runnable on their own clauses now.
