## Verdict: FIX FIRST

The shape is right: one action value, declared handlers only, signed run links, the in-widget run reusing the lane. Two things will not hold as written. A Button's own `args` have nowhere to travel (H1), and two interpreters can now commit the same widget's state at once, which L5's commit rule was built never to allow (H2). H1, H2 and the Mediums block 'accepted'. The Lows can be built into the steps.

The first thing that broke was the request: `widget_tree.REQUEST_KEYS` is `("id", "date", "state", "first_party")` and `parse_request` refuses any other key, so there is no action run in the runtime today, only `Widget.run_action`, the test helper. Everything in s7 "Called" is new code, and no build step in s13 says so (M7).

## High

**H1. One button name, many buttons: the drawn Button's `args` are lost, and `v` cannot match.**
s7 item 2 makes a Button's default `{"do": "run", "function": action, "args": args}` and says two Buttons with the same action name are one place. The ordinary pattern is one action with per-row args: five habit rows, each `ui.Button("check", "Done", args={"id": h})`. That is one place and five different default actions. The link `pywidget://a/<id>/b/check?v=..&sig=..` and the intent `WidgetButtonIntent(widgetID:, button:)` carry no instance and no args (s6: "No `args` ... in the link"), and the app "recomputes [`v`] from the action stored *now*". With nothing stored there is no single action to recompute from, so either every row runs one row's args or every tap fails as N4.
Fix: keep the *setting* per name, but make the *tap* per drawn instance. (1) The link and the intent carry `i`, the instance's index among that name's Buttons in the tree's order (`pywidget://a/<id>/b/<name>/<i>?v=..&sig=..`; `i` is inside the signed string). (2) `v` hashes the *effective* action: the stored one if any, else the tree's default for instance `i`, args included. (3) With nothing stored, the app (link) or extension (intent) reads that instance's args from the widget's `tree.json`, the file the widget drew, never from the URL. A tree rewritten since the draw gives a different `v`: N4, nothing runs. (4) A stored `run` for that name replaces the action for every instance, its `args` included; the picker says "applies to all 5 buttons named check". (5) The caps in s3 count drawn instances, not names.

**H2. Two interpreters can commit one widget's state at the same time.**
L5 s5.3's result commit (one commit, ops re-applied over the window, `conflict` only past the ring) rests on "one interpreter runs one handler at a time, so two handler commits never overlap". ADR-011 makes a second one: on iOS 18 to 26 a lane widget's button runs its handler in the extension (s4) while its tap's `run`, or any signed link, runs a handler in the app. A person who taps the button and then the widget background, both reading `{"glasses": 3}`, gets two commits of 4. That is ordinary use, and ADR-007 s13 (d), "ordinary concurrency loses nothing", must hold before the lane ships. s7 "Called" also cites `state.json` and premade-inputs s2.3.1's lock, but ADR-007 s8 lists `state.json` and "state.lock's state use" as names held for after 1.0, nothing in the runtime writes `state.json` today, and the 2026-10-27 chair line holds every extension `state.json` write until G-L5-1, the widened G-L5-5 <span title="A test written in advance. If it fires, we drop the idea.">kill</span> test and Odalys's review of the s5 delta have passed.
Fix: (1) Say which part of L5 s5 is 1.0: `state.json` (`pywidget.state/1`) with `(epoch, rev)` and one result commit; no ops, no `pending` queue, no `failed.jsonl` (L5 s5.6 stays 1.1). (2) One handler per widget at a time across both processes: the run takes `widgets/<id>/state.lock` (flock, already shared by both writers) from the snapshot to the commit, bounded by its own budget. A second run that cannot get the lock in its budget is refused, with a run-log row (trigger `widget_action`, outcome `busy`) and the badge, never silently dropped. The window is at most 2.0 s in the widget and `timeout` plus the <span title="Our grade scale, nine steps: D, D+, C-, C, C+, B-, B, B+, A. An idea&#x27;s ladder is the letter it reaches before any cap.">ladder</span> in the app. Renders read state under a short hold and fall back to the cached tree on their own deadline, as today. (3) Add a build step for the state store with those tests, plus the chair line's gates: G-L5-5 widened to two processes committing one widget, with the kill test. Odalys reviews the s5 delta before step 6 lands.

## Medium

**M1. The in-widget run's time does not fit the lane's.** s4 runs "the function under its `timeout` (at most 5.0 s ...) within the lane's own deadline". ADR-007 s5 gives the lane `budget_s` 2 s and deadline 4 s, and after `perform()` the extension must also render. A 3 s handler is past the budget every time, and past 4 s it is killed, demoted and retried as a link.
Fix: the in-widget run has one `budget_s` of 2.0 s for handler plus render. The renderer draws the intent only when the action's declared `timeout` plus the widget's measured T is at most 2.0 s; otherwise it draws the signed link. State this in s4 "Who may"; `timeout` keeps its 5.0 s ceiling for app runs.

**M2. A tap the extension refuses or loses is invisible.** Between the draw and the tap the widget can be demoted, or the margin can refuse. s4 says only that "the next render draws that button as the signed link", so the person's tap did nothing and nothing says so.
Fix: `perform()` re-reads `.lane-demoted.json` and runs the margin first. A refusal, a demoted widget or a kill marker writes a run-log row (trigger `widget_action`, outcome `oom_guard`, `demoted` or `killed`) and shows the badge. The redraw shows the link form, so the next tap opens pywidget. Not queued in 1.0; say so.

**M3. Open buttons put a web URL into the tree, which s5 says never happens, and the schema cannot carry them.** s5: "A stored web link never goes into the tree". s7 item 3's `Button(ui.Open.link(url), ..., name=)` is the script's default, so the URL is in `tree.json`. The schema's Button `p` has `action` required (`viewtree.schema.json`, the Button and Toggle branch).
Fix: an Open button is `{"t": "Button", "p": {"action": "<name>", "open": {"do": "link", "url": "..."}}}`. `action` stays required and *is* the name, so item 2 and item 3 read the same way. `open` takes s1's value minus `run`. `TreeRules` checks `open.url` with s5's https grammar, separate from `linkURL`. The renderer never puts it in a `Link`; it draws `pywidget://w/<id>/b/<name>`, and the app reads the default from `tree.json` and checks it again at the tap. Amend s5's sentence to "a web link is never a `Link` destination in the tree". This is a format change after the Day 13 freeze, so it needs ADR-002's dated line under Ruling 6, not only Ruling 5's (M6).

**M4. Name clashes in one widget.** The manifest's `buttons` map is keyed by name, and both a run Button's `action` and an Open button's `name=` land there. `Button("help", ...)` plus `Button(ui.Open.link(u), name="help")` is one key with two meanings. Also: "the same rule" as widget ids (item 1) leaves open whether names compare ignoring case. Ids do (`_widget_id_key`), and `actions` is a case-sensitive dict, so `Add` and `add` can both be declared and look identical in the picker. A second `@widget.action("add")` silently replaces the first (`self.actions[name] = ...`).
Fix (s7 item 1, edited in this landing): names are `[A-Za-z0-9_-][A-Za-z0-9_.-]{0,63}`, so no leading `.` (no `.` or `..` path part), the `pywidget.` prefix stays reserved, and names compare exactly. pywidget_ui refuses a second declaration of a name, or one equal ignoring case, with one error naming both lines. A tree that uses one name both as a run Button and as an Open button's `name` fails the lint.

**M5. Q1: another widget's action from a button. Refuse it in 1.0** (answered in s7, edited in this landing). The stored value `{"do": "run", "function": "add_glass"}` has no widget field, so if two widgets of a project both declare `add_glass` the reader cannot tell which one is meant. The in-widget run would also have to write another widget's state and tree, which ADR-007 s13 (a) forbids the lane, and lock two widgets (H2). Allowing it later is a new optional `widget` field and `formats.actions: 2`. Nothing in 1.0 has to change for that.

**M6. The dated lines this needs, beyond ADR-002 Ruling 5.** ADR-007 s4.1 T5 still says "Widget action intents (after 1.0; ADR-002 Ruling 5)". ADR-007 s8's writer list and held names change: `state.json` and the state use of `state.lock` (H2), `widgets/<id>/actions.json` (s10), the link key file (M8) and the extension's `state.json` write in 1.0. s8 itself says "Any new file needs a dated line here". ADR-002 Ruling 6 needs a line for item 1's name pattern in the schema's `actions` keys and Button `action`, and for M3's `open`. L5 s4.3 ("Why not run the handler in the extension") and the 10-27 chair line are superseded in part; a line in L5 points to ADR-011.

**M7. The runtime half of "Called" has no build step.** Step 5 lists s7 items 1 to 5, all in `pywidget_ui`. The run itself is new code in four places, each with tests. (a) `widget_tree.REQUEST_KEYS` gains `action`, checked before user code runs: name rule, `args` an object of at most 1 KiB canonical (L2), `tap_id`. (b) One run does the handler, then the render with the returned state, so a handler that raises writes nothing (s7: "leaves state and tree as they were"). (c) Swift's `RunRequest` sends it, with a contract version line (v4.5 reserved the field; 1.0 implements it). (d) The lane runs the same path in the extension, through the same `_reset`, so a thread a handler leaves is counted as a render's is.
Fix: widen step 5 to "Python contract and action run for widget buttons", Pernille, with (a) to (d). Idris reviews.

**M8. The signing key has two creators and no file rule.** "Made on first use" in both processes means the app and the extension can each make one at the same moment. The rename that loses leaves links signed with a dead key, and every tap from them reads as N5, a false "didn't come from your widget". The key file is also not on ADR-007 s8's list, and the extension signs while the phone is locked.
Fix: only the app creates the key, with an exclusive create then a re-read, at first launch and before any action is saved. The extension reads it; with no key it draws the unsigned `w/` link, which opens the default. The file uses the App Group's default protection (readable after first unlock), sits beside `.lane-demoted.json`, and is never in an export or a project. `sig` is never written to the run log or the console.

**M9. Toggle is not mentioned, and retiring Ruling 5 would cover it.** Ruling 5 covers Button *and* Toggle. Retire it for Toggle and Toggle taps have to mean something, which needs L5's `isOnState` and ops, both 1.1.
Fix: item 5's dated line retires Ruling 5 for Button only. Toggle stays drawn and inert in 1.0 with its console line, is not person-settable, and counts toward s3's caps. `RefreshButton` counts toward the caps and is not settable.

## Low

**L1. The caps lint.** At `entry()` it is one console line per family that draws more than its cap, not an error: s3 says the renderer draws the first N, and a lint that raises would stop a render the phone would show. Count in depth-first tree order, drawn instances (H1), Buttons, Toggles and `RefreshButton`. One fixture table drives the Python and Swift tests so both drop the same buttons.

**L2. Q2: manifest `args` are passed as given. There is no declared shape in 1.0.** The picker in s9 has no way to type args, so in 1.0 a stored `run` carries none (absent means `{}`). Args come from the tree's default (H1) or a hand-edited or imported manifest, so a handler treats `args` as untrusted input; API.md says so in the `Widget.action` row. Both readers check: a JSON object, finite numbers only (`_finite_json`), at most 1 KiB. The KiB is measured on canonical bytes: sorted keys, separators `,` and `:`, UTF-8, no ASCII escaping. `v` hashes the bytes the app wrote into `actions.json` and never re-serializes them, because Python writes `250.0` where Swift writes `250`. A declared shape (`@widget.action(..., args={...})`) is an additive later field once there is a form to fill.

**L3. The numbers.** s4 cites the cold 9 MB but not ADR-007 s3's warm 11 to 15 MB. A button press usually lands in a warm extension that has just rendered, and the margin as first built would have refused 4 of the 69 runs. `lane-peak` is shared by render and handler, which is safe (the higher figure wins). Step 9 should count button refusals in warm processes, not only the peak.

**L4. iOS 27 background runs.** The app's background limit A is unmeasured (ADR-007 s6), so the margin applies at the run's start. A busy or `stuck` queue refuses the tap with the badge instead of holding `perform()`. A cold background launch does not run <span title="The rule that decides whether an idea gets two blind graders now, waits (park), or stops.">T1</span>'s batch.

**L5. `ui.Open.code(file=)`.** The path is relative and ends `.py`, with no `..` part and no leading `/`, and it resolves inside the project. Checked in Python at the call and in Swift at the tap; a failure is N6.

**L6. Imported projects.** A manifest from someone else can set a widget's tap to an https link or a `run`. Signing does not help here, because the extension signs whatever is stored. Ask on import, or reset `tap` and `buttons` to the default. This is Idris's and Maren's call; noted so it is decided.

**L7. The 'open an app' action (Operator note 21:4x, #41 c6905759408).** It will be a sixth `do`. The reader refuses an unknown `do` (s1 rule 2), so it ships as `formats.actions: 1` only if it is in before the first build that writes actions; otherwise it is `2`. `ui.Open.app(slot)` fits item 3 as written.

**New Low, mine to build in step 5.** s6 hands Python "the same decoded value" Swift hashed. Swift's canonical bytes write `250.0` as `250`, so a handler gets an `int` where `Widget.run_action` in a test gave it a `float`. The run request carries the canonical bytes and Python decodes them; API.md's `Widget.action` row says integral numbers may arrive as `int`. In (c), `action.name` is the function's name; I will call it `function` in the contract line so it is not read as the button's.

**Section 5a, from my side: nothing unsafe.** The widget and `tree.json` carry a slot id, never a link; the extension never reads `slots.json`; the app checks the link again with `LauncherTarget.check` at the tap; `app` is in `formats.actions: 1`, so no reader meets it as unknown. `ui.Open.app(slot)` is checked in Python with the slot id rule, mirrored from `LauncherLink.isSlotID` through step 1's shared fixture table. That only ever opens an app the person chose, so it is safe; the slot row's "where else it is used" should list script defaults as well as stored actions.
