## Plain summary (for the Investors)

Every project becomes one folder holding its files and one small file, `pywidget.json`, that says what the project is and what it makes. Each project gets **one ID** when it is made, and the ID never changes. Everything else that today has its own name (the widget, the Shortcuts entry, the saved keys) hangs from that ID, so renaming a file or a widget can no longer break anything.

Existing projects are moved once, the first time the new version opens. Nothing a person made is moved or rewritten: each project folder gains its `pywidget.json`, and widgets already on the Home Screen, and Shortcuts already set up, keep working without being touched. A test proves this on a copy of every case we know of, and a run on a phone with the current TestFlight build proves it again.

Code someone else made (a project opened from a file, or a folder copied into the app's folder in Files, even one with a project's name or ID) does not run in 1.0. The app shows every file and, in plain words, what the project says it uses, and that is all it does with it. We looked for a way to run such code inside the app with less reach than the person's own, and found none we can promise holds yet. If the person reads it and wants it, they can make it their own project; from then on it runs like code they wrote, with the same access, and the app says so before they choose. Making it their own always makes a new project, which starts with no saved keys and no widgets or Shortcuts. A project whose folder has gone stays in their list, marked missing, until they delete it (which deletes its saved keys too) or the same folder comes back; no other folder can take its place or its keys. If something like a restore ever leaves one of their own folders looking like someone else's, they make it their own and set up its keys, widgets and Shortcuts again by hand (section 11). Whether 1.0 works this way, or we build the walled-off way first, is a question for the Investors (section 7).

When a project came from the Gallery and a newer version exists, the app offers it and the person chooses. Nothing updates by itself, and a file the person changed is kept unless they say otherwise. In 1.0 the fields that make this possible are written, and no update is offered yet; the offer screen is 1.1.

Widget tap and button choices (ADR-011) are stored in the same file, beside the widget they belong to. So is which piece of data each value on a widget shows; a piece of data a widget uses can't be deleted, and renaming it offers to rename it everywhere it is used (#325).

## 1. Decision

1. **One folder per project**, directly inside `Documents/Scripts/`, as today. The folder's name is the project's name. Layout inside is free (03-structure s1's option A): the manifest names each output's file, and a programmer may keep one `main.py`; templates and the Builder make tidy folders, and the app enforces none.
2. **One manifest per project**, `pywidget.json` at the folder's top, format 2 of today's file (section 4). It is the truth: the app reads a project's outputs from it, never by scanning saved text for `Widget("<id>")`. Every copy the widget extension reads is a cache built from the folder, never a second original.
3. **One ID per project** (section 3): a random UUID, written once by the app, never changed, never typed. Every other identity is derived from it and stored, never recomputed (section 5).
4. **The move of existing projects** (section 6) writes a manifest into each project folder and moves saved keys to the project's scope. It moves no widget folder in the App Group, so placed widgets and Shortcuts keep the ids iOS already holds for them. It is resumable after a crash, a no-op when run twice, and tested on a fixture of every case.
5. **Outside code** (section 7, #284 A): recommended for 1.0, it never runs, in either process. It is marked in the index, opens read-only, and its page shows every file and what its `touches` declare. **Make it mine**, a tap on that page only, turns it into the person's own project, always a new one with its own ID and no saved keys, with words saying it will then have their reach. An in-process boundary (an interpreter of its own) is a later option with named preconditions, not 1.0.
6. **Versions** (section 8, #285 B): `version` is the file's format; the item's version and a fingerprint of every installed file live in `origin`. Updates are offered, never applied without the person's tap; a changed file is kept unless they choose otherwise.
7. **Actions** (section 9, ADR-011 s10): `tap` and `buttons` on each widget output; `formats.actions`; the extension reads only the App Group cache `widgets/<key>/actions.json`.
8. **Display values bound to data** (section 4, #325): `sources` names each data function and its outputs; a widget's `bind` maps each value its display shows to one of them; the app refuses deleting an output a display uses and offers renaming every reference.

## 2. The folder

```
Documents/Scripts/                    the projects' root (ProjectStore.app; files.documents() today)
├── My Weather/                       one project: one folder, one ID
│   ├── pywidget.json                 the manifest (section 4)
│   ├── main.py                       any layout; the manifest names each output's file
│   ├── views/today.py
│   └── data/cities.csv
├── Recovered/                        a project like the others (ProjectStore.recovered)
└── notes.txt                         a loose file: not a project, never moved (T-0663)
```

- A project is a folder directly in the root that is not hidden and not a link (ProjectStore's rule, unchanged). A folder with no `pywidget.json` is still listed; the app writes one for it at once (section 6, step M2, the same code as the move), and a folder the index does not know is outside code whatever it holds (section 3).
- The folder name is the project's name, so Files and the app show the same thing. The manifest's `name` is a copy for exports and for Shortcuts; when the two differ (a rename in Files), the app writes the folder name into `name`. A rename never changes the ID.
- Keys and passwords stay in the keychain under the ID, never in the folder, so an exported project cannot carry them (03-structure s1).
- The app's own records about a project live outside the folder, in the app container: `Library/Application Support/pywidget/projects.json` (the **index**: per ID, the folder name, its `fileIdentifier` and the `volumeUUIDString` of the volume it was recorded on, as one pair per entry, and once for the whole index the volume UUID the app last saw (section 3), each output's name and `key`, whether the project is outside code (section 7), and whether it is missing (section 3, rule 5)). The index never travels with a project, so a project file cannot say it is the person's own, and a key changed in the file is never believed (section 5). Premades' tap and button choices sit beside it, in `premades.json` (section 9).
- The App Group keeps its layout: `widgets/<key>/` (the run's copy, `tree.json`, `.sent.json`, the locks), `lane-scripts/<key>/` (the extension's mirror, section 4 "The mirror"), `scripts/<key>/` (`files.shared()`, `premade.json`). `<key>` is a widget output's key (section 5). Each `widgets/<key>/` gains one file, `project.json` (section 5), written by the send inside its one rename.

## 3. The ID

- **Form.** The app writes a random version 4 UUID, lower-case, 8-4-4-4-12 hex. The readers check what today's `check_id` in `app_manifest.py` checks, unchanged, and the Swift reader's twin: 8-4-4-4-12 hex in either case, read as lower-case, never the nil UUID, **any version**. Accepting any version is deliberate: format 1 files and the mirror's file (`LaneMirror.defaultManifest`, a name-based version 8 UUID) must keep reading. A manifest ID that is not version 4 is not refused; only the app's own new IDs are promised to be version 4.
- **Made once, by the app,** when a project is created, moved (section 6), imported from a file, or got from the Gallery. Import and Get always make a **new** ID, so two people's copies of one item, or two imports of one file, are never one project. A Get writes `origin` with the item's fixed ID. An import, and a folder found in the root (rule 2), keep any `origin` the manifest already has, so a Gallery item's `origin.id` survives an export and an import and its updates can still be offered (section 8); only a manifest with no `origin` gets one, of `kind` `file`, with the ID it carried as `origin.id`.
- **Never changed.** No code path gives a project a different ID: a manifest's `id` is only ever written from the index (rules 1 and 2 below). A person never types it; it is shown only in the project's About row, for support.
- **One ID per folder, one folder per ID.** The index knows each project's folder by its file identifier, the folder's `fileIdentifier` (`URLResourceValues.fileIdentifier`, the APFS inode number, iOS 16.4 and later; the deployment target is 18.0), together with the `volumeUUIDString` of the volume it was recorded on, both in that project's entry, with the name beside it, never by the name or the manifest alone. Not `fileResourceIdentifier` or `volumeIdentifier`: the SDK's `NSURL.h` says both are "Not persistent across system restarts", so an index keyed by them would lose every folder at each restart. The inode number belongs to the folder on disk, so a rename and a restart keep it, and a folder deleted and made again under one name gets a new one; step 2 tests both, on the iPhone for the restart (section 12). An inode number is unique only on its own volume, so an entry matches only by that pair, never by the number alone. The app records the identifier and the volume UUID together whenever it makes a folder (a new project, an import, a Get, `Recovered`, the move). A rename keeps the identifier, so the index follows a folder renamed in Files; a folder copied in, duplicated, or put in place of another by Files' Replace is a new folder with a new identifier, whatever its name and whatever ID it carries, and stays so after any number of restarts. On every listing the app compares each folder, and its manifest's `id`, with the index:
  1. **A folder the index knows**: its `fileIdentifier` equals an entry's, and the volume UUID the device reports now equals the one stored in that same entry, a missing project's entry included (rule 5): it is that project, under whatever name it now has. If its `id` differs from the index's (changed by hand, or to another project's ID), the index's ID is written back, and the page says so.
  2. **A folder the index does not know**, whatever it holds: no manifest, an ID the index has never seen, or **an ID the index holds** (a Files duplicate, or an export copied back in: an export keeps `id`, section 5), and including **a folder that replaced a same-named project folder** in Files. It keeps its files, gets a new ID and new output keys like an import (its `origin` as for an import, above), and is **outside code** (section 7): shown, never run, until the person makes it their own. So it inherits nothing from the project it resembles, then or later: not its ID, its saved keys, its placed widgets or its reach. When its ID was another project's (the index notes the ID it carried for this line, and for nothing else), the page says "This is a copy of “My Weather”, so it is a project of its own." (DRAFT).
  3. **During the move** (section 6), before the index exists, every folder is the person's own; two folders with one format 1 ID: the first in Finder order keeps it and the other gets a new ID.
  4. **A restore or a new phone** gives every folder a new identifier. The index keeps, once, the volume UUID the app last saw, and this rule fires **only when that UUID differs** from the one the device reports now: then the index and the folders came back together from one backup, so each entry not marked missing is matched once by folder name and `id`, its new identifier and the new UUID recorded in its entry, the last-seen UUID is set to the new one, and nothing is marked outside by the restore. An entry already missing stays missing and keeps its old pair: its volume UUID is no longer the device's, so no folder on the new volume matches it by rule 1, even one that gets the same inode number. A folder that then matches no entry is outside, as in rule 2. A restart, an iOS update or an app update keeps the UUID, so the rule never fires for them and a folder put in by Replace before a restart is still the unknown folder of rule 2. If the device reports no UUID (`nil`), the rule does not fire: unmatched folders are outside by rule 2, with new IDs and keys, and their old entries are missing (rule 5); section 11 says what that loses and how the person sets each one up again.
  5. **A missing project.** A project whose folder is no longer found by its `fileIdentifier` (deleted or replaced in Files, moved out of the root, or its identifier changed) keeps its index entry, marked **missing**, with its ID and output keys, and its saved keys stay under `<id>/`. The Projects list shows it, its name with "Missing" (DRAFT); its page says "This project's folder isn't in PyWidget's folder any more. Its widgets and Shortcuts don't work, and its saved keys are kept until you delete it." (DRAFT) and has one button, **Delete**. Nothing runs it, and `WidgetChoiceQuery` and `ScriptQuery` do not list it. An entry stops being missing in only two ways: the person deletes it, which removes its saved keys under `<id>/` and its index entry, as Delete does for any project; or the same folder comes back, found by the entry's own pair, its `fileIdentifier` and its volume UUID (rule 1). That is the only automatic match, and no copy can make it, because a copy is a new folder with a new identifier. No name, ID, file, listing or tap points a missing entry at another folder: a folder with its name and ID is a project of its own by rule 2, and Make it mine makes it a new project with a new ID and no keys (section 7). So a missing project's keys can be deleted by the person, and no other folder reaches them.
- **What derives from it:** section 5.

## 4. The manifest, format 2

Today's file is `{"schema": "pywidget.app", "version": 1, "id", "name", "entry"}` plus kept extras, of which the app reads one, a top-level `lane` (`LaneMirror`, `lane.mirror_entry`). Format 2 has no top-level `lane`: the lane is per widget output. Format 2 keeps `schema` and the meaning of `version` (the format of this file), so a build that reads format 1 refuses a format 2 file with its own `newer_version` words ("This project was set up by a newer version of PyWidget. Update PyWidget to open it."), which are true.

```json
{
  "schema": "pywidget.app",
  "version": 2,
  "id": "3f0c9a52-7d1e-4b8a-9c2f-5e6d7a8b9c0d",
  "name": "My Weather",
  "outputs": {
    "today": {"kind": "widget", "view": "views/today.py", "title": "Today",
              "key": "3f0c9a52-7d1e-4b8a-9c2f-5e6d7a8b9c0d.today", "lane": "widget",
              "bind": {"temp": "weather.temp_c", "summary": "weather.summary"},
              "tap": {"do": "page"},
```

| `touches` | `capabilities`: ids from the draft schema's list (`manifest.schema.json` `$defs/capability`, for example `location.when_in_use`, `calendar.read`), unique, at most 32; `network` and `open`: host names, lower-case, A-labels, no wildcard, no port, at most 16 and 8 | touches nothing |
| `formats` | an integer per part the project holds: `tree` (ADR-002), `blocks` (ADR-008), `actions` (ADR-011), `bind` (`sources` and `bind`, this record) | the part is absent |
| `origin` | section 8 | the person's own project |
| `builder` | reserved for ADR-008 (the Builder's fingerprints and compiler version); format 2 refuses nothing there and reads nothing | — |

</div>


- **Unknown top-level keys are kept** and written back unchanged (today's `extra`), so a newer app's additive field survives a round trip through an older one. A part whose `formats` number is newer than the app's is refused in plain words naming the part ("This project's widget actions were set up by a newer version of PyWidget. Update PyWidget to open it.", DRAFT), as ADR-011 s10 asks for `actions`.
- **Reading** keeps today's reader's guards unchanged: 64 KB at most (`MAX_APP_MANIFEST_BYTES`), a regular file, never a link, UTF-8, strict JSON with no duplicate keys and no `NaN`, and a stable `code` for every refusal. New codes: `bad_output`, `bad_key`, `bad_lane`, `bad_touches`, `bad_origin`, `bad_source`, `bad_bind`, `newer_format`. Both halves (Python `app_manifest.py`, Swift `ProjectManifestReader`) read one fixture table, as `tests/bridge/fixtures/app_manifest/cases.expect.json` does today.
- **Writing** is the app's alone, one atomic replace (temporary file and rename, as `app_manifest.write` does), keys in a fixed order, so a manifest's bytes change only when its content does. **Run code may not write it** (Pernille's review M2): today a run's `files.documents()` is the root, so a script can rewrite any project's `pywidget.json`. The file check (section 7) refuses, for every run in either process, own code included: opening a `pywidget.json` anywhere under `Documents/Scripts/` for writing or appending, and `rename`, `replace`, `remove`, `link`, `symlink`, `truncate`, `chmod` and `utime` with one as either path; the same for the app's caches (`widgets/*/project.json`, `widgets/*/actions.json`, `lane-scripts/*/pywidget.json`). For the person's own code this is a guard against accidents, not a boundary (`lane.py`'s threat model); what makes a rewrite harmless is that nothing a run could gain is read from the file alone: keys come from the index (section 5), the outside mark from the index, and an outside project's file is never run, whatever it says (section 7). A rewrite a person makes in Files, outside any run, is read like any hand edit.
- **The mirror** (`lane-scripts/<key>/pywidget.json`, Pernille's review M1). Today it is the project's format 1 file when that names the sent file as `entry` (with its `lane`), else `LaneMirror.defaultManifest(id:)`; `lane.mirror_entry` reads it through `app_manifest.run_setup` and refuses a `lane` other than `widget`. With format 2 it is always `defaultManifest(id: <key>)`: a format 1 file, `{"entry": "main.py", "id": <the name-based UUID of the key>, "name": <the key, cut to 64>, "schema": "pywidget.app", "version": 1}`, sorted keys, no `lane`. It is a cache the send writes, never read as the project's manifest and never copied from it; its `id` is the cache's own, not the project's ID (the extension takes that from `project.json`). So `mirror_entry` and `run_setup` keep reading format 1 unchanged, a mirror's presence is what puts a widget in the widget lane (a send kept out removes it, as today), and the extension never reads format 2.
- **Which file each open uses** (M1). Only a key reaches the app from outside it, and only `widget` and `shortcut` outputs have keys, so iOS never names a `run` output.
  - A Home Screen tap (`pywidget://w/<key>`, default `code`, ADR-011 s2): the output holding that key in the index, the editor at its `view`. This replaces `WidgetTapRouting.scriptFile`'s scan of declared ids, which stays only for a key no output holds yet (before the move reaches it).
  - A widget's render, in either lane: its `view`, sent as `main.py` (today's rule, T-1905).
  - A Shortcut (`ScriptEntity`, a key): a `shortcut` output's `run`, or a `widget` output's `view` as today.
  - The project page's **Run**: the `run` output named `main` (the move's name for a format 1 `entry`). With no `main`, the page lists the project's `run` outputs and Run asks which; none is picked silently. The editor's Run runs the open file, as today.
- **Display values and their data** (the binding). The Operator's note of 11-18 on T-4476 puts it in this record: "the manifest ADR must carry the binding of display values to named data-function outputs and the reference check that guards delete and rename" (an Investor, #325 c6982170889, 9:54 AM ET 11-18: "Dynamic values on the display must be pulled from the outputs of the data functions. Similarly, data function outputs can't be deleted or renamed unless their references are first removed from the display."; the rename answered B, #325 c6985066876, 11:42 AM ET 11-18, `log/rulings.md`: "renaming a data function's output that a display uses is offered as a rename everywhere it is used; deleting a used output is refused until no display uses it"). The format is `sources` and each widget output's `bind` (the table above); ADR-008 carries the rest of the Builder's rules from the same comment.
  - **How a bound widget runs.** At each refresh the run calls each source its `bind` names once (`function()` from `file`, in the same run, as the view's own code runs today) and hands the view's `draw(data)` a mapping holding exactly the bound names, each the value the function returned under the output's name. A source whose result is not a mapping, or lacks a bound output, ends the run with one console line naming both ("weather.read() returned no “temp_c”, which Today uses.", DRAFT), and the widget keeps its last drawing. The Builder's views always read their values from `data` (ADR-008), and its design files name a value by its `bind` name, never by the source's output, so a rename below rewrites the manifest alone. A hand-written widget with no `bind` fetches for itself, as every widget does today; the move writes no `sources` or `bind` (section 6).
  - **The reference check, on delete and rename.** Every change the app makes to `sources` (the project page, the Builder, the app's file list) passes one check before the manifest is written. **Delete:** an output, a source, or the file a source names is refused while any widget output's `bind` names it, with words naming each widget ("“temp_c” is used by the Today widget. Remove it there first.", DRAFT). **Rename** of an output or a source that a `bind` names offers "Rename it in Today too?" (DRAFT); yes rewrites the declaration and every `bind` that names it in the manifest's one atomic write, and no changes no byte, so a half rename never exists. Renaming a source's file in the app rewrites its `file` the same way. The function's own Python is ordinary code the app never rewrites (03-structure s3, (d)), so after a rename of an output the page says the function must return the new name, and until it does the console line above names it.
  - **Outside the app's own edits** (a hand edit in Files or on a Mac; a run cannot write the file, above), the reader is the check: a `bind` naming no declared source output is refused, `bad_bind`, naming the entry, and a source file deleted in Files leaves its widgets on their last drawing with the page naming the missing file.
- **The draft permission schema** (`docs/design/manifest.schema.json`, Odalys, 10-25; nothing reads it) is joined into `touches` as 03-structure s1 proposed: its capability ids and its `network.domains` and `open_urls` lists are kept; its `secrets`, `data_sources`, `content_rating`, `files` and signature are for a shelf of other people's work (1.2 at the earliest, #274 A) and are not in format 2.

A send, the extension's `project.json`, the keychain scope and the Shortcuts list all take the key from the index. ## 6. The tested move of existing projects

### What exists today, from the code

1. Project folders in `Documents/Scripts/<name>/`: `.py` files at the top and, since T-1905, any files below; some hold a format 1 `pywidget.json` (id, name, entry, and a typed `lane`).
2. `Documents/Scripts/Recovered/`, made by a save that could not write in place; loose files in the root (never projects).
3. In the App Group: `widgets/<id>/` per sent widget (the project's copy with the widget file as `main.py`, `tree.json`, `.sent.json` naming the widget file and listing the project's files with size, date and status-change time, the locks and lane records); `widgets/index.json`; `lane-scripts/<id>/`; `scripts/<id>/` (shared data and premades' `premade.json`).
4. In the keychain: items `pywidget.secrets` / `<widget id>/<name>` and `shared/<name>`.
5. Held by iOS, out of the app's reach: placed widgets' configurations and Shortcuts actions, each holding a widget id string.
6. Premades: read-only in the bundle, widget ids `pywidget.premade.<name>` (`WidgetID.premadePrefix`), settings in `scripts/pywidget.premade.<name>/premade.json`.

### The steps

The move runs once, in the app, at the first launch of the build that has it, before the Projects screen lists anything. The extension may run before, during and after it: nothing it reads moves, so it keeps drawing every widget.

- **M0. Journal.** Write `Library/Application Support/pywidget/move-2.json`: the plan (every project, every claim, every key item to move) before any change, and a mark per finished step. A crash resumes from the journal; a finished move leaves it as the record and the move never runs again.
- **M1. IDs.** For each project folder: a valid format 1 manifest keeps its `id`; any other folder gets a new UUID. Two folders with one format 1 ID: section 3's rule (the first in Finder order keeps it; the move's summary names the other).
- **M2. Outputs.** Each `widgets/<key>/` (premade keys left out) is claimed by at most one project: (a) the project whose top-level file the folder's `.sent.json` names with the exact recorded attributes (ProjectBoundary's match); else (b) the only project with a top-level file whose declared id is `<key>` (`declaredID`); else, with two or more such projects, the first in Finder order, and the summary names the others. A claimed folder becomes a `widget` output: name from the key (lower-cased, other characters to `_`, a leading non-letter prefixed `w_`, cut to 32, `_2` on a clash), `view` the claimed file, `key` **the folder's own name**, `title` the key as the picker shows it today. A format 1 `entry` becomes `{"kind": "run", "run": <entry>}` named `main`; a folder with no format 1 file and a top-level `main.py` gets the same. A format 1 top-level `lane` is copied to every widget output of that project (today `LaneMirror` applies it to every send of the project) and is not kept at the top level (format 2 refuses it there, section 4). The file declaring an id that no folder holds gets no output (it was never sent, so nothing iOS holds names it); its project page offers "Make a widget".
- **M3. Orphans.** A `widgets/<key>/` no project claims (its project deleted or renamed away) becomes a new project named after its key (ProjectStore's clash naming), its files copied from the widget folder: the paths its `.sent.json` lists, else `main.py` alone; never `tree.json`, `.sent.json`, the locks or the lane records. Its output keeps the key, so the placed widget keeps drawing and can be edited again.
- **M4. Manifests.** Write each format 2 `pywidget.json` atomically. A format 1 file's bytes are kept first in `Application Support/pywidget/move-2/<id>.v1.json`. A folder that already holds a readable format 2 file is left alone (the move is a no-op on it).
- **M5. Keys, copied.** For each moved output, every keychain item `<key>/<name>` is copied to `<id>/<name>` and read back. Two outputs of one project with one name and different values: the first output in name order wins, the other is left where it is, unread, and the project page lists it ("A saved key named token came from two widgets; the one from today.py is kept.", DRAFT). `shared/<name>` is not touched.
- **M6. `project.json`.** Write `widgets/<key>/project.json` for each moved key (`"outside": false`), as one temporary file and rename into the folder; nothing else in the folder changes.
- **M7. Keys, removed, at a later launch** (Pernille's review, low). A run reads `project.json` once, at its start, so a run that started before M6 keeps the old scope to its end, and deleting the old item under it would lose its key, or a value it wrote after M5. So M7 never runs in the launch that did M6: the journal records M6's finish time, and M7 runs at the first app launch at least one hour after it (every run, in either process, is <span title="A measured fact that holds a grade below a letter, however good the rest is.">capped</span> far below that: the extension's in seconds, the app's background runs at 30 s, a foreground run ends with its process). For each old `<key>/<name>`, M7 compares it with the `<id>/<name>` copy; an old value that differs (written by a run after M5) is copied again, read back, then the old item is deleted. Up to M6 a run finds the key under its old account (no `project.json`, today's scope); from M6 under the new one, which M5 wrote first, so no run ever finds it missing.
- **M8. Index.** Write the index: every project `outside: false` (everything on the phone before the move is the person's own), with the folder names, each entry's `fileIdentifier` and the volume's `volumeUUIDString` as its pair, the same UUID once as the one last seen (section 3), and every output's key. The move's other steps do not wait for M7; M8 and M9 run in the first launch.
- **M9. Summary.** If anything was claimed by rule (b) over another project, made from an orphan, renamed on a clash or left in M5, one sheet says so in plain words, once (DRAFT, Maren's words before the step ships). Otherwise the move is silent: nothing a person made has changed.

Not moved: loose files; premades (they become bundled projects with fixed company IDs and their keys stay `pywidget.premade.<name>`; their settings stay in `scripts/`); `lane-scripts/`; `widgets/index.json`; `scripts/`. ADR-011 actions: none exist before the manifest, so the move writes none and absent is the default (ADR-011 s10).

## 7. Outside code: shown, never run, in 1.0 (#284 A)

**Which code is outside.** A project is outside code when it arrived from outside the app: opened from a file or a zip (`ProjectTransfer`), or found in the root as a folder the index does not know (section 3, rule 2). That includes a folder that carries an ID the index holds (an export keeps its `id`, so a project sent away and copied back in carries one, as does a Files duplicate) and a folder that took the place of a same-named project folder through Files' Replace: the index knows folders by their file identifier, not by their name or their manifest, so neither becomes the person's own, nor gets the ID, keys or reach of the project it resembles (section 3, rules 2 and 5; the test is `ProjectIdentityTests`, section 12 step 2). The index records the mark; the manifest never does, so a file cannot declare itself the person's own. Files changed inside a folder that is already the person's own are not outside: they run (section 11). Projects made in the app, moved in section 6, or got from the in-app Gallery (company code in the reviewed binary, #276) are the person's own. The only way from outside to own is **Make it mine** (below).

**No in-process boundary holds for 1.0** (Pernille's second review, of 0305343b01). The previous revision ran each outside project in a Python interpreter of its own inside the app, with less reach checked per call. Her review found four things that design does not survive:
1. **The interpreter is not a wall** (high). The Python the app ships lets code in an interpreter of its own reach the main interpreter and start new interpreters without the app's checks, so "outside code runs in its own interpreter" is not a boundary as written. It is not yet checked on the 3.15 build the app ships.
2. **The hard stop cannot reach it** (medium). Every Swift and C path that enters Python (`PythonRuntime.swift`, `EditorTooling`, `SendLaneScan`, `pw_rt_hard_stop`) takes the main interpreter through `PyGILState_Ensure`, so a run in another interpreter is out of the hard stop's reach.
3. **The module fence contradicted the http module** (medium). The record applied the lane's `NEVER` list to outside code in the app, but that list refuses `urllib`, which `pywidget.http` imports (`urllib.parse`). The last revision also said `pywidget.files` needs it through `pathlib`; that was wrong: on 3.15 `pathlib` loads `urllib` only inside its URL methods (Pernille's third review).
4. **Common modules would not import** (low). numpy, Pillow and matplotlib use single-phase initialisation and refuse to import in an interpreter with its own GIL, so outside code there could not use them.

Each of the last three is work with a known shape; the first may not be fixable while the module behind it ships; and beneath all four, `lane.py`'s fence is "Not a sandbox" and CPython does not promise audit hooks as one. So this record claims no in-process boundary for outside code in 1.0, and recommends the cautious way its open question already named.

**The recommendation for 1.0: no outside code runs.**
- **Shown.** An outside project opens read-only. Its page says "Code from someone else", its name, where it came from (the file's name) and, if the manifest has one, `origin.maker` shown as the file's claim, "Says it's from: <maker>" (DRAFT), never as a fact, since nothing checks it, what it uses in words, one row per entry of `touches` ("Your location while you use the app", "The internet: api.open-meteo.com"; with none, "It doesn't say it uses your location, contacts or the internet."), and every file, each openable read-only in the editor; then "PyWidget shows this code but doesn't run it." (Maren draws it; all words DRAFT). The rows are what the file declares, not a promise: nothing checks them, because nothing runs.
- **Never run, on any path.** Run, a widget send, a Shortcut, a button, a widget tap's `run`, a background refresh: each refuses an outside project with "This project came from someone else. PyWidget shows its code but doesn't run it." (DRAFT). Its outputs get keys in the index (section 5), but `WidgetChoiceQuery` and `ScriptQuery` do not list them, and nothing of it is sent to `widgets/` or written to `lane-scripts/`. So neither process ever holds outside code to run.
- **Reading is not running.** The editor's tooling and the send's lane scan read an outside file's text; they never import it or execute any of it. A test in step 5 holds it: an outside file whose top-level code writes a marker is opened, highlighted, completed in and listed, and no marker is written.
- **Make it mine.** A button on the outside project's page, and nowhere else: never from a file, a link, a Shortcut, a run or the manifest. It shows the same page with, above the button, "Once it's yours, it runs like code you wrote: it can use your saved keys, your other projects and the internet." (DRAFT). The tap sets the project to the person's own in the index; nothing in the folder changes, and its ID and keys are the ones it got at import, which no other project holds (section 3). It always makes a new project with no saved keys: whatever name and ID the folder carries, it never becomes a missing project and never reaches that project's keys, widgets or Shortcuts (section 3, rule 5). From then on it is an own project like any other, and its `origin` stays as the record of where it came from. This is sound because it claims no boundary: before the tap nothing of it runs; after it, the code has exactly the reach of code the person typed or pasted, and the screen said so first. What it rests on is the person's reading, a risk named in section 11, not a check. Making a project one's own gives it more reach than #284 A's "less reach" for outside code, so it is part of the Investors' question below, not decided here.
- **The person's own code** runs as today, in the main interpreter, where the hard stop reaches it. A first use of a capability or host not in its `touches` is added to `touches` by the app (at the run's end, or at the next foreground for a run in the widget, from its run-log row), and the project page shows it.
- **The file check** for every run, own code included: an audit hook refuses writes to any `pywidget.json` and the app's caches (section 4), with today's lane hook (`lane.py`, T-0707) as its model. For own code it is a guard against accidents, not a boundary.

**Today's gap, named.** `ProjectTransfer` already imports `.py` files and zips (T-0355 slice 2), and their code runs with the person's own reach, in the person's own interpreter; ADR-001 s6 says no outside code runs before phase C. That gap is board line **T-5891** (a step of T-4476). Build step 5 marks every import outside and read-only from its first commit; until it lands, the build that leaves internal TestFlight must not have import, or must have this step.

**A later option: outside code in an interpreter of its own.** Kept as the design to return to, not built for 1.0. Each outside project would run in a subinterpreter of its own in the app (`Py_NewInterpreterFromConfig`, own GIL, `check_multi_interp_extensions` on), one alive at a time, never reused for another project, ended at a memory warning; the router would know the caller by its interpreter, from per-interpreter state in a multi-phase `_pwbridge` (today it is single-phase, with one thread state, `g_ts`, and one run id per process, `Shared/Bridge/pwbridge.c`); the app would show a notice and record an approval (a SHA-256 over every file's path and hash, `touches`, and each output's name, `kind`, `view` and `run`, kept in the index) before the first run and after any change made outside the app; and the extension would never run outside code (its widgets in the app lane only). Its reach would be:

Its preconditions, each a test that passes on the shipped build before it could be offered:
1. **No way out of the interpreter.** The route found in Pernille's review, and every other way to reach the main interpreter or make an interpreter without the run's checks, is removed from the shipped Python or refused before any outside code runs; checked on the 3.15 build the app ships.

## 8. Versions and updates (#285 B)

- **`version`** is the manifest's format (section 4). The item's own version is **`origin.release`**, an integer that rises by one with each release the maker publishes, with **`origin.label`** the words shown ("1.3"). Comparison uses `release` only.
- **`origin`** is written once at Get or import: `kind` (`gallery` or `file`), `id` (the item's or the file's ID; the company's Gallery items have fixed IDs), `release`, `label`, `maker`, `licence`, and **`files`**: each installed file's path and SHA-256, at most 512 entries (a larger project is not a Gallery item). An import, or a folder found in the root, keeps an `origin` its manifest already carries, so the Gallery item's `origin.id` stays the update source (section 3). In an imported or found project every `origin` field is what the file claims; `maker` is shown only as "Says it's from: <maker>" (DRAFT, section 7). The person's own projects have no `origin`.
- **The offer.** When the Gallery holds the item `origin.id` at a `release` higher than the project's, the project page shows "Version 1.4 is available" and what changed (DRAFT). Nothing else happens until the person taps.
- **On the tap**, per file of the new release: a file whose bytes still match `origin.files` (untouched) is replaced; a file the person changed is shown side by side and **kept unless they choose the new one**; a file they deleted is not brought back unless chosen; a new file is added; a file the release removed is removed only if untouched. If the new release's `touches` adds anything, the app asks first ("This adds: your location.", 03-structure s1); an outside project is never run either way (section 7). Then `release`, `label` and `files` take the new release's values (a kept file's entry takes the new release's hash, so it still reads as changed next time).
- **No thanks** writes `origin.declined: <release>`; that release is not offered again, the next one is.
- **Never silent.** No code path writes a project file from an update without the person's tap in that session: not a launch, not a background refresh, not an app update. A test holds a newer release in the Gallery across all three and checks every project file byte for byte.
- **In 1.0** the maker is always the company and the Gallery ships in the app (#274 A, #276). Get writes `origin` with its fingerprints, so a copy made in 1.0 can be offered 1.1's release; an app update never changes a person's copy, and the offer screen is 1.1 (ADR-001 s4).

## 9. Where tap and button actions live (ADR-011 s10)

ADR-011 s10 stands as written, with these words fixed by this record:
- `tap` and `buttons` sit on each `widget` output in `outputs`, and `formats.actions` is `1` when any output has either; absent means the default. A newer `actions` format is refused in words (section 4).
- ADR-011's `widgets/<id>/actions.json` is `widgets/<key>/actions.json`: the output's key. The app writes it on save, inside the send's one rename, as each action's canonical bytes; the extension reads only that cache, never the manifest.
- An output renamed keeps its key and so its actions' cache; a `buttons` entry for a button the tree no longer draws is kept (ADR-011 s8).
- On import and Get (outside or not), `link` and `app` actions are reset to the default and the summary counts them (ADR-011 s9 L6); `page`, `code`, `home` and `run` are kept.
- The move (section 6) writes no actions.
- **A premade's choices** (Pernille's review M3). ADR-011 s10 says premades' settings live "in the same place" as a project's, but a premade's manifest is in the read-only bundle. Its tap and button choices live in the app container beside the index: `Library/Application Support/pywidget/premades.json`, `{"formats": {"actions": 1}, "premades": {"<name>": {"tap": ..., "buttons": {...}}}}`, keyed by the premade's bundled name, each value read by the same `WidgetAction` reader with the same refusals, written by the app alone in one atomic replace. Absent, or a premade not named, means the default (`page`, ADR-011 s2). The app builds `widgets/pywidget.premade.<name>/actions.json` from it exactly as for a project's output, and the extension reads only that cache. Not `scripts/pywidget.premade.<name>/premade.json`: that is the premade's own data, which its Python writes under the shared lock (`PremadeSettings`, `_premade_lock`) and which `files.shared()` reaches; where a tap goes is the app's choice, like the index. The file is in the backup, as Application Support is, so a restored phone keeps the choices as it keeps a project's manifest. An app update that changes a premade's bundled files never rewrites it.

## 11. What would make this fail

- **iOS drops or changes the stored id of a placed widget across an app update.** T-M5 on a phone is the check; then the move would need a picker hint, not a different design.
- **People make a project their own without reading it.** Make it mine gives outside code the person's full reach, and what stands between is the page that shows every file and says so. Code can be written to look harmless. This is the same risk as pasting code from a web page into the editor, which the app allows today; the record does not claim more. If TestFlight use shows people tapping through, the button moves behind a second step, or leaves 1.0 and imports become read-only only.
- **People bring their own code in through Files.** A folder copied in from a Mac, a Files duplicate of their own project, or a folder put over one by Files' Replace is outside until the person taps Make it mine, once per project. If that is a burden in TestFlight use, the page's words change, not the rule.
- **Files changed inside the person's own folder run.** The index knows folders, not who wrote each file: a file added to or edited in an own project's folder through Files or a Mac runs with that project's reach at its next run, as a hand edit does today. Marking such files outside would also mark the person's own edits from a Mac; 1.0 does not, and the record claims no check there. What it does hold is that a folder never becomes the person's own by its name or the ID it carries (section 3).
- **iOS keeps a folder's identifier where the record assumes a new one, or changes it where the record assumes it stays.** The header says the inode number is "Not stable across all file systems or mounts"; the record relies on it only for folders in the app's own Documents on the phone's APFS data volume. If Files' Replace or a copy kept the `fileIdentifier`, a replaced folder would read as the person's own; if a restart changed it, or a restore kept the volume UUID, the person's projects would show as outside with new IDs and new keys, as they do with a `nil` UUID (section 3, rule 4). That is not free, and the record does not hide it: each such project's old entry is missing (section 3, rule 5), so its placed widgets get nothing new from it, its Shortcuts and automations no longer find it, and its saved keys are out of its reach. The person sets each one up again by hand: Make it mine on the folder (a new project, with a new ID and no keys), type its saved keys again, place its widgets again or choose the new project on each placed one, choose it again in each Shortcut and automation, then Delete the missing entry, which deletes the old keys. Nothing does this for them, because a folder's name and ID can be copied (an export keeps the ID), and each automatic or one-tap take-back built on them handed a copy someone else edited the old project's keys (Pernille's sixth review). A take-back by fingerprints (every file's hash matching one stored in the entry) was weighed and not chosen: the index would keep and rewrite a hash of every file of every project at each save, an edit from a Mac before the restore would defeat it, and it would be one more page where a tap hands over keys. If TestFlight shows this loss happening, that is the evidence to build one, as its own reviewed step. Step 2's seen checks on the iPhone (Replace, Replace then a restart, a plain restart, a restore) are the test; if Replace fails, the index also records the folder's creation date and a replaced folder is told by that.
- **Three known gaps in section 3** (Pernille's fifth review, lows; (a) narrowed, (b) and (c) noted, not yet changed). (a) A folder put in by Replace before a backup, and never listed by the app before it, matches its entry by name and `id` under rule 4 after a restore, so it becomes the person's own without Make it mine. Rule 4 now skips entries already missing, so this needs no listing between the Replace and the backup; it is the one place a name and an ID are believed, and only with a changed volume UUID. (b) If the index ever stored a `nil` volume UUID, the first real UUID would differ from it and fire rule 4, matching folders by name and `id`; the index should never store `nil`, and step 2 now tests that it never does. (c) Files' Replace may keep the replacing folder's creation date, so the creation-date fallback above may not tell a replaced folder apart; it is a fallback, and step 2's Replace check comes first.
- **The Investors choose B.** Then the later option's six preconditions (section 7) become 1.0 work, and if any fails (precondition 1 is not yet known to be possible), outside code does not run in 1.0 after all and the finding goes back to them.
- **The file check can be got round by own code.** It is a guard against accidents (section 4); nothing in 1.0 relies on it as a boundary, because what a rewrite of `pywidget.json` could gain is read from the index, never from the file.
- **A project with hundreds of files.** `origin.files` caps at 512 entries in 64 KB; a Gallery item larger than that is split or refused at the company's own build.
- **Two widgets of one project relied on separate keys with one name.** M5 keeps one and lists the other; if this is common in TestFlight use, keys get an output-level scope in a later format.
