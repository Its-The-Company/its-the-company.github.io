## The four questions

**1. Does catching BaseException swallow anything the runner must still see?** No.
- The runner's Stop reaches user code as `KeyboardInterrupt`, three ways: the soft Stop (the C half's interrupt, run by
  the user's SIGINT handler if one is set), its repeats (`user_code(True)` around the handler and `render()` only), and
  the hard stop (`hard_stop`'s `sys.monitoring` callback raising `KeyboardInterrupt` on every user line). All three are
  `KeyboardInterrupt`, and the `except KeyboardInterrupt` clause still comes first, so a plain Stop is still
  `interrupted` (probe rows 1 and 4; the hard stop still ends a double swallow at 2.2-2.4 s).
- A Stop the script itself turns into something else (its SIGINT handler raising a `BaseException`, or a
  `BaseExceptionGroup` wrapping the `KeyboardInterrupt`) now ends `error` with the script's type. That is the main
  code's rule too (`_classify` tests `isinstance(exc, KeyboardInterrupt)`, so the main-code group in probe row 5 is
  `error`), and before this commit those cases were `internal_error` with no lane keys, which demoted the widget. The
  run still ends: the clause sits after all user code in the run, and `_epilogue` then releases the hard stop and
  swallows any trip still pending, as before.
- The lane's time-out and <span title="A test written in advance. If it fires, we drop the idea.">kill</span> path: Swift's budget Stop is the same `KeyboardInterrupt`; past it, the extension's own
  limit ends the process, which no Python clause can catch. The one visible difference is in the Activity log: a budget
  Stop the script turned into its own exception is mapped by `RunResultSink` from `error` to that type, not to
  "Took too long" (that mapping needs status `interrupted`). Same as for an `Exception` raised from a SIGINT handler
  today, and as in the main code; I do not ask for a change.
- `MemoryError` and `RecursionError` are `Exception` subclasses and were already caught; nothing changes for them. If
  `format_error` itself fails inside the clause, the run still falls to `_last_resort` as before; not new.

**2. Do the tests fail without the fix?** Yes, both, on both interpreters, for the right reason (see Tests run). They
cover a script's own subclass, `GeneratorExit` and (3.11+) a `BaseExceptionGroup` from a handler, and `Boom` from a
render with and without a handler before it, in both lanes, and check status, type, no tree, one `finished`,
`background_threads` and the lane keys. They do not cover a Stop the script converts; the probe above does, and I do not
ask for it to be added.

**3. Are the docs consistent with each other?** Mostly; see L1, N1 and N2. The contract's s7 `error` row and the
`records.finish` docstring say the same thing. The how-it-works fingerprint is current
(`tools/site/how_it_works.py`: "The run ends", checked add84a3b3230, now add84a3b3230, ok).

**4. Is anything in Swift affected?** No. No Swift file changed, and no wire or record shape changed. `LaneGuard`
reads `never_resident` and `lane_tampered` whatever the status, so the fix only moves these runs from "keys missing,
malformed, demote" to "keys present, empty, no demotion". `RunResultSink` maps `error` to `WidgetRunOutcome(.error,
errorType: <the user's type>)`, as for any other script error.

## Findings

**L1 (Low, docs): two plain sentences say more than the app does about Stop.**
- `API.md`, `Widget.action` row: "one that exits (`sys.exit()`, any code) or raises any exception ends the tap as an
  error". `KeyboardInterrupt` is an exception, and a Stop or the run's time-out raised into the handler ends the run
  `interrupted` ("Stopped at ..." in the app, "Took too long" in the widget's Activity), not as the script's error.
  Suggest "raises any exception other than a Stop or the time-out".
- `how-it-works/python-run.md`: "When a widget button's code, or the code that draws the widget, stops the script or
  fails, that run ends as the script's error". "Stops the script" reads to a non-engineer as pressing Stop, which ends
  the run as stopped, not as an error. Suggest "ends the script itself (sys.exit)". The same sentence says "the console
  shows the line that stopped it"; for a tap that runs inside the widget there is no console in front of the person,
  so the sentence should name where that run's error shows.

**N1 (Nit, contract history order):** the v5.13 row is above v5.12 in the version table; every other row is in
ascending order. Move it below v5.12 when the L1 line touches the docs.

**N2 (Nit, contract s7 row):** "as the main code's are" covers it, but the row could say in so many words that a
`BaseExceptionGroup` holding a `SystemExit` or `KeyboardInterrupt` is filed by the group's type (`error`), not as
`exit` or `interrupted`. Optional.

No Critical, High or Medium findings.
