Here is the shape of it. People who write Python on an iPhone or iPad already move code to and from a computer. They do it with git through Working Copy, with AirDrop, with iCloud Drive, with Google Drive. They complain about it rarely (section 6: 10 of 446 low reviews of six code apps), and when they do, the thing they reach for is git, not a browser. A web IDE is the brief's answer to that need; the reviews say the need is real but small, and that the cheapest first step is a phone app that sits well beside the tools people already use.

## 1. What the web IDE has to do (from the brief) and the gap it has to live with

Brief C8 (build-brief.md line 89): "Browser editor, Python in the browser, a widget preview, and sync with the phone." Stack line 182: "TypeScript, the Monaco editor, and Pyodide for running Python in the browser." L14's constraint: "Browsers can't call iOS APIs or render SwiftUI." Its done test (line 193): "The web IDE can edit, preview and sync a widget that then runs correctly on the phone."

Three gaps sit between the web and the phone, and each option below closes some of them:

1. **Python version.** Pyodide's newest release is 314.0.7 (release asset list, `pyodide_release`, published 2026-09-14). Its version 314.0.0 line says "Upgraded to Python 3.14.2" (`pyodide_changelog` line 202). The app runs CPython 3.15.1 (L13 item 6). A script using anything new in 3.15 runs on the phone and fails on the web. The Unreleased section of the changelog names no 3.15 upgrade.
2. **Device modules.** Our seven C2 modules (clipboard, files, notifications, http, location, pedometer, keychain) do not exist in a browser. Pyodide also changes the standard library: "The following modules can be imported, but are not functional due to the limitations of the WebAssembly VM" (`pyodide_constraints`), listing multiprocessing, threading and sockets; "SSL module is replaced with a stub implementation that does not use OpenSSL"; and network calls are "subject to the same limitations as any JavaScript network call", including being "blocked by CORS policies if the server doesn't serve them with the correct headers". A widget that calls an API with no CORS headers works on the phone and fails on the web.
3. **Rendering.** The view tree (viewtree.schema.json, "pywidget view tree, version 1"; pywidget_ui `LIBRARY_VERSION = "0.3.0"`) has 22 node kinds and 37 modifiers (counted from the schema by script). On the phone SwiftUI draws it; on the web we must draw it ourselves. Two parts of the schema point at Apple-only material: `imageSource` kind `symbol` (SF Symbols) and `fontDesign` (default, rounded, serif, monospaced, display; the schema's own note names New York and SF Pro Rounded). Apple's licences for SF Symbols and the SF fonts limit them to Apple platforms **[recalled; person read]**, so a web renderer may not be allowed to ship the glyphs at all.

## 3. Pyodide and the mock device layer, in more detail

- **What runs unchanged.** pywidget_ui imports only base64, copy, datetime, json, math, os, sys (grep of `pywidget/python/pywidget_ui/*.py`), all present in Pyodide, so the same DSL code builds the same view-tree JSON on both sides. L17 already plans its block compiler in Python "built from `ast` nodes" to share it with the web through Pyodide (L17 line 33). The C2 host stubs are pure Python written for 3.9 and later (C2 s10), so they should load in Pyodide as a wheel; nobody has tried it.
- **The web can show what the phone hides.** The stubs encode the C2 context matrix: a background widget run gets `app_cache` locations, no prompts in widget runs, keychain locked before first unlock. A web context switch (app, widget, Shortcut; locked, unlocked; permission granted or not) lets a user see what their widget does at 3 a.m. on a locked phone. That is hard to stage on a real phone and could be the web IDE's own reason to exist, not a weaker copy of the app.
- **Time limits.** On the phone a widget run has `budget_s` and the stop <span title="Our grade scale, nine steps: D, D+, C-, C, C+, B-, B, B+, A. An idea&#x27;s ladder is the letter it reaches before any cap.">ladder</span> (ADR-007). In the browser, interrupts need a worker ("you must be using Pyodide in a webworker") and a SharedArrayBuffer, so "your server must set appropriate security headers" (`pyodide_interrupt`). With headers: same KeyboardInterrupt behaviour as the phone's first rung. Without: terminate the worker. The Unreleased changelog adds "a `maxMemoryBytes` option" to <span title="A measured fact that holds a grade below a letter, however good the rest is.">cap</span> the heap; when it ships, the web can mimic the extension's memory limit (L3).
- **Packages.** micropip installs "Any pure Python package with a wheel available on PyPi" (`pyodide_readme`); that matches what L13 allows on the phone for pure-Python packages, but native packages differ on each side (Pyodide's own builds against our cp315/abi3 wheels). W1 must say which.
- **Same tools as the app.** jedi and pyflakes are pure Python and already GO in the app (ide-tooling.md); running them in the worker keeps completion and lint identical on both sides. Unmeasured in Pyodide.
- **Fixtures.** Recorded sensor runs from the phone (L1) become JSON the web replays through `feed_location` and `feed_steps`. A recorded run is the user's own location and step history: it stays on their device or their own sync channel, never ours.

## 4. The renderer and its proof

- **Scope**: 22 node kinds (VStack ... `When`), 37 modifiers, 9 widget families, 7 environment keys, 17 schema definitions. The schema's sorted-keys rule (L4 line 50) means web and phone can diff the same document byte for byte before drawing.
- **Proof**: L4 line 205 sets one fixture suite for both renderers and says L14's pixel-diff runs on it. Today 12 JSON fixtures sit under `pywidget/tests/` (fixtures, a11y/fixtures, bridge/fixtures); the renderer suite needs many more, one per node kind and modifier at least. Harness: Simulator PNG from the Swift renderer, Playwright WebKit PNG from R1, pixelmatch diff, a per-fixture tolerance, and a report naming the node that drifts. Runs on the Mac mini; costs nothing.
- **Widget sizes**: Apple's size tables are on a barred host. Take the point sizes per family and device from Simulator renders instead (a measurement we own), and record them as fixtures.
- **SF Symbols and fonts**: the open legal question in this lane. Until a person reads Apple's licences, R1 draws a symbol as a labelled box and W1 says the symbol is shown on the device only. If the licence forbids web use, P2 (phone as preview) is the only exact preview of a widget that uses symbols.

## 5. Privacy and law (Commandment 6)

- **Static web IDE with no sync (P1 + R1 + S4)**: user code never leaves the browser. We still serve pages, so the host keeps access logs with IP addresses, which are personal data under GDPR **[recalled: CJEU, Breyer, 2016]**: the website needs a privacy notice. Self-host Pyodide and fonts so no third party sees visitors.
- **CloudKit JS (S1)**: if Apple's documentation confirms the developer cannot read the private database, user code stays between the user and Apple. Our page loads Apple's script and the user signs in to Apple on it **[recalled]**; a person reads Apple's CloudKit and web-services terms before we rely on this.
- **Own backend (S2)**: storing user code makes us a GDPR controller for EU users **[recalled, all of this list]**: a lawful basis (contract, Art. 6(1)(b)), a notice (Art. 13), access, export and erasure on request (Arts. 15, 17, 20), a processor agreement with the host (Art. 28), security (Art. 32), breach notice within 72 hours (Art. 33), and transfer rules if EU data sits on US servers (Chapter V). CCPA applies to for-profit businesses above its thresholds (annual revenue over a dollar threshold near $25 million, or the personal information of 100,000 or more consumers or households, or half of revenue from selling or sharing it); we are far below, but California users still expect deletion. The App Store side: account deletion in the app (5.1.1(v), p. 43, quoted in row S2); and if we add a third-party sign-in, Guideline 4.8 (p. 40) wants "another login service" that, among its conditions, "limits data collection to the user's name and email address" and "allows users to keep their email address private". A legal read by a person is required before S2; it is not desk work.
- **Guideline 2.5.2 and code moving to the phone**: L6 row 143 rates "Website code editor syncing to the phone" Low-Medium when it is the user's own code moved through the user's own iCloud Drive or sync, with "no server-pushed code". S1, S3 and S4 fit that framing; a server of ours that pushes code into the app is the riskier shape.

## 7. How a web companion could earn

- **L11 option A1** puts "web IDE and sync when Phase 3 lands" in the Pro tier (L11 line 60). The question is how Pro gets enforced on a web page.
- **A static page cannot check a purchase.** The Pro purchase is a StoreKit 2 entitlement the phone reads on the device (privacy-label.md condition 3). A web page without our server has no trusted way to know it; anything it checks, the visitor can edit. Checking on the web needs a server and the App Store Server API **[recalled]**, which brings S2's costs and duties.
- **So enforce on the phone.** Guideline 3.1.3(b) (p. 27) lets apps "allow users to access content, subscriptions, or features they have acquired in your app on other platforms or your web site ... provided those items are also available as in-app purchases within the app". It does not force a web checkout, and a web checkout would mean payments, an account and a payment processor: the Investors' (Commandment 6). The clean shape: the web IDE is free to write, run (P1) and preview (R1); the things that cross to the phone (sync into the app, phone-as-preview, sending a widget to the Home Screen) are Pro features the **app** unlocks with its own StoreKit entitlement. No web payment, no server.
- **The web as the front door.** A free, no-install page where anyone can try a widget in the browser, with a live preview is the one channel where the product can be shown working before anyone downloads it. It is also what a web search for Python widgets on iPhone could land on. That earns by installs, not by sales on the page. Unmeasured: no search-volume or conversion figure was read for this lane.
- **Weight of evidence**: thin. Section 6 found 10 desk-bridge mentions in 446 low reviews; packages and abandonment are far louder. I would not plan Day-30 money on a web companion. Phase 3 sits after <span title="Our arithmetic estimate of what the idea would earn by day 30 (the $200 deadline) or day 90. It never raises a grade.">Day 30</span> in ADR-001 anyway.

## 8. Desk recommendation (for the ADR; not a decision)

1. **Phase 3a, static and serverless**: CodeMirror 6 or Monaco (E1/E2: Monaco is the brief's; its README answers "Is the editor supported in mobile browsers or mobile web app frameworks? No.", which is acceptable for a desktop-only page because iPad and iPhone users have the app), Pyodide 314.x in a worker with our C2 stubs (P1), the HTML renderer with the pixel-diff harness (R1, R2), warnings (W1), browser storage and file import/export (S4). Hosted on a static host that sets cross-origin isolation headers (H2, Investors). No user code reaches us.
2. **Phase 3b, sync through the user's own cloud**: CloudKit JS private database (S1), after a person reads Apple's CloudKit JS and private-database terms and the membership is active. S3 (git) as the developer path. Phone-as-preview (P2) over S1.
3. **No own backend for sync.** Build a server only when the marketplace (Phase 4, ADR-006) needs one anyway, and then decide whether sync moves onto it.
4. **Before any of it, in the app**: clean opening of projects from Files locations and working relative paths (section 6), which answers most of the desk-bridge reviews at almost no cost.

## 9. Open questions

1. **Apple's SF Symbols and SF font licences** (person read, barred host): may a web page draw symbols or ship the fonts? Decides R1's fidelity and whether P2 is the only exact preview.
2. **CloudKit JS** (person read): is it still maintained, what sign-in does a web user see, can the developer read a private database, and what are the web quotas and terms? Decides S1.
3. **Hosting**: does a free web companion to a paid app count as "commercial software as a service" under GitHub's Pages limits? Which static host sets COOP/COEP headers at no cost, and on what terms? The Investors' (account, possibly spend).
