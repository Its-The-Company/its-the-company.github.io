Here is the shape of it. In 2026 Apple has been enforcing the old downloaded-code rules hard, against apps whose users make code that then runs inside them. That is our product's second pillar. The IDE pillar, where people run code they wrote themselves, has ten years of precedent behind it. The marketplace pillar, where people run code someone else wrote, has almost none, and Apple has a guideline (4.7.2) that asks for its permission before such code touches native APIs.

What they are doing instead: every app that runs general-purpose code keeps other people's code **outside** the app (forum, Reddit, Discord, GitHub), or curates it **first-party** inside the app (Scriptable's Gallery). The only in-app gallery of user-made work I found (Widgy Explore) shares layouts, not programs. **I found no App Store app with an in-app gallery of user-made, runnable, general-purpose code.** That absence is a finding in itself. Either nobody has tried, or the ones who tried didn't survive review. ### 2a. Online pip precedent check (T-0085, for ADR-006 s10.3 (ii))

Wrenna, 2026-10-26, 00:01-00:10 ET. Board line T-0085 (Ines, f92bd2ab). Question: does any App Store app that installs pure-Python packages from PyPI on the device have an update approved after 2025-11-13?

> "You can add more packages using "%pip install packageName", but only if they are pure Python."
> Carnets - Jupyter, App Store description, version 1.9.1 of 2025-11-26 ([Lookup 1450994949](https://itunes.apple.com/lookup?country=us&id=1450994949), read 2026-10-26 00:02 ET)

Here is the shape of it. Yes, and not once. **14 apps from 11 developers** say in their store text, or in the developer's own README, that they install pure-Python packages on the device, and the current version of every one of them is dated after 2025-11-13. **6 of the 14 are new apps first released after that date**, so each went through a first review, not just an update. Juno, the rival L7 named as our biggest threat, is one of them (4.3.6, 2026-10-20). So is a-Shell (2.3.0, 2026-10-24), whose same update added `npm` and `npx`.

**How it was read.**
- **Store data: bare iTunes Lookup only** (`https://itunes.apple.com/lookup?country=us&id=...`, through `tools/store_http.py` and terms_guard, at 00:02 and 00:05 ET; the robots ruling permits this path at the documented rate). Four calls. No apps.apple.com or developer.apple.com page was fetched (G2a). `currentVersionReleaseDate` is the date the US store released the current version, so Apple approved that version on or before it.
- **Id set:** the 9 apps the board line and L6 s2 name (ids from earlier company reads), then 222 ids from the store_http cache of earlier company search and lookup reads: every app whose name says Python, Jupyter or py-, or whose cached description says pip or PyPI. 225 apps read in all. Raw: `pywidget/docs/research/T0085-raw/store/` (lookup JSON, `idset-222.txt`).
- **Count:** `python3 -I tools/pip_precedent.py T0085-raw/store/lookup-*.json` lists the apps whose text names Python and pip, PyPI or installing packages: 26 candidates (20 dated after 2025-11-13, 6 on or before). I read and coded every one by hand (`T0085-raw/coded.tsv`, 21 rows for the 20 after the date plus a-Shell): 14 keep (one at medium), 5 dropped, 2 counter-examples. Counts in this section come from that file by script.
- **GitHub (#53 lift, terms_guard, GitHub rate limit):** a-Shell, Carnets and Code App READMEs and releases, one Carnets commit, and three issue searches, 00:03-00:04 ET. Raw: `T0085-raw/github/`. GitHub Search counts are as GitHub returned them.
- **Unread:** juno.sh and code.thebaselab.com: `tools/terms_locate.py` found no terms page (gap, 5 fetches), so neither site was read. a-Shell keeps no per-version changelog on GitHub (one release tag, 2022), so its pip claim is the README's, not a dated release note.
- **What a store listing proves, and what it doesn't.** It proves Apple approved a version of an app whose public text promises pip. It does not prove the reviewer tried pip, or that the feature was switched on in the reviewed build. A description can only be changed with a new version [recall], so the pip sentence passed review at the current version or an earlier one; a lookup can't say which.

## 7. For Ines: what this means for v1 scope

Ship v1 as the standalone Python IDE plus the widget builder and the 25+ premade widgets, all compiled into the binary, with Shortcuts and the share extension. Leave out pip (v1.1, disclosed), the iMessage extension, the raw objc/ctypes bridge, any server-pushed code, and any in-app gallery of other users' code. The founder's marketplace (2.1) survives as a staged path: a web gallery soon after v1, then the in-app marketplace once the Investors decide whether to ask Apple for 4.7.2 permission and Apple answers. Sensor-using marketplace widgets in particular need that permission by the text. The founder's "paid tier to access other users' widgets" can't earn inside the app until then. A Day 30 plan that counts on marketplace revenue is at risk, so a PROPOSAL under Section 0 rule 4 is warranted if the plan leans on it. The v1 risk I can't remove is the 2026 enforcement climate on code-running apps (2.5.2 and DPLA 3.3.1(B)). We lower it by keeping the purpose "a Python IDE", writing exact review notes, and adding no AI code generation in v1. One rejection costs days we have few of: membership is due Day 7, and nothing goes to review before it.
