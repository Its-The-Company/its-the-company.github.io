## Verdict: PASS with findings

The code does what its header says. In an App Store build it does nothing: `record` and `recordShortcutReload` return at
`LaneRestBench.records`, a compile-time `false` outside the gate build and the forced Simulator run
(LaneRestBench.swift:18-22). MeasurementExport, the only way the file leaves the App Group, is inside
`#if PYWIDGET_LANE_GATE || DEBUG`. SensorProbe.swift itself is compiled into every build, as LaneRestBench.swift is. It is
inert there, it imports only Foundation and UIKit, and it uses no API that needs a purpose string, an entitlement or a
privacy-manifest reason (UIDevice battery, ProcessInfo power and thermal, a file read). Nothing leaves the phone unless an
Investor taps Export measurements and picks a share target.

Readings. Battery: `isBatteryMonitoringEnabled` is turned on for the read and put back with `defer`, all on the main
actor, where UIDevice belongs. A level of -1 becomes null, never 0. No other code in the app or the extension uses
battery monitoring, so putting it back races nothing. Low Power Mode and thermal state are read directly; unknown future
cases get a name, not a crash. Lock: a file written once with complete protection, then opened. "unreadable" is the locked
case, and failures are named by domain and code (but see M1 and L2). Threading: `record` hops to the main actor once per
call. ExtensionLane.swift has no main-actor or main-queue use, so the hop should not wait on a script. The intent's own run
starts only after the row is written. Writes go through LaneRestBench's single `O_APPEND` write, so rows from the app and
the extension do not interleave.

Privacy (Commandment 6). Each row holds the step, process name, bundle id, pid, seconds since process start, battery
level and state, Low Power Mode, thermal state, the lock outcome, the `not_probed` list and a timestamp. None of these is
personal content. The test pins the key set, so a step count or a place cannot be added without a red test. The
shortcut_reload row is the step and the time only. That is what the question needs and no more.

HealthKit ruling (T-4841): followed. s8 item 4 has the ruling's words exactly, and SensorProbe's header cites the
decision file. No target has HealthKit: no import, entitlement, capability or `NSHealth*` string in any plist,
entitlements file, project.yml or Swift source at 6401b148 (grep, Vendor and tests excluded). "health" appears only as a
label in `not_probed`.

Tests. Row shape, null battery, once per step per process, rows appended and kept, every Shortcuts reload as a row, the
lock check's four outcomes on the Simulator, state names, and battery monitoring put back are all tested, and the export
test now carries the sensor file through `collect` and the manifest. What no test reaches is the part the device answer
depends on, and the part that keeps App Store builds silent (M1, M2).

## Findings

### M1. The lock answer rests on one flag that no test can see (T-5058)

- Where: `ios/Shared/SensorProbe.swift:61`, `options: [.atomic, .completeFileProtection]`.
- The Simulator has no data protection and reports no protection class (DeviceModulesTests.swift:549-550), so every
  Simulator test passes with or without this flag. The combined mutant without it passed the whole unit target. On a phone, a file without it takes the App Group's default
  class (complete until first unlock, recalled), so it would read "readable" while the phone is locked. T-4840 would then
  write "the extension reads protected files while locked" into s8. That is a wrong device answer, it could only be
  caught on a later build, and it is the one answer from this probe that decides product behaviour.
- Fix: make the row carry its own evidence. After the write or the read, add the file's class to the row
  (`attributesOfItem(atPath:)[.protectionKey]`, as a field such as `"protection": "complete"`, null where the platform
  does not report one), so the device export shows the class the answer was read under. In the unit test, name the write
  options as a constant (`lockProbeOptions`) and assert it contains `.completeFileProtection`; a test can see that even
  though the Simulator cannot enforce it.

### M2. Nothing tests that App Store builds stay silent, or that the three call sites exist (T-5059)

- Where: `ios/Shared/SensorProbe.swift:133` and `:141` (`guard LaneRestBench.records, ...`); the call sites
  `ios/Widget/PyWidget.swift:44`, `ios/Shared/RefreshWidgetIntent.swift:31` and `ios/Shared/RefreshWidgetsIntent.swift:25`.
- The combined mutant without both guards and all three call sites passed the whole unit
  target, 2084 tests. With the guards gone, every App Store build would write a battery, thermal and lock row to the App Group on
  every extension process and every Shortcuts reload. That data would sit on customers' phones with no feature using it,
  which is what Commandment 6 and ADR-001 3.2 rule out. With a call site gone, the gate build ships, the Investors run
  their session, and the export comes back with `sensors.jsonl` under "missing": a TestFlight round lost on a line nobody
  noticed was deleted. test_lane_gate_flag.py guards gate-only UI (RowTests) and the gate's spelling, not these guards.
  LaneRestBenchTests pins LaneRestBench's own call site, but not this one.
- Fix: give `record` and `recordShortcutReload` the gate and folder as parameters, defaulting to `LaneRestBench.records`
  and `WidgetFolder.appGroup`. Test that with `records: false` a call writes nothing and creates no file. Add a source
  test, next to `testGetTimelineTakesTheReadingFirst`, that requires exactly the three call sites, each as the first line
  of its function: `record("rest")` in the provider's `timeline(for:in:)`, `record("intent")` in RefreshWidgetIntent's
  `perform`, and `recordShortcutReload()` in RefreshWidgetsIntent's `perform`.

### L1. A "rest" row can be taken after a run, which the header says never happens (T-5060)

- Where: `ios/Shared/SensorProbe.swift:98` ("the first rest row is the process at rest, never one after a run"); s8
  "Added".
- On iOS 18-26 the refresh button's intent can run in the extension (RefreshWidgetIntent.swift:7). If a tap is a fresh
  extension process's first event, `intent` is taken, RefreshTap.run runs the script, and then the reload WidgetKit makes
  calls getTimeline in the same process. `rest` is taken there for the first time, after a run. The row carries pid and
  `since_process_start_s`, so a careful reader can sort it out, but T-4840's reading steps do not ask for that, and
  thermal state after a run is not the state at rest.
- Fix: when `intent` is taken first in a process, either mark `rest` taken too, or write `"after": ["intent"]` in the
  later row. Add a test that takes `intent` then `rest` and checks which one you chose.

### L2. The lock check has two outcomes the reading steps do not cover (T-5060)

- Where: `ios/Shared/SensorProbe.swift:56-68`; s8 "What reading it answers" (L3-runtime-spike.md:112); T-4840's line.
- "created" carries no lock answer, and on a phone it is most likely the very first extension `rest` row of the install,
  the row T-4840 most wants. "not created: <domain> <code>" is what a first call on a locked phone gives if a file with
  complete protection cannot be made while locked (recalled, not checked). s8 and T-4840 read only "readable" against
  "unreadable", so the first row of a locked phone would be read as no answer, or misread.
- Fix: in the gate build, have the app make the probe file at launch, when the phone is unlocked because the app is in
  front, so the extension's first row reads a real answer. Have s8 (and T-4840's steps) say how "created" and
  "not created" are read.

### L3. A test comment promises a device read that no line now carries (T-5060)

- Where: `ios/Tests/DeviceModulesTests.swift:549-550`: "The device run (T-0011) reads it", meaning the location cache's
  protection class. T-0011 does not read it, and neither T-4824 nor T-4840 names it.
- Fix: add it to T-4824's location item (one `protectionKey` read of the cache file, written to the row), or change the
  comment to say where it is read.

## Notes (no work)

- N1. The ruling's "What it changes" says T-0011 measures pedometer, motion activity, CMSensorRecorder, battery and
  location. This code measures battery, power, thermal and lock only. The rest is specified in s8 items 1-3 and carried
  by T-4824 (with the extension's own purpose strings first), and the device reading is T-4840. That split is sound. T-0011's
  board line should not be ticked as "measured" before those two are done.
- N2. SensorProbe's code and strings are in the App Store binary, inert, as LaneRestBench's are (accepted in my review of
  T-2851). Wrapping it in the gate condition would also take it out of the Debug unit tests, so I would leave it as it is.
  If the Release binary check (T-4688's M1 shape) is ever extended, `sensors-lock-probe` is a good string to look for.
- N3. Battery monitoring is a process-wide setting. Turning it on and back off within one main-actor turn is correct
  today. If the app ever uses battery for a feature, the read must not turn it off under that feature; the `was` restore
  already handles that.
