## T-1174: at most 100 detail files; pruneWidget's comment

What changed: `appendNeedsPrune` returns `details >= detailRows` (was `>`). The pruneWidget comment now says an added row is planned like any other row, so a row past 14 days is dropped and `added` is false. One unit boundary moved from 100 to 99 and from 101 to 100. The 103-append test now pins `Set(out) == newest 100`. There is one new store test, and the mutant file was updated.

Read against the code: at 100 detail files, pruneWidget plans with the new row included and no file for it yet, so it keeps the details of the newest 100 rows. That deletes the oldest detail (99 left), and the new detail makes 100. A run that ran nothing (`busy`, `deferred`, `oom_guard`) at 100 also prunes one, which matches "details for the newest 100 rows". The comment matches `planWidget`/`planRows`: the added line is appended to `lines` before the plan. No other comment or doc in pywidget/ still says 101 or "never dropped" for this code (grep).

I wrote my own driver, not the author's scratch: `xcrun swiftc` over the 23 Core sources plus a plain main.swift in /private/tmp/company-scratch/T-1660-idris. Result: 13 of 13 checks green. Finding 1 (Low, test gap; filed T-1664). The new test has both rows aged, so `keep` is empty. Any `added` rule that is false only on an empty keep passes it. The case that matters has fresh rows kept and the new row dropped by age. With the last mutant, `w.row` reads true and a detail file is written for a row that is not in runs.jsonl. That breaks recordWidgetRun's own promise, "a detail is never written without its row". The fix is one more test: 100 fresh rows, then a 15-day-old row, then `row == false`, no detail file, and 100 rows. The test only, no code change.

Still owed (Xcode): RunLogTests under xcodebuild, both the RunLogRetentionTests and the RunLogStoreTests classes. The tick says so too, and no open line held it, so T-1664 carries it (Checks: land:xc).

Observation, not filed: once a widget has 100 detail files, every append now goes through pruneWidget. That means a read of up to 1 MiB of runs.jsonl, a parse and one delete. Before, this happened on every second append. It is the price of the <span title="The worker who reads both graders and decides. The decision, a ruling, is one row in the rulings file.">chair</span>'s "never over 100", and I don't see a cheaper way that keeps it. The Xcode run is the place to time one append at 100 detail files in the extension.
