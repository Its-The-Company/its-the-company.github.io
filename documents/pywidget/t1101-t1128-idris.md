Reviewer: Idris (owner of T-0656, the Swift half that calls this module). Date 2026-11-02.
Read: `git show 871ebe4a` and the code: `pywidget/python/pywidget_tooling/editor.py`, `positions.py`,
`pywidget/tests/tooling/test_editor.py`, `mutants-t1101.json`, the project.yml phase, `install_packages.sh`,
`stdlib_cut.py`, `packages/manifest.toml`. I did not read the author's notes beyond the commit line.

## Verdict: FAIL (changes requested on the time budget; the rest is fix lines)

Every item of T-1101's done line is met and the suite is green. The call shapes match the prototype
(`tests/tooling/bridge.py`), plus `mode`, `reason` and `cancelled`. No bad input made either call raise.
The `sys.setprofile` hook itself is restored on every path I could drive. But the deadline it enforces
makes completion 3 to 6 times slower on the host, so the 100 ms target is out of reach in ordinary
cases. A module jedi has not seen yet never finishes at 400 ms, because each keystroke throws the work
away. And a deadline raised inside a <span title="The starting recipe a lane uses to look for ideas. G2, for example, starts from public datasets.">generator</span> finalizer is swallowed and does not come back (F1, F2).
I would not build T-0656's budget on this mechanism. The fix is small and mostly moves the timer to Swift.

**Measurement caveat.** The host's load average was 118 to 155 during every timing below, because other
agents had builds running. The absolute milliseconds are inflated. The bare-against-hooked ratios were
taken in the same process seconds apart, so they <span title="What keeps an idea below the top: the cap that applies to it now.">hold</span>. Device numbers still belong to T-0656's bench.

## Findings

### F1 (High): a deadline raised inside a finalizer is swallowed, and the call then runs unbounded
`editor.py:101-105`. The hook calls `sys.setprofile(self.prev)` and then raises `_OverBudget`. CPython also
unsets a profile function that raises: `hook_after_caught_raise` reads `None` on both interpreters. So the
first raise removes the deadline for good. If that raise lands in a frame whose exception is discarded, the
budget is gone and nothing stops jedi or pyflakes. Generator and genexpr finalizers discard exceptions, and
both tools are full of generators.

*Failure scenario, reproduced.* `/tmp/t1128/probe3.py` runs a 300 ms loop that drops a generator with a
`finally:` on each pass, under `_Deadline(10)`. On 3.13.18, 13 of 20 runs went the full 300 ms with
"Exception ignored ... _OverBudget" on stderr. On 3.9.6 the same swallow appeared inside jedi itself, during
a budget run: "Exception ignored in: <generator object ClassMixin.py__mro__> ... editor.py line 105
raise _OverBudget()". The hook can only raise inside a finalizer while it is still installed, so that was
the first and only raise of the call. A pathological file then blocks the editor's Python thread with no
limit, which is the one case the budget exists for.

### F2 (High): the hook costs 3-6x, and an unseen module never completes at 400 ms (the 100 ms question)
`editor.py:73-74, 89-114`. The docstring at :49-52 says the hook costs "about twice". A Python-level
profile function runs on every call, return, c_call and c_return event, whatever it does inside, and I
measured warm repeats at 3 to 6 times:

At `budget_ms` 100, `os.pa` fell back 5 of 5 times on 3.9 and `s.st` 4 of 5 times on 3.13. With the
default 400, the G1 file (`gen_bench_file.build()` plus `os.pa`) fell back 4 of 4 on 3.9 and 1 of 4 on
3.13. `diagnostics()` on it came back `syntax_only`/`budget` 4 of 4 on 3.9, so the gate file got no
pyflakes at all. Those calls also took 455 to 886 ms against a 400 ms budget.

*Livelock, reproduced.* An abort throws jedi's inference away, so a module whose first inference costs
more than the budget never finishes. For `import asyncio as m` / `m.` at the default 400 ms, 5 keystrokes
in a row gave 5 fallbacks of 400 ms each on both interpreters. On 3.9, `xml.dom.minidom` and
`http.client` did the same. The user never sees jedi's answer for that module, and each keystroke still
holds the Python thread for 400 ms. (After the aborts the answers were unchanged. Aborts at 8 budgets
from 0.5 to 21 ms on 4 probes left jedi's later results identical to the baseline, so there is no
corruption, only lost work.)

*So: 400 against 100.* 400 is not a 100 ms answer, and with the hook the default would not hold 100 ms
even for warm, common completions. Bare jedi is close: warm `os.pa` took 25-32 ms on 3.13 and the G1 file
38-58 ms after its first call.

*Fix (Python half, T-1143).*
1. Stop installing the hook by default. Add `OverBudget(BaseException)` beside `Cancelled`, for Swift to
   deliver with `PyThreadState_SetAsyncExc` when its own timer passes `budget_ms`. That timer costs nothing
   per event.
2. Swift re-sends every 50 ms until the call returns, because an async exception can be swallowed by a
   finalizer too (F4).
3. Map `OverBudget` to the fallback with reason "budget".
4. Add `prime(req)`: the same jedi call with no budget, for Swift to run at idle on the same queue after a
   "budget" fallback, so parso's and jedi's caches fill and the next keystroke is warm. That removes the
   livelock.
5. Keep `_Deadline` only as an opt-in for host tests.

The Swift watchdog and the idle prime are mine, in T-0656.

### F3 (Medium): SyntaxErrors raised at compile time come back as warnings, or as a clean file
`editor.py:330-338`. `compile(..., flags=ast.PyCF_ONLY_AST)` only parses. The compiler and symtable raise
more SyntaxErrors than the parser does.

*Failure scenario, reproduced on both interpreters.* `nonlocal x` at module level returns `items: []`,
mode `pyflakes`, so the editor shows a clean file and Run fails with "nonlocal declaration not allowed at
module level". `break`, `continue`, `return 1` and `yield 1` at top level, `await x` in a plain def, and
`def f(a, a)` all come back as pyflakes warnings (BreakOutsideLoop, ContinueOutsideLoop,
ReturnOutsideFunction, YieldOutsideFunction, UndefinedName, DuplicateArgument). Each of them is a
SyntaxError when run. That contradicts the docstring at :34: severity "error" is the SyntaxError.

*Fix (T-1144).* `compile(text, "<editor>", "exec", dont_inherit=True)`, which builds bytecode and runs
nothing, inside `warnings.catch_warnings()` with SyntaxWarning ignored. On the 2,000-line file it took
9.3-9.8 ms against 9.5-10.7 ms for the AST-only parse: no measurable cost. Add a test with those 7 cases.

### F4 (Medium): the cancel contract leaves out two outcomes Swift has to handle
`editor.py:54-57`. The docstring says a `Cancelled` is caught and returned as `{"cancelled": true}`. My
probe fired `Cancelled` at random into a worker thread that loops `diagnostics()`, using
`PyThreadState_SetAsyncExc` as Swift will. Two other outcomes showed up.

- *Swallowed.* On 3.9 a `Cancelled` arrived inside `_hook`, in a pyflakes genexpr finalizer
  (`checker.py:795`), and was printed as "Exception ignored". The call returned a normal answer.
- *Arrives after the return.* On 3.9, 1 of 199 escaped `diagnostics()`. On 3.13 one landed on the
  caller's next line, `sys.getprofile()`, and killed the worker thread.

*Failure scenario.* If Swift fires a cancel just as a call returns, the pending exception lands on
whatever Python runs next on that thread state. That could be the next `complete()`, which then answers
"cancelled" for the fresh request, or a user's script.

*Fix (docstring, T-1145; Swift, T-0656).* State three rules:
1. Swift drops stale answers by request id, never by the `cancelled` flag.
2. Right after each call returns, while it still holds the GIL, Swift clears any pending exception with
   `PyThreadState_SetAsyncExc(tid, NULL)`.
3. A cancel is best effort.

### F5 (Medium): `insert` is wrong on a case-insensitive match
`editor.py:256-261`. jedi matches case-insensitively by default, and `c.complete` is the label minus the
typed length.

*Failure scenario, reproduced.* For `import os\nos.PA` the item is label `path`, insert `th`, replace
cols 3 to 5. A UI that appends `insert` writes `os.PAth`. The `replace` span with the `label` is right,
and so are the dict-key case (label `"alpha"`, replace cols 2 to 5) and the path case (label `tmp/`,
replace cols 7 to 9).

*Fix (T-1144).* Set `insert` only when the typed text, `src[start_cp:cp]`, is an exact prefix of the
label. Otherwise leave it out, and have the docstring say "replace + label is authoritative". Add the
`os.PA` test. T-0656 will use replace + label either way.

### F6 (Low): the fallback imports modules, contrary to its own comment
`editor.py:196-203`. The comment says "loaded only: importing runs code". `dir(mod)` followed by
`getattr` runs a module's lazy `__getattr__`.

*Failure scenario, reproduced on both interpreters.* After `import concurrent.futures`, the fallback for
`cf.Pro` imports `multiprocessing` (False before, True after). With `multiprocessing` unavailable,
`complete()` returned no items and reason "error: ModuleNotFoundError". The never-raises promise held only
through the outer handler. multiprocessing is `shipped` in stdlib-manifest.json, so on a device this runs
module code on a keystroke.

*Fix (T-1144).* Read `vars(mod)` (the module's `__dict__`) instead of `dir` + `getattr`. Add a test that
`multiprocessing` stays out of `sys.modules`.

### F7 (Low): line/col on the bridge, while positions.py prefers a document offset
`editor.py:11-15, 240`; `positions.py:17-19`. positions.py says the preferred bridge position is a
whole-document UTF-16 offset, because "the editor's idea of a line break never has to agree with the
tokenizer's". `complete()` takes only line/col.

*Failure scenario.* NSString's line ranges also break on U+2028, U+2029 and U+0085, and Python does not.
If a pasted U+2028 sits above the caret and Swift counts lines with NSString, every later line is off by
one and the completions belong to the wrong line.

*Fix (T-1145).* Accept an optional `"offset"` (UTF-16, document) in `complete()`, through the existing
`offset16_to_position`. Optionally return `offset`/`end_offset` on diagnostics items. Until then T-0656
counts only `\r\n`, `\r` and `\n`.

### F8 (Low): three behaviours with no test (M1-M3 survived)
- `MAX_ITEMS` (M1). `os.` gives jedi 378 items. The call returns 200, which is 25.6 KB of response on every
  keystroke, and no test holds the cap.
- `budget_ms: 0` (M2). With `b < 0` it means "always fall back", and nothing notices.
- `warm()` (M3). With jedi broken it reports True, and no test notices.

*Fix (T-1144).* One test each: `len(items) <= MAX_ITEMS` for `os.`; budget 0 gives the default; `warm()` is
False when `jedi.Script` raises.

### Info
- I1, profile restore: holds on every path I drove. 4,073 calls under random async `Cancelled` (3,136 on
  3.9, 937 on 3.13) left 0 stale hooks. `test_profile_hook_is_restored` covers the over-budget and normal
  paths. `sys.setprofile` is per thread, so a concurrent caller on another thread is not affected. The
  remaining leak window needs two async exceptions inside `__exit__`, so I rate it below Low.
- I2, thread safety: jedi's and parso's caches and `_ENV`/`_WARM` are process-global and jedi is not
  thread-safe. The docstring should say "warm, complete and diagnostics on one serial queue" (T-1145).
  T-0656 will do that.
- I3, the install phase (`project.yml:129-138`) is sound. It copies only `*.py`, so no `__pycache__`, and
  `InstallPhase` runs the phase's own text and imports from the result. It cannot break the stdlib size
  check: `stdlib_cut.py:287-290` measures only `python/lib` and `Frameworks/`, and `Runtime/` is outside
  both. jedi, parso and pyflakes are `tier = "pure"` in `packages/manifest.toml`, so
  `install_packages.sh` stages them into `app_packages/` under the bundle root, as the phase comment says,
  and not into `Runtime/`. The acknowledgements walk only matches licence file names, so it is not
  affected. One thread for T-0656: `runner.py:286` puts `app_packages` on `sys.path` only for an "app" <span title="One numbered piece of research into one area of ideas. Each lane has its own file.">lane</span>
  run, so the editor's calls must set up `Runtime/` and `app_packages` themselves.
- I4: the docstring's fallback kinds (:25, "builtin") don't match the code, which uses "class" and
  "function" for builtins. Fold into T-1145.
