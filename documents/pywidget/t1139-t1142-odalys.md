## Checked against the chair line
1. Item 2, row keys: all 17 keys are in `RunRow.keys`, with the chair's types. An unknown key, or a known key holding the wrong type, goes to `extra` and is written back on a prune rewrite; an unknown trigger or outcome stays as text. `backgrounded` and `detail` are written only when true. Rows are named by `row`, and the detail file name comes only from a value that parses as a UUID, so a row's text never becomes a path. Pass.
2. Item 3, Swift the only writer: the commit adds no Python and no writer outside RunLogStore. The outcome mapping reads `bridge-outcome/1` (`duration_s`, the innermost `user` frame, the `syntax` position) and writes nothing back. Pass, apart from finding 1, which is about the numbers it reads.
3. Item 4, what is kept: `deferred`, `busy` and `oom_guard` get a row and no detail file; a console row is `kind=console` with no `file`, `line` or detail. Row, detail, then status run in that order in one hold of `widgets/<id>/state.lock`, and a detail is never written without its row (tested, and the seeded order mutants die). Pass.
4. Item 5, age: `maxAge` is 1,209,600 s (14 x 24 h); exactly 14 days stays and one second more goes (tested). A torn line or a `ts` this build can't read counts as past age. The prune is an atomic rewrite under the lock. On an append it runs only when the first row is past 14 days or the file would pass its <span title="A measured fact that holds a grade below a letter, however good the rest is.">cap</span>; otherwise the append is a single `O_APPEND` write (an inode test pins that). A torn last line is repaired before the next row. Pass.
5. Item 5, detail file: output keeps the last 16 KiB at a line start, else at a UTF-8 boundary, with `cut: true`. The error gets 8 KiB: the message whole, then the chain, `text` and frames trimmed from the outer end, and the innermost user frame is kept within the contract. The whole file stays under 24 KiB even when every byte needs escaping (tested). Pass; see finding 5.
6. Item 5, per widget and whole log: `runs.jsonl` is capped at 1 MiB with the oldest rows dropped, and `console.jsonl` at 512 KiB. At launch the oldest detail files across all widgets are deleted while `log/` is over 24 MiB, and the rows stay. A widget with no row inside 14 days loses its folder at the launch prune, and only then. Clear deletes `log/widgets/<id>/` only, under the lock. Pass, except finding 3 (100 vs 101 details).
7. The per-widget lock: every write and delete of a widget's files is inside `WidgetStateLock` on `widgets/<id>/state.lock`, with the bounded 0.5 s wait. A widget whose folder is gone is pruned without a lock, because there is nothing left to write it. The lock helper creates the lock file but never the folder, so a run for a deleted widget writes nothing (tested). Pass for the code; finding 2 is about the tests.
8. s5.12 12.8: the layout is `log/widgets/<id>/runs.jsonl` plus `out/<row>.json`, `duration_ms` comes from `duration_s`, `editor_save` is a trigger, `lane` is `app` or `widget`, and output is stored as `[stream, text]` pairs. Matches the table as the chair line amended it.

## Findings
1. Finding 1, held (High for T-1140, not reachable at this HEAD because nothing calls the store yet). Detail is kept out of this page (Commandment 42); the fix line carries it.
2. Finding 2 (Medium, test gap on a chair-line requirement). The launch prune's per-widget lock is not pinned by any test. Mutant O1 runs `pruneAll`'s per-widget prune without `state.lock`, and O2 runs the whole-log trim's deletes without it. Both survive the 55 tests. The code holds the lock today (a probe saw the busy widget skipped and left alone), but a later edit could drop it silently. Fix: hold `widgets/a/state.lock` with flock, run `pruneAll`, and assert `a` is in `busy` with its rows and folder untouched. Do the same for the trim with `log/` over 24 MiB. Add O1 and O2 to the mutants file.
3. Finding 3 (Low, bound). Between appends, a widget keeps 101 detail files. `appendNeedsPrune` counts `out/` before the new detail is written (`details > detailRows`), and a test pins 101 ("one over until the next append prunes"). The chair line says details are kept for the newest 100 rows, and the 101st row's detail can still be read through `detail()`. Fix: prune at `details >= detailRows` and pin 100. In the same file, `pruneWidget`'s comment says the row being added "is never dropped by age", but `planRows` ages it like any other line. Make the comment match the code, or the code match the comment, with one test.
4. Finding 4 (Low, test gap). In `readTail`, the branch for a window that starts on a line start is untested. Mutant O4 makes that branch keep nothing, and it survives. Only a file grown past its cap reaches this branch, but there the mutant would lose up to 1 MiB of rows. Fix: one test with a rows file whose byte before the read window is a newline, then add O4 to the mutants file.
5. Finding 5 (Low, judgement). A line-start cut can keep almost nothing. For one 20,000-byte line followed by `done\n`, the cutter keeps 5 bytes of the 16 KiB allowed (n=1 probe), so a script that prints one large JSON line loses all of it. The chair line says "cut at a line boundary", so the code meets the letter. Proposed fix: take the line start only when it keeps at least 8 KiB, else cut on the UTF-8 boundary. If Ines reads item 5 strictly, close it with a note.
