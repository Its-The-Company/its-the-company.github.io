**Verdict: CHANGES NEEDED before T-1140 wires launch recovery and the loop breaker.** The codec, the seven 7.2 row functions and the 7.1 row 4 badge match the spec, and I found nothing wrong in them. The recovery decision does what 02:40 item 3 says with the ids it gets. But the ids it gets are a counter that restarts every launch, so in practice it matches real <span title="A test written in advance. If it fires, we drop the idea.">kills</span> (finding 1). The loop breaker cannot get its inputs from the run rows as they are specified (finding 3). None of the findings is a security weakness, so nothing is held. Read from the commit (WidgetStatus.swift, WidgetStatusTests.swift, mutants-t1148.json), not from the notes.

## Measured (host only, scratch worktree at 186e9027; nothing planted in the company folder)
1. `swift test --filter WidgetStatusTests` in pywidget/ios/Core: 28 run, 0 failures. That is the baseline before any mutant.
2. `tools/mutation_check.py ... mutants-t1148.json --filter WidgetStatusTests`: 26 run, 26 killed. This matches the claim.
3. My own mutants, 3 run: `expired-sets-no-ts` killed. Two survived: `failure-keeps-deferred-since` (drop `s.deferredSince = nil` from `failed`) and `huge-number-reads-as-line` (drop `abs(d) < 1e15`). See finding 4.
4. Three probe tests of my own, each asserting what 02:40 asks: 3 run, 3 failures (findings 1-3). They are kept in my scratch folder and are not part of the suite.

## Checked against the spec (no finding)
1. **Codec.** A missing, unreadable or non-object file reads as no status. A known key of the wrong type reads as absent, and `true` never reads as a line. An unknown outcome stays as text and shows no badge. Unknown keys survive a rewrite. Output is sorted keys, and the same status gives the same bytes (n=7 bad-file cases, all nil).
2. **7.2 rows.** `ok` clears `failing_since`, the failure details and `deferred_since`. `error`, `timeout` (`TimeoutError`) and `stuck` (frame, no type) keep the streak's first failure. `expired` adds the run id and leaves the failure. `deferred` touches only `deferred_since` and keeps the first. `oom_guard` writes the outcome only. `killed` is a badge with no frame.
3. **02:40 item 3.** Every write starts from `carried(old)`, so `expired_runs` survives all seven writes (test c). The list is kept to 8, oldest dropped (test d), and a repeated id is listed once.
4. **02:40 items 1-2.** `recovery` reads list membership only, never `last_outcome`. `.writeNothing` returns nil inside the lock, so the file stays byte-identical (test a). `showsBadge` is display only, and the loop breaker reads rows only.
5. **7.1 row 4.** Badge for {error, timeout, stuck, killed} with a tree, and never without one (row 3 is the card). All 8 outcomes are tested.
6. **Lock.** `update` and `recover` go under `state.lock`. `recordExpiry` takes no lock, as amendment 3 item 1 says. Both are tested.

## Findings
1. **High. `expired_runs` matches across launches, so real background kills go uncounted.** Run ids come from `PyBridge.newRunID()` (a `UInt64` from 0 in each process), and the crash marker stores the same bare number (`CrashMarker.begin`, "run <n>"). The 17:15 line, item 2, says the same: "`run_id` stays Swift's per-launch counter". `expired_runs` keeps 8 ids across launches, and v1 has no drain to clear them. Take a widget whose run 1 expired in one launch. In a later launch its run 1 is killed for a real reason. Recovery finds "1" in the list and writes nothing: no badge, no count, never demoted. That is the failure 02:40 item 3 was written to prevent ("each new run has a new `run_id`, so the kill counts"). A widget that is first in its T2 batch gets the same low id every launch, so this is the common path, not an edge case. Probe P1 (expiry of "1", then recovery of a later launch's "1"): expected `.writeKilled`, got `.writeNothing` (n=1, deterministic). The tests use ids like "r", "r2" and "1".."9" within one imagined launch, so they cannot see it. Fix line T-1168.
2. **Medium. The expiration handler's unlocked write can be lost under a locked write.** `recordExpiry` reads, changes and renames with no lock, by design. A locked writer that read before it and writes after it drops the new id from `expired_runs`. Then the next launch counts and badges the kill that 02:40 item 1 says writes nothing. The likely writer is the stopped run's own sink. A related open question for T-1140: the stopped run comes back `interrupted`, and if the sink maps that to `timeout` per 7.2's table, it badges over `expired`. Probe P2 (an expiry landing inside an `update` <span title="What keeps an idea below the top: the cap that applies to it now.">hold</span> that then writes `ok`): expected `["r"]`, got `[]` (n=1). Both writers are in the app process, so an in-process mutex between `recordExpiry` and `updateHeld` closes it without a file lock at suspension. Fix line T-1169.
3. **Medium. The loop breaker's inputs cannot be read back from run rows.** `LoopBreaker.Run.afterExpiry` has no row key. RunRow's 17 keys (T-1139, 17:15 item 2) hold `backgrounded`, but nothing records that recovery matched the list. Once the streak is recomputed from `runs.jsonl`, the matched kill counts. `Run` also has no run identity. 5.3 has launch recovery record a stuck widget as `stuck` from the marker. If the batch already wrote a `stuck` row for that run, one stuck run gives two rows and a demotion. Probe P3 (ok, stuck, stuck): `.demote` (n=1). The mapping from RunRow's trigger words (8, plus 3 reserved) to `foreground`, `background` and `other` is not written anywhere either. Fix line T-1170.
4. **Low. Two test gaps.** No test shows that a failure clears `deferred_since` (mutant `failure-keeps-deferred-since` survived), and no test covers an out-of-range `line` (mutant `huge-number-reads-as-line` survived). Fix line T-1171.

## Note for the <span title="The worker who reads both graders and decides. The decision, a ruling, is one row in the rulings file.">chair</span> (no fix line)
- 7.1 lists `expired` and `oom_guard` as no-badge outcomes, and each overwrites `last_outcome`. A widget whose script is failing loses its badge after one expiry or memory skip, even though `failing_since` and `error_type` stay. That matches the spec as written. It may not be what Maren's states intend. I am raising it, not fixing it.
