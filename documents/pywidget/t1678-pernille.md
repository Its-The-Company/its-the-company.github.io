Reviewed: 184b2877d (T-1169/T-1170: status mutex, `launch` and `after_expiry` row keys, loop breaker counts a run once), 0cfa6404b (RunLogRecorder, T-1140 slice 1), 94f1203da (T-1669 slice 2: WidgetWriter, PyBridge marker, ConsoleModel). Read against ADR-007 (5.1 trigger table, 5.3, 7.2) and the T-1140 board line. Commandment 13 review: I saw the diffs and the code, not the author's reasoning.

**Verdict: no P1. Five P2s.** F1 to F4 change what the Activity screen and the loop breaker read, so they should land before a TestFlight build that carries the run log. F5 is missing tests. Seven P3 notes. No security finding, nothing held.

**Checked and sound.** I found no fault here:
- Lock order. `state.lock` comes first, then `WidgetStatusStore.writeLock`. `recordExpiry` takes only the mutex. The `change` closures in RunLogRecorder (`Self.status`, `WidgetStatus.recovery`, `self.row`) are pure and never call back into a store, so there is no wait cycle and no re-entry on the NSLock.
- Background-task assertion. `BackgroundHold.app` begins the task, runs a body that cannot throw, then ends it. `BackgroundTask.end` is guarded against a second call, so the expiration handler and the normal end can both run safely. The task is ended on every path.
- Coalesced refresh. `RunClaims` gives one row per run id, and the trigger comes from `RunInfo`, the newer request's. The stuck path logs `stuck` inside the <span title="What keeps an idea below the top: the cap that applies to it now.">hold</span>.
- Loop breaker. It dedupes by `launchRunID`, and the newest row decides. The marker's `launch` line matches `WidgetRun.launch` (both `LaunchRunID.thisLaunch`), so a batch `stuck` row and the recovery `killed` row for one run count once.
- File growth. `appendRow` <span title="A measured fact that holds a grade below a letter, however good the rest is.">caps</span> each file on every append (`widgetRowsBytes`, `consoleRowsBytes`, `details`), so growth stays bounded before the launch prune is wired (T-1677).

**Tests run.** I ran `swift test` in the core package, in a scratch copy made with git-archive from HEAD 608a30d30. RunLogRecorderTests: 11/0. The run-log, status and loop-breaker suites are green. The only failures are LinkRuleTests and ProjectManifestReaderTests. Their corpus files (cases.json, manifest fixtures) sit outside pywidget/ios, and my scratch copy did not extract them, so these failures are unrelated. I did not run Xcode, so the WidgetWriter, PyBridge and ConsoleModel tests are unexecuted by me. Idris reports PyWidgetTests 939/0.

## Findings

### F1. P2. A stuck run is re-recorded as `killed` at the next launch, against ADR-007 5.3
`pywidget/ios/Shared/RunLog/RunLogRecorder.swift:167-175` (recover), with `PyBridge.swift:892` (the marker stays while a run is stuck).
- **Failure.** A stuck run never returns, so its crash marker stays. WidgetWriter already wrote the `stuck` row and `last_outcome=stuck`. When the person quits and reopens the app (5.3's own remedy), `recover` writes a second row, `killed`, and `WidgetStatus.killed` overwrites `stuck` in status.json. 5.3 says: "the next launch finds the crash marker, records the stuck widget as `stuck` (not `killed`)". The person then sees two rows for one run. The second one carries the copy "closed while it ran, possibly out of memory" (or "iOS closed PyWidget in the background"), which is wrong for a script stuck in C that they quit themselves. T-1170's dedupe keeps the loop-breaker count right, but the row, the status and the copy are wrong.
- **Fix.** Have the marker say the run went stuck. PyBridge can append a `stuck` line when it reports `stuck`, the same way `noteBackground` appends `backgrounded`. Alternatively, `recover` can look up the widget's rows for a row with the same `launchRunID` and outcome `stuck`. In either case write a `stuck` row with the marker's frame if known (or no row, since the batch already wrote one) and leave status.json `stuck`. Test: a marker with the stuck line, plus an existing `stuck` row for L0:9, gives no `killed` row and keeps `last_outcome=stuck`.

### F2. P2. The Refresh Widgets intent (T3) is logged as trigger `intent`, so the loop breaker never counts it
`pywidget/ios/App/Bridge/WidgetWriter.swift:413` (`installAppWriter`, `trigger: .intent`), against `pywidget/ios/Shared/WidgetStatus.swift` `RunTrigger.loopBreakerTrigger`.
- **Failure.** RefreshWidgetsIntent is an AppShortcut with `openAppWhenRun = false`. Its only non-test use is `RunScriptIntents.swift:213`; no widget has a `Button(intent:)` for it. ADR-007 5.1 row T3 is exactly this case: a Shortcuts automation, in the app, with no scene. T-1170's own mapping says `shortcut` stands for "T3 and T4, App Intents in the app with no scene, usually from an automation", and maps `intent` (a widget's button, L2) to `.other`. So every row from the T3 path is `.other`. A script that is killed or goes stuck on every hourly automation is never demoted, which is the case 7.2's loop breaker exists for. The T-1669 line asked for "Refresh intent intent", so the spec and the code agree with each other and both disagree with the ADR.
- **Fix.** Pass `.shortcut` from `installAppWriter`. If someone wants `intent` kept for this path, Ines needs to rule that on the ADR first. Test: one WidgetWriterTests case asserting the row trigger from `WidgetRefresh.run()`.

### F3. P2. A save run that a console Run stops is logged as `error` and badges the widget
`pywidget/ios/App/Bridge/WidgetWriter.swift:194` (record runs for every run) with `:140` (`saveRuns.ended` is read only after `refresh` returns) and `SaveRuns.yield` (`bridge.stop`).
- **Failure.** When the person taps Run in the console while an `editor_save` widget run is in flight, `SaveRuns.yield` stops that run. It ends `interrupted` without a budget stop. `WidgetRunOutcome.map` turns that into `error`/`KeyboardInterrupt`, and `record` writes an error row and `last_outcome=error`, which is the error badge (7.1 row 4). The retry behind the console run clears it only after the console script finishes, and that can take minutes. 7.2 treats "a console run in progress" as `deferred` (no badge), and 5.3's principle is that our own scheduling never shows the person a fault.
- **Fix.** Inside `run`, before `record`, ask SaveRuns without consuming whether this run id was yielded. Add a `stoppedForConsole(runID)` that `ended` still consumes later. If it was, log `deferred` (`WidgetStatus.deferred`, `wants-run` kept) instead of the mapped error. Test: a yielded save run's row says `deferred` and status.json has no error.

### F4. P2. Launch recovery writes console rows for preview and Shortcut runs, under the wrong id
`pywidget/ios/Shared/RunLog/RunLogRecorder.swift:161-165` with `pywidget/ios/Shared/Bridge/PyBridge.swift` (marker begin: `widget:` only for `.widget`; `sourceName` is `url.path` for a file source).
- **Failure (a).** Every marker without a `widget` line becomes a console `killed` row. That includes `.preview` and `.shortcut` runs, not only console runs. 94f1203da's message and `testAPreviewMarkerNamesNoWidget` say "recovery never logs it". The test checks only the marker text, and the code does log it. A Shortcut run also gets a row only when it is killed, never when it finishes.
- **Failure (b).** The recovered row's `id` is `last.name`, which is `RunRequest.sourceName`. For a file run that is the absolute sandbox path (`[local folder]<uuid>/Documents/...`). The live console rows use `fileTitle` (the last path component, or `console`). One project therefore shows up under two ids, and the exported log carries the container path.
- **Fix.** Write the run's context into the marker (`context app|preview|shortcut`). In `recover`, write a console row only for `app`, and nothing for `preview` (and nothing for `shortcut` until it has live rows too). Use the last path component of the name as the id, matching `fileTitle`. Also drop `launch: last.launch ?? ""` (line 164): a marker without a launch line should give a row with no `launch`, not `"launch": ""`. Test: recover with a preview marker writes no row anywhere. Recover with a file console marker writes id `Trip.py`.

### F5. P2. The T-1169 "checked again under the mutex" lines and the launch prune call survive mutation
`pywidget/ios/Shared/RunLog/RunLogRecorder.swift:81`, `:173`, `:151`; `pywidget/ios/Tests/Core/RunLogRecorderTests.swift`.
- **Failure.** I planted three mutants in a scratch copy and ran `swift test --filter RunLogRecorderTests`. All three survived (11/0):
  - M1: line 81, `if expired || old?.expiredRuns.contains(mine) == true` changed to `if expired`. An expiry that lands after `prepare` then overwrites the expired status, which is the T-1169 race the comment says this line closes.
  - M2: line 173 deleted (the recovery decision re-read under the mutex).
  - M3: line 151, `r.pruned = false` without calling `pruneAll`. atLaunch never prunes, and no test notices. This one matters as soon as T-1677 wires atLaunch.
- **Fix.** `RunLogRecorder(container:observe:)` already exposes `Step`. Call `status.recordExpiry(id, runID: "L1:4", ...)` from `observe` at `.detail`, which runs after `prepare` and before the status write. Then assert that status.json keeps `expired_runs` and `last_outcome=expired` (<span title="A test written in advance. If it fires, we drop the idea.">kills</span> M1). Do the same with a marker run in `recover` (kills M2). Add an atLaunch test with a row older than 14 days that must be gone afterwards (kills M3). Add the three to a mutants file.

## P3 notes (review only, no board line)

- **N1.** `RunLogRecorder.swift:197`. A `tree_too_large` row is written again for the same fault every 14 days. `render-fault.json` stays on purpose, the dedupe reads only the rows, and the prune removes the old row. Fix: also keep `fault_ts` in a small file beside render-fault.json, or skip the row when the fault's mtime is older than the retention window.
- **N2.** `CrashMarker.swift:79`. The `name` line is not newline-checked, unlike `widget` and `trigger`. A file name containing `\n` can inject `run`, `launch` or `widget` lines that `collect` reads (the last line wins). The effect is limited to the person's own log and badges, so this is not held. Fix: drop or escape a name containing `\n`, as the widget line does.
- **N3.** `WidgetWriter.swift:176, 261`. `peak_mb` is the process lifetime peak, so it is absent for any run that does not set a new process high. That will be most runs after the first heavy one. It also includes memory raised by whatever ran while this run waited in the queue. The T-1140 line asks for "peak_mb from task_info around the run", and ADR line 310 needs it for the (c) demotion rule. A per-run figure needs a footprint sample during the run, or an interval peak with a reset. Check that any reset call is public API before using it (Guideline 2.5.1).
- **N4.** `RunLogRecorder.swift:81-86`. An expiry that lands after `prepare` leaves the row as the run's real outcome (say `ok`) while status.json stays `expired`. The tree was written, but the widget shows the stale clock until the next run. This is rare and harmless to the counts. Note it in the Activity spec or re-read the row outcome there.
- **N5.** `WidgetWriter.swift:298`. If `beginBackgroundTask` is called with no background time left, it can return `.invalid` (or expire at once), and the body still runs the App Group writes without an assertion. This is bounded by the 0.5 s lock wait. Accept it, or skip the write when the id is `.invalid` and let the next run write.
- **N6.** The assertion covers only the sink and the log, not the Python run. A suspension mid-run with budget timers on wall-clock time can turn a foreground run into a `timeout` row on resume. This predates these commits. Mention it in T-1677's Simulator check.
- **N7.** `RunClaims` and `budgetStopped` are bounded at `PyBridge.contextMemory`. Entries are never taken by recorder-less writers (tests), but the bound makes that harmless.

Board lines for Idris: F1 T-1679, F2 T-1680, F3 T-1681, F4 T-1682, F5 T-1683.
