## Against the chair lines

- **7:51 PM item 2: set once, kept, badge from the second refusal.** Line 204 sets `oom_guard_since` only when it is nil. Line 248 badges on `since < ts`, and only with a tree (line 243). ok, error, timeout, stuck, killed and expired clear it, and the test loops over all six, including the next refusal starting a new streak. Strict `<`, a nil `ts` and a nil `since` are each pinned (`badge-on-same-instant`, `badge-without-ts` and `badge-without-since` die).
- **20:00: a missing status reads as a refusal already under way.** `old == nil` gives `missingStatusSince`, which is `distantPast` when it round trips and `ts - 1 s` when it does not. Badge with a tree, none without one, the value survives the round trip, and the next refusal keeps it. All of these are tested. The fallback branch can't be reached on the host, and the chair asked for the badge to be tested, not the value. That is acceptable.
- **`deferred` keeps `oom_guard_since`: correct.** I judged this on its effect, not on the author's reading. `RunLogRecorder.status` sends a `deferred` run word to `.deferred`. By its contract from before T-1714 (pinned: my `deferred`-writes-`ts` mutant dies), that changes only `deferred_since`. It writes no `last_outcome` and no `ts`, and nothing ran. If `deferred` cleared the streak, then refusal, deferral, refusal, deferral and so on would leave the picture stale with no badge for as long as the pattern lasted. That is the 4:54 PM item 2a break that 7:51 PM item 2 exists to close. So keeping it is required, not just allowed. At HEAD this is not hypothetical: the extension lane itself writes `.deferred` for a late turn and a closed lane (ExtensionLane.swift `logLate`, `logClosed`). The ADR's words "cleared by any other outcome" read literally against `Outcome.deferred`, so they need a half-line (item (b) below, T-1741).
- **Codec:** key, `Key.all`, encode and decode are all there, and unknown keys and `expired_runs` are still carried ("oom_guard twice" row). Byte-stable encoding is unchanged.

## Once per reload (T-1728)

T-1714's rule counts **writes**, not reloads. `since < ts` is true at the second `oomGuard` call whenever it comes. Nothing in T-1714 is wrong here, and it claims nothing more. But the 7:51 PM sentence "one skipped reload is not a stale picture" now depends entirely on the caller.

At HEAD that caller exists. 0e756d6cc (T-1854, T-2035) has `ExtensionLane.refused` write `.oomGuard` on every refused turn (ExtensionLane.swift:333, and :338 on the demotion branch), with no count per reload. `refresh` joins a family's request only while the earlier turn is still in flight (`inFlight[id]`, :171). A refused turn returns almost at once, so a second family's request in the same reload usually gets its own turn and writes a second `oom_guard`. That badges from the first reload, which 7:51 PM forbids. The flag is off, so no user sees it yet. It is finding (d) below. It is not a defect in T-1714, and it is not mine to fix in T-1854.

The only per-run identity is `process`, and keying on it would undo 7:51 PM's one-process case. So I find no clean per-reload key at HEAD. Idris reached the same conclusion on his own and stopped T-1728 for Ines's ruling (T-1751, options A, B and C). I note on T-1728 and T-1751 that the per-turn write has already landed, and that `oomGuard`'s docstring (WidgetStatus.swift:195-200) should state the caller's duty: one call per widget per reload, or whatever unit T-1751 picks.

## Findings

- **P2 (rule, for Ines; then Idris) (a): the first refusal after a failure drops a real error badge for one reload.** `error`/`timeout`/`stuck`/`killed` badge. A following `oomGuard` (WidgetStatus.swift:201-207) keeps `failing_since` and the failure details, but sets `oom_guard_since = now`, so `showsBadge` is false until the next refusal. The picture was already stale, from the last good render before the failure, so this is a 2a break for one reload. It existed before T-1714, when `oom_guard` never badged, and T-1714 shortened it to one reload. It can't be fixed in code without changing 7:51 PM's "the first stays unbadged". Suggested rule: `oomGuard` on a status with `failing_since` set reads as a refusal already under way, the same branch as 8:00 PM's missing status.
- **P3 (wording, for Ines) (b):** in ADR-007 7:51 PM item 2, "cleared by any other outcome" should say that `deferred` keeps it, for the reason above, so the next reviewer does not flag it again.
- **P3 (observation, for Ines; no fix asked) (c):** 8:00 PM's branch keys on the file being absent (`old == nil`). After a deletion, if the next write is a `deferred`, that creates a status with no outcome, and the next refusal starts a plain streak, so no badge until the one after. The deleting script needs an app-side deferral to land between deletion and refusal each time, and it doesn't control those, so this is not a sustained route. The one-token alternative (`old?.lastOutcome == nil`) survives the suite (mutant `R-missing-means-no-outcome`). If Ines wants it, it needs a test.
- **P2 (outside T-1714; for T-1728 under T-1751's ruling) (d): the lane already writes one `oom_guard` per refused turn.** ExtensionLane.swift:333 and :338 (0e756d6cc) call `.oomGuard` on each refusal, and two families in one reload get two turns, so `oom_guard_since < ts` badges at the first reload, against 7:51 PM item 2. The flag is off, so this blocks opening it, not the build. The fix is T-1728's count, once Ines rules on T-1751. Option A adds a per-id set under `lock` in this same function.
