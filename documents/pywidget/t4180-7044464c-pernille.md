## What holds

- The check itself is sound and unchanged: a token made from random letters each run, read by Vision off the placed
  widget's own pixels (:308). A stale tree, an old snapshot or a broken write cannot pass it: if the app does not write
  this run's tree, no pixel on the Home Screen carries this token. The test cannot pass with the write path broken.
- The loop now looks the widget up again on each pass (:300) instead of shooting an element found once, so a widget
  that SpringBoard re-lays out is not shot by a stale reference, and one that disappears fails with its own message.
- The before-run read (:278) is print-only and fails nothing; it is useful evidence of what WidgetKit drew on placement.
- placeTreeWidgets removes every PyWidget widget first (:1950), so testE leaving its widget placed harms no later test.
- The site test change is right: aside boxes are left out of the step-order check, and UITests is copied so the
  aside's anchor resolves in the test's copy.
- The records of 7044464c agree with log/ and the runner: both jobs were created (ops/jobs/J-20261118-1733-xc-test-3
  and -4, task T-4898, the outbox purposes word for word, at d4a9445325, which contains b13c2df276), and the event
  (log/events.jsonl, 11:54:45 AM) says "two runner full runs queued", which was true when written.

## Findings

### H1 (High): the reorder does not fix the red; both runner runs it queued failed the same way

WidgetKitCheckTests.swift:272-308 at 7044464c. J-20261118-1733-xc-test-3 and -4 (runner 30, at d4a9445325, finished
8:08 PM and 8:10 PM) each executed 2,257 tests with exactly one failure, WidgetKitCheckTests/testETokenOnTheHomeScreen, at
:308 with Vision reading "Choose", "a widget", "Touch and hold, then", "Edit Widget", "PyWidget" (the T-4962 line quotes
the message). That is the same card as before the change (J-20261118-0405, -0802). T-4898's own done-when, two full
runs with testE green, is not met, and the cause the commit names ("the run wrote tree.json and asked WidgetKit to reload
while no widget was placed") is shown not to be the cause: with the widget placed first and the reload after it, the
placed widget still showed the card at the last read, 30 s after the run.

The local evidence could not have shown this. The commit says that in both local iterations the newly placed widget
already showed the previous run's token before the run, so on that Simulator widgets/new_widget had a tree and the
unset widget was never on the card; the runner's state (the card, after SettingsUITests' Reset to first launch has
emptied the App Group) was never reproduced locally. A local green there was expected with either order, so it says
nothing about the fix. No red was seen before the change. The local log (ops/runs/xcodebuild-20261118-113415.log) is
not in the repository, so I could not read it.

What fails: main stays red on every full run, and a fix was recorded as made. T-4898 is still open, which is right; it
must not tick on b13c2df276. Fix: reproduce the runner's state first (Reset to first launch, or delete
widgets/new_widget and reload, then the test) and see the card red locally before changing the steps.

### H2 (High, outside the diff, found checking the records): T-4962 ticked "main passes again" on a job that cannot run this test, and T-4962's own run is red

b7d07e38b8 (T-4962) bears on this review: it throws away T-4898's ordering (it runs first, then places, and now
chooses a fresh widget id in Edit Widget), so none of b13c2df276's test steps remain on main; only the site test
change does. But its outcome matters for T-4898's line. T-4962 was ticked at 10:15 PM by tools/runner_watch.py on
J-20261118-2200-land-m-46de23: at a30f1835e0, which does not contain b7d07e38b8, and a land job runs the unit target
only (tools/main_gate.py:2063-2065, "the whole unit target"); it executed 2,120 with 2 skipped, against 2,257-2,262
executed and 41 skipped on a full run, so testE was not in it. Then T-4962's own full run, J-20261118-2217-xc-test at
b7d07e38b8, finished 11:18 PM red on testE alone (2,262 executed, 1 failure). Nothing on the board or in log/ says so yet.

What fails: tools/runner_watch.py:311 marks every land job `covering`, and `shows_green` (:275-283) takes any passed
job as proof that the error is gone, so a red in PyWidgetUITests is "cleared" by a job that never ran PyWidgetUITests.
The board says main is green and lands queue while the full suite is red. Fix: a job covers a red only if its test set
can contain the red's test (a land job never covers a PyWidgetUITests red); a fixture test where a passed land job
leaves a UI-test red open, red against today's code. Board line added.

### M1 (Medium): the records state a disproved cause as fact

log/events.jsonl, 2026-11-18T11:54:45 (Idris, fix): "the run reloaded before the widget was placed, and a new placement
can keep an earlier render. The test now places first". The same claim was in the code comment
(WidgetKitCheckTests.swift:267-271 at 7044464c) and the page (script-to-home-screen.md:58 at 7044464c, "Now the widget
is placed first, so the redraw request reaches it"). H1 shows it did not. T-4962 rewrote the comment and the aside to
say the order made no difference, which is true; the event cannot be edited, so my review event records the correction.
Lesson for the record: a hypothesis seen on one Mac goes in as "suspected", and the runner's result decides.

### M2 (Medium, addressed by T-4962): at 7044464c the test proves a Debug-only path, not the one a person takes

WidgetKitCheckTests.swift:276 with Widget/PyWidget.swift:53 and Shared/WidgetPlacement.swift:186. The widget is left
unset, and an unset widget draws widgets/new_widget only through the Debug test hook (`testHooks && hookTree()`); a
shipped build always draws the Choose a widget card for it. So the test showed the run's tree reaching a Debug-only
unset widget, not a chosen one. This predates T-4898, which kept it. b7d07e38b8 now chooses the widget in Edit Widget,
which is the person's path; no line needed.

### L1 (Low): the event links a commit that is not on main

log/events.jsonl, 11:54:45: link 0f66d66b93, which is only on <span title="An idea that reaches B or better but is held below B by a measured cap. No graders until a permitted reading lifts the cap.">parked</span>/b/20261118-124539-16894; main's commit for the
same change is b13c2df276. A reader following the link from the site finds a commit main does not have. Fix in the
tool that writes lane events (the link should be rewritten to the landed hash at land), or leave it: the summary names
T-4898, and the grep finds the right commit.

## Verdict

FIX FIRST. The test's check is sound and cannot pass with the app's write broken, but the change it was made for did not
work: both runner full runs it queued failed testE on the same card (H1), and the cause it recorded is disproved (M1).
T-4962 replaced the steps, and its own full run is red too, while the board ticked it green on a land job that never
runs UI tests (H2). T-4898 stays open with Idris until two full runner runs show testE green; H2 goes to Odalys.
