## The atomic write, both halves

- **Order.** Python: `os.open(O_CREAT | O_EXCL, 0600)`, `json.dump`, `fh.flush()`, `_sync`, close, `os.replace`.
  Swift: `open(O_WRONLY | O_CREAT | O_EXCL | O_CLOEXEC, 0600)`, a write loop that retries `EINTR` and continues on a
  short write, `sync`, close, `rename`. In both the bytes are on the disk before the new name can be: right.
- **The sync.** `F_FULLFSYNC` first, plain `fsync` when it fails, on both sides; that is the right call on Apple
  systems, where `fsync` does not flush the drive's cache. Swift's `fcntl(fd, F_FULLFSYNC) != -1 || fsync(fd) == 0`
  matches Python's `_sync`.
- **The folder.** Neither side syncs the folder after the rename, and both say why. I agree: on APFS the rename is
  one metadata transaction, so after a power loss it is either there (pointing at data already flushed) or not there
  (the old file whole). The worst case is that the last save is lost and the previous settings come back, never an
  empty or short `premade.json`, which is what L2 was about. Any later full flush persists it. Not a finding.
- **Fails closed, no partial file.** Python: every `OSError` (makedirs, the sidecar open, the temp's open, write,
  flush, sync, close, replace) reaches `save()`, which returns False; on any exception in the write block the temp
  file is unlinked (M4 shows the tests hold that), and the file is never touched before the rename. Swift: a failed
  open, write, sync or rename unlinks the temp and throws `.writeFailed`; the file is never opened for writing. Right.
- **What a False leaves.** `store.dirty` is cleared only after the rename, so the run's keys wait for its next save,
  as the contract says (`test_a_folder_it_may_not_write...` pins it).

## Findings

No High, no Medium.

### L1 (Low): the real sync's failure path is not pinned on either side

The tests replace `_sync` (Python) and `sync` (Swift) whole, so the fallback's own failure is not tested: M5, a
`_sync` that swallows the `fsync` error, passes all 27 tests, and a save after a failed flush would then rename an
unsynced file and return True, the case L2 exists to stop. On Swift the default `sync:` argument is the only
production wiring and nothing pins it either (`{ _ in true }` would pass by reading). Suggested: a Python test that
makes both `fcntl.fcntl` and `os.fsync` raise and asserts `save()` is False with the file byte for byte and no temp
file; a Swift test that calls `write` without the seam on a descriptor where both fail is harder, so at least a test
that `sync` returns false on a closed descriptor (`fcntl` and `fsync` both give `EBADF`).

### L2 (Low): s2.3.1, the contract every writer follows, does not name the sync

L2 asked for a shared decision for s2.3.1. Both halves now do the same thing, but `premade-inputs.md` s2.3.1 still
reads "Write a temp file in the same folder, rename it over premade.json, then release", with no flush, no
`F_FULLFSYNC`, and no word on the folder. The next writer (Habits' Done today button, the second writer of `habits`
in s2.3.1's dated line of 2026-11-17) will be built from the text, not from this code. Suggested: one bullet in s2.3.1 with the order
(write whole, `F_FULLFSYNC` then `fsync`, fail closed, rename, no folder sync and why), citing T-4533.

### L3 (Low, not the author's): a third premade.json writer has the same window

`pywidget/ios/Shared/LauncherPremadeSlots.swift:64` writes the launcher premades' `premade.json` with
`Data.write(.atomic)`, which does not flush before its rename, and `:53-54` leaves an unreadable file alone for good
(`.unreadablePremadeFile`), so a power loss in that window sticks the launcher's slots as L2 described. It is outside
s2.3.1 (the editor is that file's only writer) and outside T-4533's targets; it is my code (T-4211, T-4218). After
TestFlight.

### Notes, not findings

- A value `json.dump` cannot encode (a NaN with `allow_nan=False`, an object) raises `ValueError`/`TypeError` out of
  `save()` rather than returning False. The temp is unlinked and the file untouched; it is a premade's bug, not a disk
  error, and was so before T-4533.
- If `os.close(lock)` itself raised after a good rename, `save()` would return False for a written file. Closing a
  lock descriptor does not fail in practice; harmless either way (`dirty` is already empty).
- Swift ignores `close(fd)`'s result after a successful sync; with the bytes already flushed, that is fine.
- The s2.3.2 decision (fixed before the App Store release, both halves in one commit, as T-4835) matches what my
  review recommended and is on the board as T-4835 with tests for 12 hours east and west.

## Verdict

**PASS with findings.** The atomic write is right on both halves: the temp file is written whole, flushed with
`F_FULLFSYNC` (plain `fsync` as fallback) before the rename, every disk error fails closed with the file as it was and
no temp left, and skipping the folder sync is sound on APFS. It closes L1 and L2 of [`t4468-lock-idris.md`](t4468-lock-idris.html) for the two
writers they named, and s2.3.2 is decided. Open, none blocking TestFlight: the real sync's failure path is untested
(L1) and s2.3.1 does not yet state the sync (L2), both to Pernille; the launcher's own writer has the same window
(L3), to me.
