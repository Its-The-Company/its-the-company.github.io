## Verdict: PASS with findings

The location work does what the privacy policy says for the runtime's own reading. Distance no longer writes a fix
into premade.json and removes an older build's `_reading` on every path, including the `off` one, through a locked
drop that keeps what the page saved since (M1, M2 killed). The runtime's cache is marked out of backups at launch
under the cache lock (T-1241), and the reduced-accuracy floor covers both places a cached fix is served
(`LocationCall.swift:180` last_known, `:193` a background sample; `servableCache` at `:87` is the only reader of
`cached()`). The notification limits hold in Swift as well as Python, counted in Unicode scalars as Python's `len()`;
the per-script 16 replaces the per-run count that reset every run, and the test schedules across four runs.
Error wording is honest in the main: a bad reply or a locked device now ends the run as an error and keeps the good
tree instead of saying "Location is off" (M3 killed).

One promise is still broken in the same way T-4628 fixed for Distance: Altitude keeps a day of location-derived
readings in its App Group file, in backups, after access is turned off (M1). The Lows are limits that hold for one
run at a time but not for two, and messages or docs that say a little more than the code does.

## Findings

### M1 (Medium): Altitude keeps today's location readings in backups and after Location access is turned off

- Where: `widgets/premade/altitude.py:63-70` writes `samples` (up to 48 `[UTC time, metres]` pairs from today's
  CoreLocation fixes) and `_reading` (its time and vertical accuracy) to premade.json; the two `off` paths (`:35-37`
  status not When In Use, `:55-57` a refusal) return without touching either.
- premade.json is in the App Group: in device backups and kept when Location access is turned off (T-4628's own
  commit message says so, and that is why it removed Distance's fix). The privacy policy draft (`docs/release/
  privacy-policy-draft.md:35`) says the one last location reading pywidget keeps is out of backups and deleted when
  access goes; `:34` names backups only for saved places. An altitude profile with times is location data from those
  fixes, and it outlives the person's "no".
- Probe: a MemoryStore holding one sample from 20 minutes ago, Location `denied`: `altitude.read` returns `off`,
  `samples` is still there, and `dirty` is empty, so a save would not remove it either.
- T-4628 left Altitude unchanged on purpose ("Steps and Altitude unchanged"); this is the case it left open, not a
  regression. The review of T-4628 already asked Wrenna whether altitude counts as "the last location reading"
  (T-4649, open). This finding is the code half: whatever her answer, an `off` run should not leave the samples
  behind, and Store.drop makes that a few lines.
- Fix: on either `off` path, `store.drop("samples")` and `store.drop(k.READING_KEY)` and save (Store.drop exists
  since T-4628), with a host test like `test_an_off_run_removes_the_kept_fix`. Then either keep the profile out of
  the backed-up file, or ask Wrenna to name it in the policy beside saved places. Steps' kept counts are motion, not
  location; the policy makes no backup promise for them, so I leave them out.
- Board line: T-5293 (Idris, P1), noted against T-4649.

### L1 (Low): the per-script 16 and the app's 64 are counted and added without a lock

- Where: `ios/App/Device/NotificationsCall.swift:193-206` reads `center.pending()`, decides, and later adds; nothing
  serialises two `schedule` calls in the app process.
- Two runs of one script at the same time (a widget refresh in the app and a Shortcut run, say) can both read 15 and
  both add, ending at 17; the same holds for 63 and the app-wide check. `notifications.py`'s docs say a script
  "holds a quarter at most". The test schedules in sequence, so it cannot see this.
- Fix: one actor or lock around count-and-add in `schedule`, and a test that runs two schedules concurrently on a
  FakeCenter whose `add` yields.

### L2 (Low): the 2003 message states a cause seen only on a never-used Simulator

- Where: `NotificationsCall.swift:294-296`, "iOS has not finished turning on notifications for PyWidget yet." with
  "Try again in a minute."
- UNErrorDomain 2003 is not a public `UNError.Code`; the evidence (ops/runs/xcodebuild-20261117-142143.log) is a fresh
  Simulator. Nobody has seen what a phone means by it, so the cause and the minute are a guess there.
- Fix: say what is known ("iOS would not save this notification yet (code 2003)") and keep "try again", or check it
  on the next phone session and keep the wording if it holds.

### L3 (Low): a pick belongs to the process while its run lasts, not to the run

- Where: `FilesCall.swift:113` (`store.picked(path)` takes no run id), `:267-280` (`holdPicked`, `forgetPicked` by
  URL value).
- While run A is alive, another script's run can bookmark what A picked. And if two runs picked the same item, the
  first to end removes it for the other, whose `bookmark` then says "needs a file or folder picked with
  files.pick()" though it did pick it. Both need two runs at once, so this is rare.
- Fix: key the picks by run id and check the caller's.

### L4 (Low): two texts say more than the code

- `docs/design/bridge-contract.md` s4 item 7 still ends "the per-run <span title="A measured fact that holds a grade below a letter, however good the rest is.">cap</span> needs the run, so only Swift can hold it"
  and "Swift counter and check: T-0543, waits on Xcode": both landed, and the cap is per script now.
- T-3554's done-note says a script "whose time is nearly up" no longer has its notification scheduled while being
  told it failed. `device.py:152` skips the call only when the cut wait is 0 or less; with, say, 0.05 s left past the
  reserve, Swift is still called, can schedule, and Python raises BridgeTimeout whose message does not say the work
  may have happened. Either word the note and the timeout message for that case ("it may have been done"), or skip
  the call below a small floor, as for 0.

## Checked and fine

- T-4628: no coordinates written on a good run; `_reading` dropped on every path including `empty` and `off`; the
  locked save removes only the run's own dropped key (M1, M2 killed). The timeout now draws the notice, which is true.
- T-1241: `markCacheExcluded` runs at install beside `forgetLegacyCopy`, under `cacheLock`, and only marks a folder
  that exists; the stand-ins' default is a no-op, so no stand-in can make a folder.
- T-0543 L5: 1 km floor read on both cached paths; a coarse fix and full accuracy still served; the floor is not
  applied to live fixes, which iOS already coarsens.
- T-0543 L1: Swift checks before the permission gate, so a bad argument never prompts; NaN cannot reach Swift
  (Python sends with `allow_nan=False`, and `after > 0` is false for NaN anyway).
- T-0550: the read-back takes the path from the bookmark data itself, so it checks what was stored; a stale bookmark
  re-made in `resolve` skips the check, which is right (nothing was picked for it this run) and commented.
- T-3564: `sensor_status` matches by class name within the `pywidget` package only, so a script's own class named
  PermissionDenied cannot pass for one.
- T-3716: the test still proves bridge, cache and file agree with the Simulator's position; it now prints when
  something else moved the shared device.
