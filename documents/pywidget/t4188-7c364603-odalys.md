## Verdict: PASS with findings

The change does what the board line asked. A preview's budget is now whole when it starts: the dequeue skips the
queued-time cut for `.preview` only (PyBridge.swift:1347-1358), and doRun arms the budget timer from that start
with the full 2.0 s (PyBridge.swift:1442-1456), which is also the `budget_s` Python is sent (PyBridge.swift:530).
The wait has its own limit, `previewQueueSeconds` = 10 s (PyBridge.swift:790-795), through the same busy timer
widget and Shortcut runs use (PyBridge.swift:1095-1105). Widget and Shortcut runs keep the Q1 rule. Nothing here
can crash, lose data or block the main thread.

One thing gets worse in a case the change did not test: the gallery queues its twelve previews one after another,
and behind a run that will not end soon each now waits 10 s instead of 2 s before it gives up (M1). The other
findings are a test that can go green without testing its case (L1), and doc and comment text that is not quite true
of the code (L2). None of them holds TestFlight.

## Findings

### M1. Behind a parked console run the gallery now spends about 2 minutes on spinners before every tile fails

- Where: `ios/App/Gallery/GalleryPreview.swift:181-190` (runAll: one preview at a time, every tile, no stand-down);
  `ios/Shared/Bridge/PyBridge.swift:790-795, 1099` (a preview waits 10 s); compare `ios/App/Bridge/WidgetWriter.swift:271`,
  where the app pass stands down while `bridge.appRunPending`.
- The failure: a console run waiting in `input()` holds the script queue until the person answers. If the gallery
  is opened then, runAll queues the first tile's preview; it waits the full 10 s queue limit and ends `busy`, which
  GalleryPreviewRun.run reports as `.failed`. Then the next tile does the same. The catalog has 12 premades
  (widgets/premade/catalog.json), so the last tile gets its answer after about 12 x 10 s = 120 s; before T-3552 it was
  about 12 x 2 s = 24 s. That figure is computed from the code, not measured. The outcome is the same (every tile
  Failed, with Try again), but for two minutes the screen shows spinners that cannot end well. And `running` stays
  true for that whole time, so Allow and Try again on a tile earlier in the <span title="The App Store results a buyer sees for a search phrase. The top 10 is the first ten, dated the day we read them.">shelf</span> than the loop has reached do not
  start a run (GalleryPreview.swift:167-173, 194-198 call runAll, which returns at its guard).
- The same holds behind a 20 s Shortcut run, or a stuck run, but those are rarer than a console run the person left
  waiting.
- Fix: in runAll, before each tile, stop the loop when `bridge.appRunPending` (the app pass's rule) and leave the
  remaining tiles not run, so the next runAll (scene active, Try again) runs them; or stop the loop after the first
  `busy`. Either keeps T-3552's gain, because a widget run ahead is not an app run.
- Test: the gallery beside a console run parked in input(), queue limit shortened as in
  testT3552APreviewBehindAParkedConsoleRunEndsBusyAtTheQueueLimit: runAll returns within about one limit, and the
  tiles after the first are not run, not Failed.

### L1. The gallery-and-app-pass test can pass without any preview waiting behind a widget run

- Where: `ios/Tests/PremadeSensorStallTests.swift:180-208`, its guard at :207.
- The failure: the test's point is that a preview waits behind a stalled widget run for longer than its 2 s budget
  and still ends good. Its only "proves nothing" guard checks that some premade reached a stalled sensor, which the
  app pass alone satisfies. Whether a preview lands behind a widget run depends on how the two async tasks interleave.
  If they stop overlapping (the pass's placed and gates reads get slower, or the gallery finishes first), the test
  stays green and tests nothing from T-3552. In my run they did overlap: 23.0 s against 30.3 s for the sequential
  T-3393A test, n = 1.
- Fix: assert the case happened. For example, note each preview's queue time and the run it started after (record
  seqs, as testT3552APreviewQueuedBehindALongWidgetRunRuns does at :228-229), and require at least one preview that
  started more than 2 s after it was queued.

### L2. The contract's `busy` row and one code comment are not quite true of the code

- Where: `docs/design/bridge-contract.md:244` (s7, `busy`); `docs/design/bridge-contract.md:39` (s1, v5.10);
  `ios/Shared/Bridge/PyBridge.swift:791-794` (comment); `ios/Shared/Bridge/PyBridge.swift:1079-1086` (coalesce).
- (a) The s7 `busy` row still says `busy` is "a widget or Shortcut run whose budget ran out while it was queued".
  A preview now ends `busy` when its queue limit runs out, not its budget. The row should say so; its consumer column
  has no preview case either (the gallery tile shows Failed).
- (b) v5.10 says the wait has "its own limit, 10 s" without saying from when. A preview that coalesces gets a new
  `Queued` with a new busy timer (PyBridge.swift:1085), so the 10 s count starts again from the latest request, as
  the v4.4 sentence says for widget budgets. Today only the gallery queues previews, one per tile, so this never
  happens. Once the editor's preview pane calls `PyBridge.preview` (no app caller yet), saves less than 10 s apart
  keep one preview waiting behind a parked run. That is probably right, but the contract should say it.
- (c) The comment says "a gallery preview waits behind at most one" widget run. That is true of the app pass, which
  runs its widgets in order (WidgetWriter.swift:267-279). It is not true of widget taps (v5.11, T-4565: every tap is
  its own key and never coalesces, PyBridge.swift:435-438), or of a Shortcut run (20 s). Behind those a preview can
  end `busy` at 10 s. The 10 s figure still makes sense; the comment should list where a preview ends busy.
- Fix: text only. Bump the contract to v5.10.1 or fold it into v5.10's row.

## Checked and fine

- The busy timer and the dequeue race: the dequeue cancels the timer under `jobs` (PyBridge.swift:1333), and
  expireQueued removes the run under `jobs` before it emits (PyBridge.swift:1108-1115). If the handler is already on
  its way, it finds nothing and emits nothing. A run gets exactly one of `busy` or a start.
- `previewQueueLimit` is read and written only under `jobs`: makeBusyTimer is called only inside enqueueBackground's
  `withLock` (PyBridge.swift:1085, 1089), and the test setter is DEBUG-only and takes the lock (:787).
- A stalled sensor cannot leave a preview hung. A widget run ahead holds the queue for at most its 5 s budget plus
  the <span title="Our grade scale, nine steps: D, D+, C-, C, C+, B-, B, B+, A. An idea&#x27;s ladder is the letter it reaches before any cap.">ladder</span>'s 5 s, then it is `stuck`. The preview's 10 s starts after that run began, so a run that returns before
  `stuck` always lets the preview start in time. If the run is stuck, the preview ends `busy` at 10 s and
  RunResultSink.collect returns on that `finished` record (RunResultSink.swift:74-82), so the tile does not hang.
- No main-thread wait: GalleryPreviewRun.run is nonisolated and async; the enqueue holds `jobs` only briefly.
- Test timing margins: a 1.0 s busy loop inside a 2.0 s budget (:234-252); a 3.0 s widget run inside its 5 s budget
  and the preview's 10 s limit (:217-231); the parked-console test asserts only a lower bound (:269), and dispatch
  timers never fire early. Taken with test 2, test 4 also pins the knob: test 2 shows a preview may wait more than its
  budget, and test 4 shows the shortened limit is the one used. The busy loops use `time.monotonic`, so load lengthens
  only the overhead around them.
- Teardown: the queue-limit override is put back by a teardown block (:258), and the device handler too (:183).
- The tick: the board's done note names 9231ed7070, which is on HEAD. The outbox record in 7c36460373 names
  106de8a7d0, the same change before it landed (on parked/a3/20261116-044720-91557). Only the board's hash matters.
- Info, no line: a preview with `budgetS: nil` gets no busy timer at all (PyBridge.swift:1097), so its wait has no
  limit, against v5.10's wording. No caller passes nil (Premades.swift:50 and PyBridge.swift:1016 default to 2.0 s).
