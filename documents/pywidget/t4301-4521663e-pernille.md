## Verdict: PASS with findings

The fix is the one L1 asked for, and it is narrow. `WidgetPasses.pass` (WidgetWriter.swift:685-704) sets `waited`
inside the `while let running = inFlight` loop (:691-693), and passes it, captured by value, into the task that
runs the pass (:699). Between the end of that loop and `inFlight = ...` (:700) there is no `await`, so no other pass
can start in between. `refreshPlaced` (:178-190) hands `runSteps(read, waited:)` to `refresh(_:trigger:from:)`.
`runSteps` (:197-199) returns a new `PassSteps()` for a pass that waited and whose first read answered. Then the
first premade's `proCheck` calls `gates(&pass)` (:442-449), which calls `proGates`, and `proGates` is
`ProEntitlement.gates()`. That function asks StoreKit's current entitlement and, only when there is no purchase,
the tester switch, on every call; nothing is cached between calls. So every way Pro can change while a pass
waits reaches the queued pass through one fresh read:

- Bought, restored, or the tester switch turned on during the wait: the queued pass reads `entitled: true`. A
  placed Pro premade runs and is written (the new test shows the bought case). It is no longer `.skipped("locked")`.
- Refunded, revoked, or the switch turned off during the wait: the fresh read is `entitled: false`. Each Pro
  premade, placed or offered from the old read, is `.skipped("locked")`, with no run and no tree. Nothing is drawn
  as Pro after Pro has gone, and no Python run is spent on it.
- The first read did not answer (`gatesUnanswered`): `read` is kept. Pro premades are nil, so `deferred` and
  never `locked` (:436), and StoreKit is not asked a second time. That keeps T-4277's M1 saving as the line asked.

The new `PassSteps()` loses nothing else. The read before the pass sets only `gates` and `gatesUnanswered`
(:446-447), never `pruned` or `hung`. A pass that did not wait keeps its single read (the T-4277 test still pins
`reads == 1` for that case). The other `passes.pass` callers go through the old `run:` overload, which now forwards
to `waitedRun` and drops the flag. Their runs start from `PassSteps()` inside the task, so they already read after
any wait. No new race: the read now happens inside the task, after the wait has ended.

What still comes from the pre-wait read is the offered list (first renders of unplaced premades). That is safe in
both directions. After a refund, an offered Pro premade is skipped as locked by the fresh read. After a purchase,
the queued pass offers no new Pro premade. The activation that follows the purchase then has ids that are not a
subset of the queued pass's ids, so it neither joins that pass nor is spaced out by it, and it runs those first
renders itself.

## Findings

### L1 (Low): the test's 50 ms start-up sleep can go red under load

- Where: Tests/WidgetWriterTests.swift:594 (`Task.sleep(for: .milliseconds(50))`, then
  `XCTAssertEqual(held, ["other"])`), and the `proGates` closure at :579-582.
- The test assumes that the `ahead` task reaches the actor and sets `inFlight` within 50 ms. On a loaded runner it
  may not. Then the assertion fails, `refreshPlaced` starts first without waiting, reads `entitled: false`, and Clocks
  is skipped. The result is a false red, never a false green. Today's runner run was green, but the margin is a
  sleep.
- The closure also counts the read before it reads `entitled`. If `ahead`'s 5 ms poll wakes between those two lines,
  the first read already sees Pro. The `reads == 2` assertion still catches the mutant then, so this does not hide
  a regression, but the Clocks assertion stops meaning what its comment says.
- Fix: poll `await passes.inFlightIDs == ["other"]` with a deadline (as `ahead` already polls `reads`) instead of the
  fixed sleep. In the closure, read `entitled` first and then count the read.

### L2 (Low): the hung-and-waited branch is pinned only on `runSteps` itself

- Where: WidgetWriter.swift:188 and :197-199; Tests/WidgetWriterTests.swift:605-610.
- The three `runSteps` assertions <span title="A test written in advance. If it fires, we drop the idea.">kill</span> any mutant inside `runSteps`. But they do not cover a change at the call
  site. Traced: replace `Self.runSteps(read, waited: waited)` at :188 with `waited ? PassSteps() : read`. The T-4301
  test stays green, because its first read answered. T-4277's hung case stays green, because it never waits. The
  `runSteps` assertions stay green, because `runSteps` is unchanged. In the product, a pass queued behind another
  after a StoreKit hang would then wait out `stepLimit` (15 s) a second time, which is the cost M1 removed. The
  refund direction is not driven end to end either.
- Fix: a second case in the same test, where `proGates` hangs on its first call (WidgetStepTimeoutTests.Hang) and
  the pass waits behind a held one. Expect `hang.callers == 1` and Clocks `deferred` (not `locked`, no tree).
  Optionally add the mirror of the bought case: entitled first, refunded during the <span title="What keeps an idea below the top: the cap that applies to it now.">hold</span>, so Clocks is
  `.skipped("locked")` with no tree.

### L3 (Low; nit): refreshPlaced's doc comment still says one read decides each id's check

- Where: WidgetWriter.swift:172-176 ("the Pro gates are read once, before the pass, and decide both the offered list
  and each id's check").
- Since this change, that holds only for a pass that did not wait. `runSteps`' own comment explains the rest. One
  clause here ("unless the pass waited behind another; see runSteps") would keep the next reader from undoing it.
- Also for the record, and not from this change: a purchase that lands after a running pass has read its gates
  still leaves that pass's Pro premades locked. A same-ids activation then joins that outcome or is spaced out for
  30 s. That is T-3900's one read per pass. It heals itself for a first-time buyer, whose new Pro premades make the
  next activation's ids different. A re-buyer whose every Pro premade already has a tree waits for the next
  activation after 30 s. I am not filing a line for it.

## Checked and fine

- Bought, restored, refunded and the tester switch: one code path (`ProEntitlement.gates`, a fresh read each call),
  covered above.
- `waited` when the pass ahead was let go for no progress (`ended` returns nil): the loop still set `waited`, so the
  queued pass reads again. That is correct, since the wait was long.
- `waited` set when the pass ahead ended almost at once costs one extra StoreKit read, and only on an answered
  StoreKit.
- Swift 6: `[waited]` captures a copy into the `@Sendable` task closure. There is no shared mutable capture.
- The test fails on the mutant the commit message names (keep `read` always): `reads` is 1, not 2, and Clocks is
  `.skipped("locked")`. Traced, not run.
