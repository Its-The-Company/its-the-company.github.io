## Verdict: PASS with findings

The first case is a real end-to-end run, not a stub. The request is Swift's own: `RunRequest.widgetAction` builds it,
`bridge.run` sends `request.json()` (PyBridge.swift:1475, `pw_rt_run`), and the bundled `_pywidget_runtime` package
(App/Runtime/_pywidget_runtime, the real runtime; the "stand-in" in BridgeTests.swift's header comment is out of date,
not this commit's) parses it, runs `add` and renders. The state can only be `{"n":251}` if the handler ran with
`args["by"] == 250`: a skipped handler leaves `{"n":1}`, and a float 250.0 gives 251.0, which `_checked_state`
(widget_tree.py:393) writes back as `251.0` and the substring assert at WidgetActionRequestTests.swift:363 refuses.
That assert is the one carrying the int check; the `as? Int` at :362 is satisfied by 251.0 too (Foundation bridges an
integral NSNumber to Int), so it adds nothing on type, only on value.

Mutants, traced:
(a) `json()` writes `tapID` (the board line's Done-when): `parse_action` refuses an unknown action key, the run ends
`error`, `WidgetRequestError`; case 1's status assert fails. KILLED.
(b) `json()` drops `action`: a plain widget run, state `{"n":1}` (or none); case 1 fails on 251. KILLED.
(c) the args splice misses (the mark goes out as a string): `decode_action_args` cannot decode it, `WidgetRequestError`;
case 1 fails (and the debug `assertionFailure` stops the run first). KILLED.
(d) the runtime's `_args_number` stops turning 250.0 into 250: state `{"n":251.0}`; :363 fails. KILLED.
(e) `function` sent as the tap id: an undeclared action, an error outcome; case 1 fails. KILLED.
(f) Swift re-serializes args with JSONSerialization (`250.0` becomes `250`): case 1 stays green, since an int arrives
either way. Not this test's job: `testActionGoesAsFunctionArgsAndTapIDWithTheArgsBytesAsGiven` pins the bytes on the
wire. Survives here, killed by the class.

Timing: no flake I can find. `records()` registers its subscriber with an async block on the serial consumer queue
before `bridge.run` is called (PyBridge.swift:1255-1266), so no record of the run can be drained before the subscriber
exists, and the AsyncStream buffers until RecordLog's task reads it; the 30 ms sleep is belt and braces. The wait is
a 30 s poll on the finished record, with a 30 s run budget, against a job whose 18 cases took 79.1 s in all on the runner. A
slow machine makes it wait, not fail, up to 30 s.

The second case is honest about what it shows, a runtime refusal reaching Swift as `error`, `WidgetRequestError`, no
tree, but it is not an action-path test (L1). The contract line describes both cases correctly, except where it says
they are (L2).

## Findings

### L1 (Low): the refusal case cannot fail when the action path breaks

- Where: WidgetActionRequestTests.swift:366-378; widget_tree.py:309 (the id rule) runs before :320 (`parse_action`).
- `pywidget.calc` from a text source is refused by the id rule before the action is looked at. So the case stays
  green under mutants (a), (b) and (c) above, and it asserts only the error's type: any other `WidgetRequestError`
  (a renamed action key, a first-party flag sent for text) would pass it too.
- Why it matters: little; case 1 carries the action path. But a reader of the contract line could take the second case
  as the proof that a bad action is refused end to end, and it is not.
- Fix: assert the error text names the rule (`widget.id`, `first_party`), so the case can only pass for the reason it
  names. Swift cannot build a bad action through `WidgetActionRequest.make`, which is why the id was the only refusal
  on offer; say that in the test's comment.
- Board line: T-5309 (Idris, P2), shared with L2.

### L2 (Low): the contract line names a class the two new cases are not in

- Where: docs/design/bridge-contract.md s7, "Swift tests: `WidgetActionRequestTests`, among them the two that send the
  request ...". Both cases are in `extension BridgeTests` (WidgetActionRequestTests.swift:327), so their test ids are
  `PyWidgetTests/BridgeTests/test...`.
- A run filtered to the class the page names, `-only-testing:PyWidgetTests/WidgetActionRequestTests`, runs neither,
  and xc.sh does not call it red because the filter still matched other tests. Runner job J-20261119-0824 (T-4565, at
  6cf68a9b8e, which holds 6d236933) used that filter with two other classes: green, 22 executed, and these two cases
  were not among them. My own brief named the class too; I found it only by reading the file.
- Why it matters: the class-filtered run is how reviews check this area. A full-suite run still includes them, so nothing
  ships untested today (I did not check which land runs included them), but a reviewer reading "green" would be
  wrong about what ran.
- Fix: write "`BridgeTests.testAnActionRequest...` and `BridgeTests.testARequestTheRuntime...` (in
  WidgetActionRequestTests.swift)", or move the two cases into a class of their own that sets up the bridge.
- Board line: T-5309, shared with L1.

## Checked and fine

- The source is the shape ADR-011 s7 asks: `@w.action("add")` returning a new state dict, `render` reading
  `ctx.state`. The state comes back in the `widget_tree` document, as s7 says, and the test reads the tree the
  finished record points at (`RunResultSink.tree`, by `tree_seq`), not any tree record.
- `state.count == 1`: no key leaks into the state.
- The refusal case asserts `treeSeq` nil and no tree, so a refused run that still rendered would fail it.
- The contract line's two descriptions match the asserts, and its claim that `{"by":250.0}` reaches the handler as an
  int follows from the tree's `251` (int plus int), given (f) is pinned by the wire test.

## Board lines

- T-5309 (L1, L2): the refusal case asserts which rule refused, and the contract line names the cases by their real class (Idris, P2).
